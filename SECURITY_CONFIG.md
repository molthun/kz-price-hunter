# Auth/proxy: настройка после этапа 2

Эти изменения подготовлены локально. DSM, reverse proxy, Docker и работающий сайт не изменялись.

## Подтверждённая владельцем топология

- Публичный сайт: `https://shop.molthun.ru`.
- Synology LAN: `192.168.28.10`.
- Внешний/NAT IP: `93.170.212.215`.
- Контейнер: Docker network mode `bridge`.

Это не определяет непосредственный TCP peer, который видит приложение: им может быть адрес Synology, Docker gateway или отдельного proxy-контейнера. Gateway из Docker inspect — кандидат, а не доказательство фактического peer.

## Переменные

```dotenv
APP_URL=https://shop.molthun.ru
PUBLIC_ORIGIN=https://shop.molthun.ru
ALLOW_DEV_LOGIN=0
TRUSTED_PROXIES=
```

Пустой TRUSTED_PROXIES безопасен: приложение игнорирует X-Forwarded-For/Proto и ограничивает частоту по непосредственному peer. За reverse proxy разные посетители тогда разделяют IP-limit; это ограничение доступности до точной настройки, а не разрешение доверять любым заголовкам. HTTPS cookie и CSRF работают по PUBLIC_ORIGIN и не требуют доверия к Forwarded-Host.

PUBLIC_ORIGIN — один канонический origin, схема/host/port без пути, query или credentials. Если пуст, используется APP_URL. Без обоих разрешены изменения только на прямом loopback с loopback Host. Вход через публичный домен и через LAN-адрес одновременно не разрешён автоматически: используйте канонический домен. Невалидные PUBLIC_ORIGIN/CIDR останавливают импорт конфигурации.

## Что подтвердить перед развёртыванием

1. На NAS определить IP источника TCP-соединения с портом приложения **из сетевого пространства контейнера**, во время собственного запроса через публичный домен. Читать только адрес/порт, без HTTP payload, cookies, env и содержимого запросов. `docker inspect --format '{{json .NetworkSettings.Networks}}' kz-price-hunter` показывает топологию и кандидатов, но сам по себе peer не подтверждает.
2. Включить в TRUSTED_PROXIES только подтверждённый proxy IP (`/32` для IPv4, `/128` для IPv6) либо минимальный управляемый диапазон. Не добавлять внешний NAT IP, все private networks или весь интернет. Убедиться, что контейнерный порт недоступен недоверенным клиентам напрямую и что Docker NAT не делает их неотличимыми от proxy.
3. Reverse proxy должен сохранять Origin и формировать корректные X-Forwarded-For/Proto. X-Forwarded-For разбирается справа налево до первого недоверенного адреса; левый поддельный префикс игнорируется. X-Forwarded-Host/Forwarded никогда не определяют разрешённый origin. Заголовки от недоверенного непосредственного peer игнорируются.
4. Проверить часы NAS: подпись Telegram принимается не старше 5 минут; допускается до 30 секунд будущего времени. Это окно выбрано проектом, не навязано Telegram. Алгоритм HMAC legacy widget сохранён, миграция на OIDC не выполнялась.
5. Перед запуском нового кода отдельно согласовать backup/restore и startup migrations. Только затем проверять реальный HTTPS login/logout, роли, cookies и запросы двух клиентов через proxy. В этом этапе restart/build/push/deploy не выполнялись.

Рабочий `.env` не читался/не изменялся; существующие ключи в settings.json сохранены. `.env.example` содержит только пустые поля credentials. Compose передаёт PUBLIC_ORIGIN/TRUSTED_PROXIES и принудительно отключает dev login; Watchtower не менялся.

## Контракт API и локальный вход

- POST/PUT/PATCH/DELETE требуют корректного полного Origin; отсутствующий/`null`/чужой origin возвращает 403 **до обработчика**. Это относится также к login/logout. Cookie остаётся HttpOnly, SameSite=Lax; Secure выставляется при публичном HTTPS.
- Явный live и AI-разбор через GET `/api/best-price` требуют `X-KZPH-Request: 1`. Этот заголовок добавляет интерфейс; браузерный запрос с чужого сайта не может отправить его без разрешения CORS, которое приложение не выдаёт. Если Origin присутствует, он тоже проверяется. Для обычного DB-only поиска заголовок не обязателен.
- Скрипты/API-клиенты, которым владелец передал сессию, должны явно указывать канонический Origin для изменений; это не замена авторизации и не секретный ключ. Жёсткая проверка может отклонять старые клиенты, не отправлявшие Origin.
- Локальная разработка: отдельный DATA_DIR, ALLOW_DEV_LOGIN=1, пустые ADMIN_TELEGRAM_IDS/APP_URL/PUBLIC_ORIGIN, прямой localhost. Любой X-Forwarded-*/Forwarded отключает dev-вход. Локальный principal имеет ID -1, Telegram ID должен быть положительным. Dev-сессия не принимается с LAN/proxy; его Telegram-уведомления выключены.
- Существующие реальные пользователи/сессии не удаляются. Старый dev user с положительным ID не получает специальных прав разработчика; если ранее dev login создал сессию реального admin ID, она остаётся обычной действующей сессией до выхода/истечения/блокировки. Принудительный массовый отзыв не выполнялся.
- Проверка Telegram-уведомлений ограничена тремя попытками за минуту на пользователя, ответ 429 содержит Retry-After.

## Telegram и приватность

Бот принимает только private-чаты с совпадением chat.id/from.id; группового opt-in пока нет. Регистрация на сайте для личного бота не стала обязательной. Блокировка и per-user/provider budgets сохранены. Четыре workers, очередь 64 и последовательность внутри одного чата ограничивают число незавершённых задач. При остановке задачи отменяются и ожидаются до закрытия HTTP-сессии.

Очередь и polling offset остаются в памяти; restart может потерять подтверждённую, но ещё не обработанную работу или повторно получить неподтверждённые обновления. Exactly-once и восстановление очереди не заявляются. Токен бота по-прежнему считывается при запуске polling; его ротация требует отдельного согласованного перезапуска.

[Карта данных и ограничения retention](PRIVACY_DATA_MAP.md). Уведомление пользователям `/privacy` описывает текущую обработку, не обещает несуществующего удаления аккаунта или данных у внешних провайдеров.
