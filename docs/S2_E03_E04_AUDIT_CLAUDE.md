## Проверено особо и признано корректным

### Умолчания состояния (B2) закрыты правильной формой

Было: `Condition.normalize(None) → NEW`, `Availability.normalize(None) → in_stock`, то есть
молчание источника давало уверенный ответ. Стало:

```
Condition.normalize(None)     → UNKNOWN
Availability.normalize(None)  → unknown
```

При этом реальный товар из обхода по-прежнему получает `NEW` / `in_stock`, потому что допущение
перенесено туда, где оно обосновано, — в точку вызова:

```python
condition = Condition.normalize(product.get("condition"), default=Condition.NEW)
```

Это ровно то разделение, которого не хватало: честное умолчание живёт в модели, а знание «эти 37
розничных источников продают новое» — у того, кто это знание имеет. Проверено сквозным прогоном:
товар из обхода получает `NEW`, фильтр «новое» его находит, фильтр «б/у» — нет.

Вопрос с «уценкой», который я записывал вторым пунктом, тоже решён: `уценка` → `OPEN_BOX`,
а не `USED`. Решение разумное — уценённый товар чаще новый с повреждённой упаковкой.

### Изменение схемы на живой таблице безопасно

S2-E03 добавляет в `offers` три колонки (`installment_available`, `credit_available`,
`pickup_available`) через `_ensure_column` — тот же приём, что и `database._add_column`:
проверка `PRAGMA table_info` и `ALTER TABLE ... ADD COLUMN ... DEFAULT 0`. Аддитивно,
`schema_version` не меняется.

Откат на 6.0.0 проверен по коду: и адаптер, и `OfferRepository.save_or_update` перечисляют колонки
явно, поэтому старый образ на таблице с лишними колонками работает без изменений, а значения
берутся из `DEFAULT 0`.

### Правило плана о способах оплаты соблюдено

План требует: «Не предполагаем способ оплаты только по площадке — сохраняем фактические данные».
Проверено: `installment_months` и признаки рассрочки берутся из данных самого предложения,
а не выводятся из того, что канал — Kaspi.

## E1. Тип канала определяется разбором строки идентификатора (среднее)

`ChannelType.from_channel_id` разбирает `channel_id` на токены по разделителям, включая `_`:

```python
tokens = set(re.split(r"[:_\-\s/]+", cid_lower))
for t in cls.ALL:
    if t in tokens:
        return t
```

Из-за этого составные типы никогда не находятся — они распадаются на части:

```
chan_mechta_website        → website            (верно)
chan_4mobile_direct        → direct             (верно)
chan_x_physical_store      → website            ← должно быть physical_store
chan_y_food_aggregator     → website            ← должно быть food_aggregator
```

Неузнанный идентификатор молча превращается в `website`, то есть неизвестное выдаётся за известное.
А `website` входит в `direct_channel_types`, поэтому `food_aggregator` попадёт в «прямые продажи»
и исказит сравнение «напрямую против площадки» — то самое, ради чего этап и делался.

Сегодня влияния нет: адаптер создаёт только каналы `website`, `direct`, `kaspi`, `forte`, `halyk`,
и все они разбираются верно. Дефект проснётся на этапах S2-E05 (Discovery), S2-E08 (Social)
и S2-E09, где появятся физические точки, агрегаторы еды и соцсети.

**Рекомендация.** Тип канала — это колонка `channels.channel_type`. Брать его соединением с
таблицей, а не разбором форматированной строки. Строковый разбор оставить запасным путём и при
неудаче возвращать «неизвестно», а не `website`. Это тот же класс связанности, что уже подводил
проект: определение продавца по отображаемому имени (замечание N3 аудита S2-E01).

### Почему S1 закрыт не частотным правилом

Первым делом я попробовал понизить порог «значение считается общим». Это оказалось неверно:
4mobile напрямую и 4mobile на Kaspi **делят домен**, и при пороге «общий для двух продавцов»
сломался бы золотой случай 1 — один продавец в двух каналах перестал бы склеиваться.

Настоящая причина была другой: `AUTO_MATCH` по домену выдавался, даже когда названия не имеют
ничего общего. Теперь домена одного мало, если названия несовместимы (ни одно не содержит другое):

```
4mobile      + «4mobile Kaspi»        на 4mobile.kz → AUTO_MATCH  (один продавец, два канала)
Мечта        + «Мечта Астана»         на mechta.kz  → AUTO_MATCH  (филиал)
Apple Store  + «Apple Reseller Almaty» на apple.com → REVIEW      (бренд и реселлер)
```

Реселлер уходит в модерацию, а не склеивается молча — это и требовалось планом. Частотное правило
осталось вторым рубежом, и теперь его есть кому вычислять: `SellerIdentityRepository.match_candidate`
подставляет `shared_identity_values()` из базы.
