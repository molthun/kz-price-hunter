# Эксплуатация единственного рабочего сервера

Актуальная схема с 22.11.2026. Это руководство для установки проекта; собственное развёртывание начинается с [INSTALL.md](INSTALL.md).

## Текущее размещение

| Что | Значение |
|---|---|
| Основной сайт | `https://shop.molthun.ru` |
| Старый адрес | `https://shdev.molthun.ru`, отвечает тем же кодом; проверка входа/редиректа — в передаче |
| Рабочий каталог | Каталог вашего checkout; в командах ниже `/path/to/checkout` — заменяемый пример |
| Единственное приложение | `kzph-stand` (имя осталось историческим) |
| Данные | `stand-data` → `/app/data` |
| Compose | `docker-compose.stand.yml` + `docker-compose.live.yml` |
| Шаблон live-дополнения в Git | `deploy/docker-compose.live.yml` |
| Порт для существующего DSM-прокси | `35540` → `35539` контейнера |
| Перезапуск | `unless-stopped`, задаётся live-дополнением |
| Старые контейнеры проекта | Прежнее приложение и автообновление остановлены по отчёту перехода |

База бывшего стенда стала единственной рабочей БД. Не запускайте старый прод, второй scheduler или второй poller с тем же токеном. Старые данные хранятся отдельно по политике резервирования. Их наличие не означает, что нужно поддерживать вторую активную среду.

## Проверить состояние

```bash
curl --fail https://shop.molthun.ru/api/version
curl --fail https://shop.molthun.ru/api/health
```

На хосте:

```bash
cd /path/to/checkout
docker inspect --format '{{.State.Status}} {{.State.Health.Status}} {{.RestartCount}}' kzph-stand
docker logs --tail 100 kzph-stand
```

Для подробного разбора используйте [диагностику](DIAGNOSTICS.md). Токен диагностики хранится локально; без него 404 — ожидаемое поведение, а не признак отсутствия сервера. В отчёты не выводить env, cookies и токены.

## Запуск и обновление

Для схемы проекта с live-дополнением оно должно лежать рядом с основным compose. Фактические адреса хостов, SSH-реквизиты, пути backup и секреты задаёт администратор локально; они не нужны для самостоятельного развёртывания из Git. Если его нет, скопируйте **проверенную** версию `deploy/docker-compose.live.yml` в корень checkout, не затирая существующие локальные настройки без сверки.

Всегда указывайте оба файла:

```bash
cd /path/to/checkout
docker compose -f docker-compose.stand.yml -f docker-compose.live.yml ps
```

После проверки кандидата и backup:

```bash
docker compose -f docker-compose.stand.yml -f docker-compose.live.yml build app
docker compose -f docker-compose.stand.yml -f docker-compose.live.yml up -d app
```

Команда только с `docker-compose.stand.yml` может убрать порт 35540 и автозапуск. Один `git pull` не является выкладкой. Изменения ограничений ресурсов, токенов и сети не входят в обычное обновление документации. Проверяйте фактически применённые overrides, а не старые комментарии основного compose.

Полный порядок проверки, публикации, обновления и отката — [RELEASE_AND_ROLLBACK.md](RELEASE_AND_ROLLBACK.md).

## Резервная копия и восстановление

Git хранит код; работающий каталог, пользователей, историю и настройки восстанавливают из backup. SQLite с активным WAL нельзя копировать одним `cp prices.db`.

Скрипт [backup.py](../scripts/single_live/backup.py) использует SQLite backup API и проверяет копию. Выбирайте **новый** путь назначения, отличный от источника: существующий файл назначения скрипт заменяет. Пример на хосте при наличии прав чтения БД:

```bash
cd /path/to/checkout
mkdir -p backups
backup_stamp=$(date -u +%Y%m%dT%H%M%SZ)
python3 scripts/single_live/backup.py stand-data/prices.db "backups/prices_${backup_stamp}.db"
```

Если файлы принадлежат root, выполняйте эту же операцию с соответствующими правами, а не меняйте права рабочей БД вслепую. В новой установке с другим каталогом данных подставьте его путь. Проверьте `quick_check=ok`, размер и доступность копии. Отдельно сохраните `.env`, внешние настройки и необходимые загруженные файлы; храните секреты защищённо вне Git. Держите копию на другом носителе/хосте и периодически проверяйте восстановление.

Для восстановления:

1. Выберите совместимый образ/коммит и нужную копию. Проверьте её через `PRAGMA quick_check` и запуск на отдельной копии без Telegram/сборщиков.
2. Остановите приложение с обоими compose-файлами. Сохраните текущую БД **вместе с её WAL/SHM при наличии**, не смешивая их с восстанавливаемым файлом. Предпочтительно сохранить текущий каталог данных целиком при остановленном приложении.
3. Поместите согласованную backup-БД на место `stand-data/prices.db`, восстановите владельца/права и соответствующие секреты. У восстановленного файла не должно остаться WAL/SHM от прежней БД; старые файлы сохраняются в отдельном архиве, а не удаляются до проверки.
4. Запустите приложение с обоими compose-файлами и проверьте health, вход, поиск, историю, избранное/наблюдения и работу бота.

Восстановление старой копии теряет изменения после её даты. Перед откатом сохраните новые данные и выберите способ их переноса; простая смена образа тоже требует совместимости схемы.

## Адреса и прокси

`shop` уже направлен на 35540 единственного сервера. Для `shdev`:

- смена порта назначения даёт два адреса одного приложения;
- HTTP-редирект на `https://shop.molthun.ru` с исходным путём и параметрами даёт единый browser origin, ссылки и вход.

Приложение настроено на один `PUBLIC_ORIGIN`. Поэтому прохождение главной страницы по второму адресу ещё не доказывает корректность авторизованных действий. Не расширяйте доверенные proxy-сети и не отключайте CSRF ради второго домена. Проверяйте вход и ссылки после настройки перенаправления.
