## C45RR-01 — закрыт в проверенном объёме

Значения памяти/диагонали из title теперь участвуют в проверке всех участников обеих групп,
включая участника без fields. Прежний независимый сценарий с корректным SAME для пары
128 GB больше не переносит третьего участника 256 GB: worker отказывает в общем переносе.

По коду и штатным регрессиям также проверены:

- такой участник в первой и во второй группах;
- другая диагональ при отсутствии fields, включая число, исключённое из k2 как часть модели;
- признаки готового компьютера у участника без fields;
- конфликт title с ёмкостью из прежнего ключа;
- отсутствие изменений рабочих таблиц при отказе;
- совместимая группа с одинаковой памятью продолжает объединяться;
- отсутствие ложного конфликта с мощностью модели, когда title знает только другую характеристику.

Ограничение из передачи сохраняется: если нет полей и явных признаков в title, остаётся
проверка имеющегося ключа. Эта приёмка не доказывает качество всех старых групп каталога.
Консервативный отказ для «8/256» против «256» автор указал явно; это ограничение полноты,
которое нужно измерить в C2, а не основание объявить точность/полноту уже подтверждённой.

## C45RR-02 — обычное открытие исправлено; остаток [P2] при прерывании обновления

Участок: `scripts/migrate_to_k2.py:343–348`.

Обычный путь теперь добавляет api_started, заполняет его из api_calls и сохраняет старый
baseline/счётчики. Dry-run читает старую схему через alias и не обновляет её.
Прежнее `OperationalError: no such column: api_started` больше не воспроизводится.

Но ALTER TABLE и последующий UPDATE не заключены в общую явную транзакцию. При используемом
SQLite-подключении добавленная колонка сохраняется до выполнения UPDATE. Если выполнение
прервётся между ними, колонка останется с DEFAULT 0. Следующий запуск видит колонку,
пропускает заполнение и считает api_unfinished как 0 минус прежние api_calls.

Независимый `upgrade_boundary.py`:

1. Создаёт временную БД со старым форматом учёта, сохранённым baseline и api_calls=3.
2. Вызывает настоящий load_baseline; настоящий ALTER TABLE выполняется, непосредственно
   перед UPDATE вводится исключение. Подключение закрывается.
3. Заново открывает БД и запускает настоящий run_migration без сетевых вызовов.
4. Получает api_calls=3, api_started=0, **api_unfinished=-3**.

Это ошибка учёта после прерывания обновления. Товары/цены не потеряны, исходный baseline
и прежние api_calls остаются. Наличие старой или частично обновлённой таблицы на реальном
стенде/проде в этой итерации не проверялось и не утверждается.

**Критерий закрытия:** добавление колонки и её исходное заполнение сохраняются атомарно
либо повторный запуск распознаёт и безопасно завершает частичное обновление. После прерывания
между этими действиями и повторного открытия нет отрицательного api_unfinished и потери
прежних счётчиков/baseline. Для уже сохранённых настоящих api_unfinished после новой версии
не обнулять незавершённые попытки без оснований. Dry-run по-прежнему не меняет БД.
Добавить регрессию с настоящим SQLite/повторным подключением и точкой прерывания между
добавлением колонки и backfill, сохранив обычные resume/dry-run проверки.
