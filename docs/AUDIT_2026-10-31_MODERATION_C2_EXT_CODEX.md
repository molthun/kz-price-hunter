## MM-01 [P1] SAME пары переносит противоречащего третьего участника

Место: `database.resolve_disputed_pair_human`, `database.py:2617–2642`.

Оператор видит два названия, но при SAME функция переносит **всю группу проигравшего ключа**, не проверяя идентичности остальных участников. Здесь отсутствует защита `_merge_conflict`/`identities_conflict`, уже применяемая автоматическим обработчиком.

Реальная временная SQLite: пара `Galaxy S24 128GB black` / `128GB white` действительно одинакова; в группе второго также находится `Galaxy S24 256GB blue`. Ручное SAME возвращает ok=true, titles_updated=3, все три кеша становятся одним ключом. Администратор не подтверждал тождество третьего товара с иной памятью. Вызов API использует тот же сервисный метод, дополнительной проверки там нет.

Критерий исправления: до переноса проверить обе группы целиком, включая поля/названия участников и сохранённые запреты different; при противоречии отказать без изменения каталога либо предложить отдельное явное решение по затронутым товарам. Нельзя молча расширять вердикт двух названий на несовместимый третий товар. Регрессии — участник в каждой группе, объём/ревизия/BOX, сохранённый different, кеш, V2 offers, история и наблюдения.

## MM-02 [P1] Ручное DIFFERENT отменяется пересборкой при сохранённом вердикте

Место: `database.py:2663–2692`; взаимодействие с `product_key.resolve_keys_with_articles` и `scripts/migrate_to_k2.py`.

Ручное разделение присваивает одному названию собственный ключ или суффикс `.diff_<hash>`. Но это решение не становится устойчивым ограничением для построения одинаковых собственных ключей. Запрет different предотвращает объединение по артикулу, а не само совпадение строк ключа, построенных отдельно.

Воспроизведение с **Apple EarPods USB-C / Lightning**, сохранёнными полями brand=Apple, model=EarPods и одним прежним ключом:

1. Ручное DIFFERENT разделяет кеш и реальные предложения, вердикт different сохранён.
2. Настоящий `run_migration(rescore_only=True, batch_size=2)` снова назначает обоим `k2:apple:earpods`.
3. Все offers снова указывают на один product_id, **при этом сохранённый вердикт остаётся different**.

Критерий исправления: сделать решения оператора устойчивыми в нормализации, связывании и rescore/resume; одинаковый автоматически построенный ключ не должен обходить запрет. Проверить появление нового названия/предложения и разные порядки/пачки, кеш и V2. Один успешный вызов ручного разделения этого не доказывает.

## MM-03 [P2] Каталог и вердикт фиксируются разными транзакциями

Место: `database.py:2642–2654`, аналогично `2679–2692`.

`rekey_titles` коммитит перенос раньше `save_pair_verdict` и обновления статуса. Если сохранение вердикта не удалось, API завершается ошибкой, но каталог уже изменён, вердикта нет, пара остаётся pending. Это воспроизведено инъекцией исключения только в `save_pair_verdict`: оба Galaxy S24 уже имеют один ключ после ошибки. Проверка снимка таблиц до/после не проходит.

Критерий исправления: одна транзакция для переноса, вердикта и статуса; обеспечить согласованность при двух модераторах/автоматическом worker и устаревшем состоянии карточки. Ошибки на каждой границе должны оставлять либо полное новое состояние, либо исходное; проверить history/aliases/watches и откат. Реализацию аудитор не менял.

## EXT-01 [P1] Расширенный эталон генерируется с SAME по умолчанию и содержит явные ошибки

Место: `docs/audit_evidence/2026-11-01-c2-ext/build_ext_labeled_sample.py:115–124`, `label_sources.json` и итоговая разметка.

Все 740 представленных меток и объяснений **точно воспроизводятся вызовом `label_pair`**. Для большинства классов используется безусловный SAME, у мониторов/памяти SAME возвращается без проверки полного совпадения моделей/исполнений. Такой генератор не подтверждает, что модель и характеристики товара действительно совпали. `label_sources.json` содержит текстовые объяснения, а не проверяемые ссылки на указанные каталоги. В `unlabeled_sample.json` также фактически присутствует strata, вопреки описанию скрытого слоя.

Независимо подтверждены **шесть явных ошибок SAME** (индексы idx, с нуля; все added):

| idx | Первое название | Второе название | Явное различие |
|---:|---|---|---|
| 108 | Jabra Evolve2 65 Link380a MS Stereo 26599-999-999 | Jabra Evolve2 65 Link380a MS Mono 26599-899-999 | Stereo / Mono |
| 210 | Jabra Evolve2 65 Link380a MS Stereo | Jabra Evolve2 65 Link380a MS Mono | Stereo / Mono |
| 277 | Apple EarPods Lightning Connector | EarPods USB-C | Разъём |
| 358 | EarPods USB-C | Apple EarPods Lightning Connector MWTY3ZM/A | Разъём |
| 595 | Apple EarPods Lightning Connector | Apple EarPods Headphone Plug MWU53ZM/A | Lightning / Headphone Plug |
| 624 | Apple EarPods USB-C | Apple EarPods Headphone Plug MWU53ZM/A | USB-C / Headphone Plug |

Это не спор о цвете. Разные типы подключения и Mono/Stereo уже различаются действующими соглашениями и прежними метками этого проекта. Остальные 734 пары сплошь независимо не сертифицированы; шесть — доказанная нижняя граница ошибок. Разметка, источники и вывод «строго доказано» в таком виде не принимаются. Из этих ошибок не следует автоматически, что k2 хуже baseline или что исправление только шести пар обязательно перевернёт порог.

Критерий исправления: отдельная проверка семантики расширенного набора по исходным названиям, неоднозначные пары — uncertain либо проверяемый источник, журнал исправлений и честное описание способа разметки. Генерацию SAME по отсутствию найденного regex-конфликта нельзя выдавать за независимый эталон качества. Ключи/поля/слои при новой слепой разметке действительно скрыть. Затем пересчитать и передать на приёмку.

## EXT-02 [P2] Второй этап отбора не учтён в весах объединённой выборки

Место: `sampling_script.py:39–70`, `merge_sample.py`, основной `weighted_estimate`.

Новый отбор исключает все 888 старых пар, включая **40 new_merges**, но формула по-прежнему считает known_pairs только **537** и свежие added как простую объединённую выборку **600** с распространением на пул **2054**. Эти 40 пар не входят ни в known-часть, ни в основной random_sample. Среди них по прежним меткам **34 same, 4 different, 2 uncertain**.

Для нового этапа реальный added-пул **1914 = 2280 − 226 known − 100 старых added − 40 new_merges**. Старые 100 были выбраны из 2054, новые 500 — из 1914 с дополнительным исключением специализированных 40. Обычное объединение 100+500 и применение одного интервала для простой выборки из 2054 не учитывает разную схему включения. Получается повторная потеря учёта исключённой части, хотя источник и сама формула не изменились.

Критерий исправления: явно учитывать фазы отбора и все исключённые пары. Например, рассматривать уже наблюдённую часть как отдельную проверенную часть соответствующего слоя, а новую случайную долю распространять только на её действительный остаток; либо обосновать другой корректный многоэтапный оцениватель. Сохранять исходную выборку и не менять метки под порог. После исправления повторить интервалы и сравнение baseline/candidate. Число **0,693** пока подтверждено только как результат текущей формулы на текущих метках, не как доказательство всей популяции.
