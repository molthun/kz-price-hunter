## 2. T01 · P1 · core_done привязан к непостоянному размеру порции

Места кандидата: `database.py:SPOOL_CHUNK_SIZE` (200→100), `spool_apply_chunk` (≈4542),
`spool_history`; `web/server.py:_execute_queue_item` (≈1923–1927);
`release_gate.py:_spool_obligations_check`.

Журнал хранит core_done как **номер завершённой порции**, а не смещение товаров. Размер
порции задачи не записан. Обработчик интерпретирует core_done через текущую константу версии.
Смена 200→100 меняет значение уже сохранённого прогресса; при откате проблема обратная.

### Обновление 6.4.11 → кандидат 6.4.12

1. 300 товаров по 200; на товар №150 настроено any_drop, исходная память цены 200.
2. Принята задача с новой ценой 100. Первая порция из 200 товаров записана реальным
   spool_apply_chunk; core_done=1, история до записи для №150 равна 200.
3. Задача освобождена через nack и заново захвачена текущим воркером 6.4.12.
4. Воркер пропускает лишь первые 100 товаров и повторно пишет товары 100–199 как chunk_no=1.
5. Новая history для перекрывающейся части содержит уже 100, а spool_history объединяет её
   поверх исходной 200. Для №150 нет изменения по history_map, changed_ids его исключает.
6. Получено **0 событий any_drop вместо 1**, history[№150].old_price=100 вместо 200.

Первую порцию создаёт неизменённый протокол spool_apply_chunk с прежним размером 200;
потребление/retry/ACK идут настоящим воркером кандидата. При постоянном размере 200 на чистой
6.4.11 тот же контроль даёт history=200 и одно уведомление.

### Откат кандидата 6.4.12 → настоящая 6.4.11

1. Принята задача на 300 новых товаров. Кандидат сохраняет свою первую порцию 100,
   core_done=1; задача освобождается для повтора.
2. Настоящий `release_gate.rollback_check` на временной БД и прежнем коде возвращает **ok=true**.
3. Отдельный процесс с настоящим кодом 6.4.11 из чистого archive захватывает эту задачу.
4. Прежний воркер считает первую порцию равной 200, пропускает товары 0–199, записывает 200–299
   и возвращает ACK=true.
5. В БД **200 товаров вместо 300**, spool уже пуст: товары 100–199 потеряны как обязательство.

На контрольной чистой 6.4.11 производитель тоже пишет по 200: сохраняются все 300, ACK корректен.
Новая потеря связана со сменой размера, не с использованием смешанного checkout.

Оба направления подтверждены двумя прогонами кандидата; два контрольных сценария на старой
версии PASS. Реальные данные не использовались. Воспроизведение описывает переход с открытой
частично записанной задачей, а не утверждает наличие такой задачи на проде сейчас.

**Рекомендация:** зафиксировать layout/размер порции или абсолютное смещение как часть протокола
каждой задачи. Учесть уже сохранённые задачи 6.4.11 и историю исходных цен. Для отката на прежний
код либо обеспечить совместимую интерпретацию прогресса, либо явно блокировать rollback с

**Критерии:** реальная старая задача после первой порции 200 → новый worker → все товары,

## 3. T02 · P2 · Время исполнения первого write-SQL выдаётся за ожидание блокировки

Места: `database.py:ClosingConnection._run_tracked`, ≈613–636.

Для первого INSERT/UPDATE без явного BEGIN измеряется fn(sql) целиком, затем только после
его завершения выставляется _tx_acquired_at=t1; весь интервал t1−t0 записан в wait.
Тот же принцип применён к первой записи после BEGIN DEFERRED. Но SQL исполняется уже с
write-lock: внутри первого запроса может находиться основной держатель блокировки.

Независимое воспроизведение: INSERT с SQLite-функцией, которая сигнализирует о входе и ждёт
200 мс. Второй настоящий поток после сигнала пытается BEGIN IMMEDIATE на том же файле.
Без предварительного конкурента первое соединение не ждёт чужого write-lock.

Повторный прогон:

- второй писатель реально заблокирован **210.75 мс**;
- статистика первого: **hold=1.28 мс**, **wait=205.13 мс**, total=206.42 мс.

Первый прогон даёт тот же эффект (hold≈0.14 мс). Контроль с явным BEGIN IMMEDIATE правильно
включает тот же 200-мс SQL в hold. Это проверка семантики прибора, не оценка производительности
реального запроса магазина. Замер total сохраняет длительность; разделение hold/wait неверно.

**Рекомендация:** отдельно учитывать ожидание приобретения write-lock и выполнение SQL.
Если SQLite API не позволяет разделить их для неявной транзакции, явно обозначать неизвестное
разделение либо измерять через отдельный BEGIN IMMEDIATE в разрешённых путях. Не выдавать
время всей первой записи за wait и не терять его из hold. Не менять при этом атомарность и
поведение вызывающих функций.

**Критерии:** без чужого писателя медленный первый write даёт удержание, а не ожидание;
при чужом писателе wait учитывается отдельно; проверяются implicit, BEGIN DEFERRED,
BEGIN IMMEDIATE, rollback и неуспешный COMMIT. Имена/числа /api/diag соответствуют семантике.
