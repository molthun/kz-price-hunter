## Как пользоваться

Владелец задаёт приоритет и разрешает этап/задачу. Агент разбивает выбранный этап на небольшие задачи вида `P01-01`, каждая с наблюдаемым результатом, тестами и checkpoint. Смена исполнителя не меняет ID, требования и критерии готовности. Подготовка этого документа сама по себе не запускает реализацию всех этапов.

Сначала P00 → P01 → P02 → P03. Далее P04–P16 в порядке ниже; перестановку фиксировать с причиной и зависимостями. Retention, минимальная проверка миграций, безопасность и возможность отключения новых функций нужны с первого этапа, который вводит соответствующие данные или поведение; поздние P14–P16 расширяют эти механизмы.

Существующие ScanResult, аренды планировщика, волны, outbox, cooldown, FTS, AI, auth/privacy и backup-check переиспользовать после проверки кода. Не переписывать весь проект и все адаптеры одновременно. Числа магазинов, примерные показатели и номера релизов в исходном обсуждении не являются подтверждённым текущим состоянием.

## Этапы, результаты и проверки

### P00. Стабильная база
- Зафиксировать HEAD, версию приложения и схемы, тестовое окружение, результаты Python/frontend suites, размер копии БД, скорость поиска и контрольные предложения/matching. Создать отдельную ветку разработки при начале реализации.
- Сверить код и документацию; проверить предполагаемый нестабильный fallback-ID Arbuz до исправления. Сопоставить известные дефекты с уже внесёнными изменениями.
- Проверки: полный regression suite, scraper contracts, backup_check, открытие/миграция копии БД, контрольные поиски. Сравнение с продом — только по доступным подтверждённым данным; отсутствие доступа указать.
- Приёмка: воспроизводимая базовая точка и список расхождений; никакие непроверенные свойства прода не обозначены как подтверждённые.

### P01. Telemetry Foundation
- Структурированные события: event_id, timestamp, type, severity, component, shop/city/category, scan_id/request_id, message и ограниченный data_json.
- События обхода, HTTP/cooldown, деградации/восстановления, поиска, цен/matching, Telegram, AI, backup и системных ошибок. Один scan_id связывает планировщик, страницы и итог обхода.
- HTTP: число запросов, коды ответа, timeout/connection errors, latency (avg/p95), bytes, Retry-After и cooldown. Агрегаты minute/hour/day; ограниченная диагностическая история и очищенные samples, без секретов и чувствительных URL.
- Проверки: агрегация, очистка данных, retention, корректный p95 (не среднее из p95); fake-источники 200→200→429, 200→403 и timeout. Счётчики совпадают с запросами.
- Приёмка: существующие адаптеры возвращают прежние результаты, цепочка обхода наблюдаема; отказ telemetry не ломает сбор.

### P02. Data Quality & Freshness
- Учитывать received/valid/rejected, полноту категорий, заполненность цены/названия/фото/SKU, complete/limited/failed с причиной и временем.
- Уточнить семантику observed_at, last_seen_at, последнего успешного обхода; Fresh/Aging/Stale/Unknown. FAILED/LIMITED не означают исчезновение старых предложений и не освежают их цену.
- Baseline строить по сопоставимым успешным полным обходам магазина/города/области сбора. При нехватке истории показывать Unknown; деградировавшие результаты не должны обучать норму.
- Проверки: 5000→5100→4900 нормально; 5000→83 и 70% пустых цен — деградация; повтор первой страницы и HTML challenge не дают complete; FAILED сохраняет прежние товары. Переходы freshness проверять управляемым временем.
- Приёмка: искусственная тихая поломка выявляется, старый каталог сохранён, устаревшие цены явно обозначены. Порог baseline зафиксирован в карточке задачи до реализации.

### P03. Monitoring Center V1
- Разделы: обзор, магазины, сканирование, поиск, AI, Telegram, система, события. Краткое состояние и раскрываемая диагностика.
- Карточка магазина: запрос/успешный/полный обход, объём, baseline, freshness, HTTP, latency, категория, полнота, причина и история.
- Event Journal с деталями. Повторяющиеся ошибки группировать в инцидент с началом, последним появлением, масштабом, причиной/гипотезой и восстановлением.
- Проверки: healthy/degraded/offline/limited/empty, отсутствующие данные, длинные названия, 25/50/100 источников; экраны 390 px, tablet, 1366×768, 1920×1080. Проверка доступа admin/user.
- Приёмка: тестовая проблема понятна администратору без чтения сырого лога; нет ложного зелёного состояния при отсутствии наблюдений.

### P04. Полный аудит UI и данных

- Проверки: regression на каждый функциональный дефект, desktop/mobile visual smoke и основные пользовательские сценарии.
- Приёмка: значения совпадают на всех слоях, основные действия доступны на мобильном и desktop.

### P05. Settings UX
- Пользователь: уведомления, наблюдения, город/магазины, AI, профиль, мои данные. Администратор: магазины, сканирование, мониторинг, AI, алгоритмы, система.
- Состояние магазинов перенести в мониторинг, внутренние пороги — в Advanced; «Какие скидки показывать» с понятными режимами и дополнительными числовыми настройками.
- Проверки: загрузка/сохранение каждого параметра, старый settings.json, defaults/reset, ошибочные значения, user/admin permissions и изоляция пользователей.
- Приёмка: прежние настройки сохраняют смысл, обычный пользователь не меняет системные алгоритмы.

### P06. Search Analytics
- Агрегаты normalized_query, city, time bucket, searches, good/weak/zero/error, results_count. FOUND/WEAK/NOT_FOUND/ERROR определяются качеством совпадения, а не числом строк.
- Dashboard успешности и плохих запросов; подготовить сигнал спроса для P10. Не хранить user ID, Telegram ID, IP. Нормализация текста сама по себе не удаляет персональные данные: очистка/исключение чувствительного текста до записи, ограничение срока и детализации.
- Проверки: RTX 5090 с реальными товарами → FOUND; только кабели → WEAK/NOT_FOUND; пусто → NOT_FOUND; ошибка backend → ERROR. Проверить сохранённые поля на отсутствие идентификаторов/чувствительного текста.
- Приёмка: формула Search Success Rate и знаменатель документированы, ошибки не скрыты в «не найдено»; аналитика не строит профили людей.

### P07. Telegram Watch System V2
- Watch PRODUCT/MODEL/SEARCH/CATEGORY/SHOP/DEAL/ARBITRAGE. Условия: целевая цена, процент/сумма снижения, любое снижение, лучшая цена, появление/возврат в наличие.
- Город/магазины/категории, instant/digest, quiet hours с часовым поясом, cooldown, one-shot/repeat. UI на товаре/поиске и «Мои наблюдения». Сообщение объясняет сработавшее условие.
- Переиспользовать outbox и cooldown; определить переход старых подписок без неожиданной массовой рассылки. Наблюдения принадлежат пользователю и включаются в его выгрузку/удаление данных.
- Проверки: 149990→151000→149990, dedupe, 429, blocked bot, quiet hours, digest, restart, конкурирующие workers, права доступа. Отдельно проверить неопределённый результат отправки при сетевом timeout; не обещать exactly-once без оснований.
- Приёмка: один trigger не создаёт повторных заданий доставки, сценарии антиспама проходят, сообщение соответствует настройке владельца наблюдения.

### P08. AI Platform / Router
- Единый AIService/AIRouter Gemini/OpenAI. Типы задач: query/category classification, extraction, matching, attributes, anomaly explanation, source health, admin assistant, user consultant.
- Настраиваемые provider/model/fallback, deterministic first, cache, бюджеты. Разделить пользовательский AI (авторизация, возможность будущей подписки) и внутренний AI проекта.
- Учёт provider/model/task, requests, input/output tokens, estimated cost, latency/errors/cache hits/fallbacks. Цены и доступность тарифов проверять на момент реализации; бесплатность Gemini не предполагать.
- Проверки: mocks, timeout, 429, неверный JSON, исчерпанная квота, разрешённый fallback, оба провайдера недоступны, параллельное расходование бюджета, prompt injection в описании/названии товара.
- Приёмка: без AI работают каталог/сбор/обычный поиск; переход на платный провайдер только в разрешённой политике и бюджете. Mock и реальная интеграционная проверка отмечены отдельно.

### P09. AI для качества каталога
- Детерминированные правила первыми; AI только для неопределённости. Модель, категория, характеристики, quantity/unit/pack_count, дубли, сомнительные скидки.
- Quantity identity: brand/family/variant/quantity/unit/pack_count. Coca-Cola 1 L ≠ 1.5 L, Whiskas 75 g ≠ 85 g.
- Проверки: версионируемый golden dataset совпадений/несовпадений, precision/recall до и после, отдельные опасные false positives по памяти, SIM, фасовке и городу.
- Приёмка: пороги качества согласованы до оценки; рост recall не оправдывает ложные сравнения. Примерные confidence 0.95/0.20 из обсуждения не являются готовой калибровкой. Сначала shadow/canary и возможность отключения.

### P10. Adaptive Scheduler: shadow
- Рассчитывать предложения расписания, не выполняя дополнительных обходов: спрос, возраст, watches, изменения цены, полнота, стоимость, ошибки и cooldown.
- Профили FRIENDLY/NORMAL/EXPENSIVE/DEGRADED на метриках. Не найденные востребованные запросы повышают приоритет подходящих категорий; измерять результат обновления. Интервал 12 h для feed — пример, не жёсткая константа.
- Проверки: несколько полных циклов, starvation, общие лимиты/lease/cooldown, HTTP, freshness, success rate, CPU/time, complete scans, 403/429, пропущенные watches. Shadow не совершает побочные действия.
- Приёмка: воспроизводимое сравнение стратегий на replay/симуляции и отсутствие нарушения ограничений. Shadow оценивает решения, но не доказывает фактическое ускорение реальных обходов; эффект подтверждается P11.

### P11. Adaptive Scheduler: контролируемое включение
- После P10: один friendly источник → 3–5 → остальные разрешённые источники. Feature flag по умолчанию выключен, переключение возвращает старую стратегию.
- Проверки: переключение в обе стороны, restart, потеря lease, отсутствие двойных обходов, соблюдение cooldown и лимитов, метрики до/после.
- Приёмка: измеримые пороги остановки/отката определены до canary; каждый шаг расширения подтверждён. AI не меняет произвольно endpoint, защиту или агрессивность запросов.

### P12. AI Admin Assistant
- Только admin, read-only инструменты system/shop health, incidents, search analytics, scans, AI usage, scheduler stats, price quality. Структурированные ограниченные данные вместо всей БД/сырых логов.
- Проверки: синтетическое падение каталога DNS на 95% и рост 403 на 40%; правильные цифры и ссылки на период/источник; отсутствие данных, injection, права доступа, отсутствие команд записи.
- Приёмка: выводы проверяемы, гипотезы отделены от фактов; недостаток данных не превращается в выдуманную причину.

### P13. Daily Intelligence
- За 24 часа: поиски/успех, новые товары, изменения цен/скидки, Telegram, AI cost, здоровье/восстановление магазинов; AI summary рядом с исходными цифрами.
- Проверки: границы периода/часовой пояс, повторный расчёт без дублей, пустые/неполные сутки, сверка агрегатов, недоступный AI.
- Приёмка: цифры воспроизводимы без AI, summary не выдумывает события. Отправка admin digest в Telegram — отдельное последующее включение.

### P14. System & Environment
- Фактические version/Git SHA/schema, Python/SQLite/Playwright/Chromium/curl_cffi, uptime, DB size, counts; heartbeat scheduler/Telegram/scrapers/AI/backup.
- Проверки: устаревший/отсутствующий heartbeat, умерший worker при живом HTTP, restart, отключённый компонент, скрытие чувствительной конфигурации.
- Приёмка: страница показывает фактическое окружение, мёртвый scheduler не зелёный; намеренно отключённый компонент различается с отказавшим.

### P15. Backup, Retention, Self-Monitoring
- Раздельная политика diagnostics/events/hourly/daily/price history. Ориентиры исходника: 7 дней diagnostics, 30–90 events, 90 hourly; сроки выбрать по объёму, не удалять старые данные без принятой политики.
- Backup: создание, integrity_check, открытие, чтение схемы и периодическое восстановление во временную БД. Метрики возраста/размера/результата. Проверка самого мониторинга.
- Проверки: повреждённый/просроченный backup, заполненный диск, сбой очистки, восстановление, зависший worker. Внешняя проверка нужна для обнаружения полной остановки процесса, внутренний heartbeat её не заменяет.
- Приёмка: восстановление реально выполнено на временных данных, мониторинг/retention имеют ограниченное потребление ресурсов.

### P16. CI/CD Gate
- Compile → unit → migrations → scraper contracts → golden matching → notifications → AI mocks → frontend → security → dependency/secret scan → image build → image smoke. Вводить необходимые проверки в предыдущих этапах, здесь завершить общую цепочку.
- Upgrade: БД предыдущего релиза → новый образ/миграция → smoke → integrity. Rollback со старым образом только при совместимой схеме; иначе восстановление согласованного backup с явным описанием потери новых данных.
- Проверки: реальный pipeline, намеренная ошибка блокирует публикацию, контейнерный smoke, upgrade/restore rehearsal.
- Приёмка: непрошедшие обязательные проверки не публикуют образ; владелец имеет проверенную процедуру выката и восстановления.

### P17. Своя машина, локальные модели и Vision

Утверждён владельцем 29.10.2026. Причина: на NAS мало ресурсов (503 «db unready» и блокировки записи 6.5.0), а у машины стенда
RTX 4070 12 ГБ, 16 потоков, 61 ГБ ОЗУ, NVMe 915 ГБ, Ubuntu 26.04 и уже установленный NVIDIA Container Toolkit (CDI `nvidia.com/gpu`).
Платные провайдеры не убираются: локальная модель — дополнительный провайдер и запасной путь в обе стороны.
Шаги по порядку; P17-E по решению владельца можно поднять сразу после P17-A — от моделей переезд не зависит.

- **P17-0. Выпуск 6.5.1** (блокировки записи) после аудита Codex — до любых шагов этапа.
- **P17-A. Провайдер «Локальная модель».** Третий провайдер рядом с gemini/openai: OpenAI-совместимый адрес (`/v1`), имя модели,
  ключ необязателен (сейчас `providers_for` требует ключ). Выбор провайдера и модели на задачу: массовые задачи обхода
  (канонические ключи, классификация, нормализация) — локально по умолчанию, пользовательский консультант — по выбору владельца.
  Запасной путь: локальная недоступна или не уложилась во время → платная в рамках бюджета; и обратно. Учёт: вызовы локальной —
  стоимость 0, но с задержкой, ошибками и долей запасного пути.
  Проверки: моки недоступного/медленного/неверного JSON локального провайдера, переход на платный и обратно, бюджет, prompt injection,
  отсутствие ключа. Приёмка: без локальной модели всё работает как сейчас; переключение задачи — настройкой, без перевыпуска.
- **P17-B. Локальная модель в проекте.** Профиль compose `local-ai` с сервисом Ollama (GPU через CDI, модели на томе).
  Приложение не запускает контейнеры само (сокет Docker — почти root): оно обнаруживает сервис, показывает в админке GPU и
  свободную видеопамять (`/api/ps`), рекомендуемую под 12 ГБ модель и даёт скачать её (`/api/pull`). Один сервис на прод и стенд;
  у стенда ограничено число одновременных запросов, чтобы он не отнимал GPU у прода.
  Проверки: машина без GPU, сервис выключен, нехватка видеопамяти, долгое скачивание, рестарт. Приёмка: включение локальной модели
  на машине с GPU — одна команда профиля и кнопка в админке.
- **P17-C. Стандарт ключа товара и постепенный перевод всех задач на локальную модель** (решение владельца 29.10.2026:
  «постепенно всё отдавать локальной; не справляется — искать другую модель»; «ключ стандартизовать — сегодня одна модель,
  завтра другая»; «главное, чтоб работало»).
  - **Проблема.** Канонический ключ (`бренд:модель:вариант`) решает, какие товары разных магазинов — один товар (сравнение цен).
    Правила в коде (`extract_canonical_key`) дают его детерминированно. Названия, которые правила не разобрали, нормализует AI,
    и модель пишет строку ключа сама — у каждой модели свой формат (`32.5`/`32.5mm`, `null`/`0`, транслит бренда). Замер
    на стенде: ключи qwen3-vl совпали с ключами Gemini у 17 из 60 названий. Смена модели меняет ключи — сравнение теряет пары.
  - **C1. Стандарт ключа.** Модель возвращает не строку, а поля по фиксированной JSON-схеме: бренд, модель/серия, артикул
    производителя, варианты (число + единица), признак «без бренда». Ключ собирает код (`product_key.py`) по правилам:
    - бренд — по справочнику синонимов (`BRAND_MAP`, расширяется);
    - модель и артикул — нижний регистр, без пробелов и дефисов, без цветов и маркетинга;
    - единицы — по таблице (`ГБ/Gb → gb`, `мм → mm`, `л → l`, `дюйм/" → in`), десятичная точка;
    - пустое — пусто (никаких `0`/`null`);
    - без бренда и без артикула ключа нет: товар не сравнивается автоматически.

    Версия правил хранится с ключом (`k2:` в начале), поля — рядом (`title_fields`), чтобы пересобрать ключи без повторных
    вызовов модели. Детерминированные правила по-прежнему идут первыми; стандарт касается пути через AI.
  - **C2. Набор для оценки.** Несколько сотен названий из базы, где один товар есть в 2–3 магазинах. Метрики — не совпадение
    с Gemini, а то, что важно для сравнения цен: названия одного товара получили один ключ (полнота) и разные товары не склеены
    (точность), плюс доля неверного JSON и время. Пороги до замера: склеек не больше, чем у Gemini; полнота не ниже 95 %
    от Gemini.
    Ход работы (29.10.2026): по групповому эталону Gemini Gemini получает 1,0 по определению, а его собственные
    ошибки засчитываются кандидату. Поэтому порог 95 % сравнивается по набору пар, проверенному вручную, или между
    кандидатами на одном наборе. Замеры — `docs/AI_LOCAL_POLICY.md`.
  - **C3. Выбор модели.** Сначала `qwen3-vl:8b-instruct` с подсказкой под схему полей. Не дотягивает — кандидаты в пределах
    12 ГБ видеопамяти (`gemma3:12b`, `qwen3:14b` без рассуждений и т. п.). Результаты — таблица в свидетельствах.
    Итог 29.10.2026: `qwen3-vl:8b-instruct` 0,809, `gemma3:12b` 0,803, `qwen3:14b` 0,781 (полнота, одинаковые правила).
    Остаётся qwen. Дополнительно к C4 — сопоставление по артикулу производителя (`sku`) поверх ключа.
  - **C4. Переход базы.** Около 19,7 тыс. ключей старого формата из кэша AI пересобираются в стандарте: поля извлекает
    выбранная модель ночью, ключи собирает код. Перед этим на стенде — проверка, что сравнение цен не теряет пары.
  - **C5. Теневой режим на проде.** Нормализация по-прежнему на Gemini (стандарт полей), локальная параллельно извлекает поля;
    сравнение пишется в учёт. Порог держится несколько дней — включается `local_normalize_enabled`.
  - **C6. Остальные задачи** уже на локальной; раз в неделю — разбор учёта: задача, которая часто уходит на платную,
    разбирается отдельно (подсказка или другая модель).
- **P17-D. Vision по изображениям (закрывает остаток S2-E10).** Картинка → уменьшение → модель с поддержкой изображений (локальная,
  запасная — Gemini) → строгий JSON (товар, цена, старая цена, валюта, уверенность). Публикацию по-прежнему решают правила
  `domain/vision_extraction.py`: порог 0,75, «Цена не определена» при частично закрытой цене, фильтр чужих валют.
  Проверки: постер, прайс-лист 5+ позиций, зачёркнутая цена, RUB/USD, «за кг», размеры рядом с ценой, нечитаемое фото, injection
  в тексте картинки. Приёмка: изображение без OCR даёт кандидатов; сомнительная цена не публикуется.
- **P17-E. Перенос прода на машину стенда.** Два отдельных compose-проекта: прод (данные, порт, лимиты свои) и стенд (как сейчас,
  4 CPU / 15 ГБ). Выпуск не меняется: стенд собирается из checkout, прод берёт образ из GHCR через Watchtower после push в main.
  NAS: вход в интернет (прокси DSM → новая машина в LAN, правка `TRUSTED_PROXIES`), бэкапы базы и холодный резерв с последней
  копией. Перенос базы — согласованной копией (`sqlite3 .backup`), не копированием файла на ходу.
  Агент готовит compose прода, инструкцию переезда и отката и скрипт переноса; операции на NAS и проде выполняет владелец.
  До переезда владелец подтверждает: машина работает 24/7 (желательно ИБП), стабильная сеть, вход остаётся через NAS.
  Проверки: репетиция переезда на копии, откат на NAS, бэкап с новой машины на NAS и его восстановление, health и обход после
  переключения. Приёмка: прод работает на новой машине, NAS-резерв поднимается по инструкции.
  Состояние 29.10.2026: подготовлено и отрепетировано Claude — `deploy/prod-host/`, `docs/PROD_MOVE_P17E.md`;
  ждёт аудита Codex и переезда владельцем.

## Релизы и общая готовность

Предварительные группы исходного плана: foundation → telemetry → quality → monitoring → UI/settings → analytics → watches → router → catalog AI → scheduler shadow → rollout → admin AI/daily → system hardening. Номера 5.7.1–6.6 из обсуждения ориентировочные: сначала сверить текущие version.py, коммиты и теги, не занимать уже выпущенную версию.

На каждый этап: критерии → реализация → уместные unit/integration/regression проверки → frontend для UI → миграция на копии при изменении схемы → Docker smoke перед выпуском → аудит → разрешённый canary/выкат → проверка результата. Неприменимые проверки отмечать N/A с причиной, непроведённые — явно.

Приёмка кода и внедрение на проде — отдельные состояния. Аудитор по возможности отличается от автора; если Codex сам реализовал задачу после передачи, записать необходимость независимого review Claude/Antigravity, не называть самопроверку независимым аудитом.
