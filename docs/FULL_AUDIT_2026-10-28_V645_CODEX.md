## 2. G01 · P1 · Снятие товара не синхронизируется с V2-предложением

Места: `database.py:_reconcile_source_conn`, `spool_finish_core`; чтение —
`repositories/search_repo.py`, `database.py:watched_offers`, `domain/purchasability.py`.

Полный подтверждённый обход снимает отсутствующий товар через products.is_active=0.
Соответствующая строка offers остаётся is_active=1, availability=in_stock. Поиск и watches
работают по offers и не учитывают снятие legacy-товара. Свежая дата прежнего наблюдения
ещё позволяет показывать покупаемую цену, которой магазин больше не подтверждает.

Воспроизведение проходит **настоящий enqueue → claim → _execute_queue_item →
spool_finish_core/reconcile → ACK**, без подмены сохранения или поиска:

1. Полный обход одного источника сохраняет товары remaining и retired.
2. Следующий полный обход того же источника содержит только remaining.
3. Для retired: products.is_active=0, но offers.is_active=1 и availability=in_stock.
4. SearchCore возвращает retired с has_purchasable_offers=true, min_price=100.
5. watched_offers возвращает is_available=1; настоящее target_price наблюдение создаёт
   notification_events=1. Реальная отправка Telegram не выполнялась.

Результат подтверждён на macOS и в Linux-образе стенда с ограниченными ресурсами.
Необходимые доказательства — results.json и linux-reproduction.txt.

**Рекомендация:** согласованно переносить снятие и возврат между products/product_sources
и offers. Учитывать несколько источников одного предложения: отсутствие в одной категории
не снимает предложение, которое подтверждено другим активным источником. Не распространять
legacy-снятие на независимые социальные/ручные каналы того же канонического товара.

**Критерии приёмки:** сохранение → полный обход без товара → DB/API/витрина/watches
не считают его покупаемым; повторное появление снова делает доступным и корректно вызывает
back_in_stock. Дополнительно: другой активный источник, limited/failed scan, старый retry
после нового полного обхода, независимый канал продавца. Нужна регрессия по рабочему пути,
а не только проверка helper или наличия SQL UPDATE.

## 3. Повторная оценка F01–F04

| Замечание | Проверка и результат |
|---|---|
| F01: старый retry откатывает цену | Прежнее независимое воспроизведение: expected_latest=200, actual=200. Новый observed_seq блокирует устаревшую запись; source_observed защищает более новую сверку; derived фильтрует superseded. Регрессии включают старые core/derived задачи |
| F02: пустое observed_at | Прежний сценарий теперь limit1=p1/100, limit50 первым p1/100. SQL использует fallback updated_at; новые tests сверяют SQL/Python |
| F03: экспорт 1000 событий | При сохранённых 1001 экспорт содержит 1001. Отдельный keyset iterator не меняет UI limit |
| F04: откат с принятыми задачами | Реальный rollback_check с открытым spool на код 6.4.1 теперь ok=false с объяснением; процедура задокументирована |

Принятие этих сценариев не означает, что экспорт стал потоковым по HTTP: events всё ещё
собираются в список, как и итоговый JSON. Для очень больших пользовательских историй стоит
рассмотреть потоковую выгрузку/асинхронное формирование файла; не объявляется новым
блокирующим дефектом без согласованных пределов объёма.

Проверка rollback для поддерживающего spool кода использует признак протокола в исходниках;
это барьер для старых версий, не доказательство совместимости любых будущих протоколов.
При развитии журнала нужны явная версия протокола и rehearsal с реальным выполнением задач.

## 4. Архитектура, данные, сбор и эксплуатация

Архитектура очереди с durable admission, атомарными бюджетами, claim token и стадиями core/
derived сохранена. Новые observed_seq/source_observed закрывают доказанный порядок retry
для цен/сверки; G01 показывает оставшуюся границу dual-write между снятием legacy и V2.
Нормальную обработку, отказ admission, конкуренцию claims, аварийные завершения процессов,
повтор derived и барьеры завершения проверяет полный штатный набор.

Сбор магазинов проверен контрактными/надёжностными тестами; не выполнялся новый живой
обход всех магазинов. HTTP limiter/cooldown/TLS не изменены данным релизом. Наличие
контрактных тестов не доказывает актуальность HTML/API каждого внешнего сайта.

Поиск, витрина и watches используют общую purchasability policy; исправления TTL, свежести,
состояния канала/продавца подтверждаются regression. Однако сама policy не может исправить
неверный is_active, который приходит из несинхронизированного хранилища — это G01.

Backup остаётся на согласованном SQLite backup API; миграция observed_seq/source_observed
аддитивна. В тестах проверяются init/migration/backup/restore. Реальное аварийное восстановление
NAS, свободное место, файловые права и совпадение всего набора продовых данных со стендом
не проверены. Внутренняя schema_version всё ещё 5, поэтому сама цифра не доказывает
совместимость старой логики с новым журналом.

Стенд: CPU NanoCpus=4000000000, Memory=16106127360; runtime в снимке: пул 16,
RSS 259.6 МБ, event-loop lag 0.4 мс, queue=0, failures=0, Redis/worker активны, problems=[].
Это read-only снимок, не долговременный SLA. На проде публичный health в этом аудите
показывает Redis active; прежнее сообщение об inactive больше не описывает текущий снимок.

### Короткий нагрузочный smoke

Отдельный Linux-контейнер 4 CPU/15 ГБ, без рабочих данных/сети: 8 пачек по 500
синтетических товаров, настоящий worker/SQLite и HTTP live/stats, 8 секунд опроса.
Арбитраж детерминированно отключён в тесте; AI/Telegram/магазины не вызывались.
До замера заданы ориентиры: live p95<250 мс, stats p95<2 с.

- Сохранены все 4000 товаров, drain=true, HTTP ошибок нет.
- live: 78 запросов, p95=0.5 мс, max=1.0 мс.
- stats: 78 запросов, p95=5.3 мс, max=16.2 мс.

Это положительная проверка короткой очереди/API под синтетической записью. Она **не заменяет**
полную волну на производственном объёме, дисковую конкуренцию NAS, p99 при настоящих сетевых
таймаутах и наблюдение памяти после нескольких волн. Часть stats-запросов обслуживается кэшем:
результат относится к обычному API-пути, не к каждой холодной SQL-выборке.

## 5. Безопасность, интерфейс, AI и выпуск

На текущем срезе заново прошли auth/privacy/security и браузерные регрессии: Telegram auth,
Origin/CSRF, trusted proxies, local dev-login, роли, XSS/ссылки, формы, seller modal, история
версий. Новые правки не расширяют доступ к административным операциям. Это не внешний
pentest DSM/маршрутизатора. Полная ручная визуальная приёмка всех экранов и размеров не проведена.

Secrets gate: findings=[]. Свежий pip-audit по requirements + pinned constraints: известных
Python-уязвимостей не найдено. Пакеты ОС/Redis/Chromium и supply chain отдельным сканером
в этом аудите не проверены. Значения credential не читались в отчёт/свидетельства.

AI/router/budget/fallback проверены штатными mocks и разбором неизменённой политики;
настоящие провайдеры, стоимость, качество модели и matching не подтверждались. Outbox и
уведомления проверены до постановки задания, без внешней отправки.

Выпуск: remote всё ещё 6.4.1-срез; текущий локальный код не опубликован. Не считать старую
зелёную CI проверкой текущего HEAD. Нужны новая CI, image smoke и фиксация конкретного
публикуемого образа. Разделение image-smoke и повторной сборки publish по-прежнему требует
контроля digest. Docker-права/production compose и Watchtower не менялись.
