# Полный аудит KZ Price Hunter 6.4.4

Дата: 28.10.2026, Asia/Almaty. Исполнитель: Codex. Основание: прямое поручение владельца
провести полный аудит проекта, а не только повторную приёмку прежних C/R-замечаний.

## Решение

**Выпуск всего среза как полностью стабилизированного не принимать.** Подтверждены четыре
замечания: F01 — P1, F02/F03/F04 — P2. Это новые сквозные сценарии, а не автоматическое
продление старого отказа по 6.4.2. Исправления 6.4.3 существенно улучшают архитектуру очереди.
Изменения приложения, исправления замечаний, выпуск и production-операции аудит не выполнял.

## 3. Подтверждённые замечания

### F01 · P1 · Повтор старого отказа перезаписывает более свежую цену

Места: database.py `spool_claim`, `spool_apply_chunk`, `spool_resolve_failures`.

Порядок выдачи блокирует новую задачу только при старой pending/processing. После dead_letter
новая задача того же магазина может успешно записаться. Администратор имеет штатное действие
retry для старого отказа. Оно снова делает старую задачу pending, а запись товаров не проверяет,
не были ли после её приёма уже записаны более свежие результаты.

Воспроизведение на macOS и Linux: приняты old=100 и new=200 одного товара; old уходит в
отказ до core; new сохраняется и подтверждается; штатный retry old и настоящий
spool_apply_chunk возвращают current_price с **200 на 100**. Это потеря актуальности данных,
потенциальные ложные скидки/уведомления и противоречие обещанному порядку результатов.

Рекомендация: версия наблюдения/монотонный порядок записи на предложение либо явное
переизвлечение данных при retry устаревшего задания. Определить отдельно политику повторения
derived после уже завершившихся более новых задач. Не запрещать полезный retry без замены
механизма восстановления.
Критерий: old failed → new committed → old retried не ухудшает текущую цену/наличие/дату
наблюдения, не снимает новые товары и не создаёт уведомление по устаревшему переходу.

### F02 · P2 · SQL и Python расходятся на пустом времени наблюдения

Место: domain/purchasability.py `sql_purchasable_conditions` против `offer_purchasable`.

Python берёт observed_at **или updated_at**. SQL при julianday(observed_at)=NULL считает
свежесть неизвестной и пропускает предложение, updated_at не рассматривается. observed_at
NOT NULL запрещает NULL, но не пустую строку — такая строка разрешена схемой и сохранённой
моделью. Это допустимый случай отсутствующего значения, не нарушение ограничения таблицы.

Воспроизведение: дешёвый p0=1, observed_at='', updated_at=2020; свежий p1=100.
limit=1 даёт p0/min_price=null, limit=50 первым даёт p1/min_price=100. Python правильно
помечает p0 stale уже после отбора, но SQL потерял доступного кандидата перед LIMIT.

Рекомендация: одинаковая нормализация отсутствующих времён и fallback updated_at в SQL;
проверить пустые/нечитаемые timestamps и timezone offsets через сохранённые данные.
Критерий: первая доступная цена не зависит от limit=1/50 для этого сценария, политики
поиска, витрины и watches дают одинаковую purchasability.

### F03 · P2 · Выгрузка пользователя молча обрезает историю срабатываний

Места: database.py `export_user_data` и `watch_events`.

Выгрузка, описанная как «всё, что сервис хранит», вызывает watch_events(limit=1000).
UI-ограничение списка применяется к переносимой пользовательской выгрузке без признака
усечения и без пагинации. У пользователя может быть больше событий, чем помещается в экспорт.

Воспроизведение на временных данных: сохранено 1001 событие, export содержит 1000.
Это продуктовый дефект полноты данных; правовая оценка обязанности экспорта не делалась.
Рекомендация: отдельная полная/потоковая выборка для export, оставив UI ограниченным.
Критерий: 1001 и существенно больше событий выгружаются полностью с ограниченным расходом
памяти, изоляцией владельца и без токенов сессий/секретов. Удаление аккаунта проверено кодом:
оно транзакционно удаляет sessions, outbox, watches, watch_state/events и пользователя.

### F04 · P2 · Успешная репетиция отката не проверяет принятые задания новой очереди

Места: release_gate.py `rollback_check`, `database.py` spool и документация rollback.

Схема всё ещё версии 5, но приложение 6.4.1 не обслуживает новую SQLite-очередь.
На временной базе нового кода создан pending task со ещё не сохранённым товаром; настоящий
rollback gate с кодом `70427f55` вернул ok=true и шесть успешных проверок. Ни одна из них
не подтверждает обработку этого task или завершение всех принятых обязательств перед откатом.
Сам gate запускает smoke-запросы, а не предыдущий фоновый worker до полного drain.

Это не утверждение о разрушении таблицы: payload может остаться и обработаться после возврата
на новый код. Проблема — сервис после отката может оставить принятые данные необслуживаемыми,
а результат gate не различает это состояние и безопасный откат.
Рекомендация: явный запрет downgrade при активном новом spool либо совместимая процедура
переноса/drain с доказательством результата. Критерий: rehearsal с pending/processing/derived/
dead-letter заданиями выдаёт корректное решение и не оставляет принятые данные без исполнителя.

## 4. Архитектура и прежние замечания

В 6.4.3 принятие задачи и проверка аренды перенесены в одну транзакцию; квоты также
проверяются атомарно. Недолговечного fallback больше нет. ACK/NACK выполняются вне event loop.
Claim имеет owner/token/expiry, перехват не сбрасывает живые claims безусловно. Core пишется
порциями по 200 вместе с исходной историей цен; сверка источника/scan log и переход к derived
транзакционны. Барьер ждёт ID своего обхода и не считает ошибку чтения успехом.

Новая модель различает аренду **поставщика результатов** и claim **исполнителя принятой задачи**.
Поэтому позднее завершение принятой задачи после потери сканером аренды само по себе больше
не дефект. Старое воспроизведение по lost/generation нельзя применять к новой модели без
пересмотра ожидаемого результата. Тесты с SIGKILL и потерей claim теперь входят в tests/.

Общая purchasability policy устраняет большинство прежних расхождений, включая stale,
нулевую цену, expired/out_of_stock и выключенные источник/продавца; остаётся F02.
Auth имеет отдельный session executor и bypass всех трёх probe-маршрутов.
Диагностика теперь видит failures, readiness различает degraded и unavailable.

Ограничение: derived-эффекты всё ещё состоят из нескольких операций, идемпотентность
опирается на прикладные dedupe/state, а не на один транзакционный event/outbox receipt.
Сводка телеметрии может повториться, что автор открыто указал. Межпроцессный takeover
именно во время derived и reorder после ручного retry требуют дополнительной приёмки;
F01 уже показывает наблюдаемый дефект восстановления.

Крупные модули: server около 3615 строк, database 4170, HTML 7006. Это риск сопровождения
и проверки глобального состояния, не самостоятельный блокирующий дефект. Разделять по
контрактам после устранения потерь данных, а не совмещать аварийную стабилизацию с переписыванием.

## 5. Безопасность, зависимости, резервирование и выпуск

Auth проверяет Telegram подпись/возраст, роли и Origin; proxy headers доверяются
настроенным адресам. Dev-login ограничен локальной границей. Догрузка описаний проверяет
домен/IP/редиректы и размер ответа; TLS не отключается. Регрессионные XSS/auth/privacy/
security suites и новая история версий прошли. Это не внешний pentest инфраструктуры DSM.

Secrets gate findings=0. Для прежнего диагностического credential отдельно подтверждены
удаление из достижимой истории и смена активного значения. Новые секреты не выводились.
Свежий pip-audit по requirements + constraints: No known vulnerabilities found. Это проверка
Python advisory, не аудит пакетов ОС/Redis/Chromium и не гарантия отсутствия неизвестных CVE.

Backup использует SQLite backup API и quick_check, проверка восстановления читает схему и
smoke-запросы; retention/restore покрыты regression. Реальный disaster recovery всего NAS,
место на диске, полномочия Docker и внешний firewall заново не проверялись.

CI отделяет Python/frontend/secrets/deps/upgrade/image smoke от публикации. Локальный HEAD
ещё не remote main; успешные старые Actions не удостоверяют новый срез. Публикуемый образ
пересобирается отдельным job, тождество проверенного и опубликованного digest не доказано.
Docker запускает приложение без отдельного USER; это эксплуатационное усиление, не найденный
эксплойт. Перед выпуском нужны новая CI и проверка конкретного образа, а также решение F04.

AI/router: проверены существующие бюджеты, атомарное резервирование счётчика, fallback,
провайдерные таймауты и отсутствие требования AI для обычного каталога. Настоящие ключи,
платные вызовы, точность matching и SLA модели не проверялись. Наличие mocks не означает
готовность реального интеграционного контура.

## 6. Эксплуатационная приёмка

Стенд 6.4.4 в снимке: uptime около 7455 с, RSS 686 МБ, lag 0.2 мс, очередь/отказы=0,
Redis активен, worker running. Это существенно полезнее прежнего снимка сразу после старта,
но NVMe/свободный CPU хоста не воспроизводят дисковую конкуренцию NAS. Сопоставимость
истории/размера производственной БД не доказана. Полный длительный replay/сканирование,
p95/p99 коротких API на фоне волны и устойчивое возвращение памяти после нескольких волн
владелец не должен считать подтверждёнными одним здоровым снимком.

Прод на 6.4.1 по-прежнему показывает redis_active=false. Причина отключения и точная
историческая причина зависания без diag/журнала хоста остаются неустановленными.
Не следует выдавать новые локальные исправления за уже внедрённые на прод.

## 7. Проверки и передача

Основные команды: Python unittest discover с отдельным DATA_DIR и пустыми ключами сервисов;
все test_frontend*.cjs через Deno/Playwright; release_gate secrets; pip-audit requirements+
constraints; независимый reproduce.py на macOS и в одноразовом Linux-контейнере под лимитами.

Свидетельства: `docs/audit_evidence/2026-10-28-full644/`.
Итог: macOS 1827 tests OK (89.763 с), frontend 19/19 PASS; Linux на точном HEAD
1827 tests OK (162.153 с). Исходный образ до наложения текущего HEAD дал один FAIL
в уже исправленном локально test_capped_on_large_hosts (1827 tests, 162.148 с). Это
расхождение версии тестовой обвязки образа и checkout, не подтверждённый runtime-дефект.
Полная сводка прогонов хранится в verification.json.
Репродукторы создают только временные БД; выход 0 означает завершение диагностического
скрипта, оценка найденных дефектов — по results.json. Наличие исходных дефектов не исправлялось.

Порядок дальнейшей работы: F01 → F02/F03 → процедура F04 → нагрузочная и релизная приёмка.
Для каждого исправления нужна штатная регрессия через реальный путь данных, затем
независимая проверка. Выпуск и изменения прода остаются отдельным решением владельца.
