## Зачем

На NAS (i3-7100T, 16 ГБ) том стоит на одном SATA-HDD. Во время обхода диск занят почти всё
время, проверки готовности не успевают, и health отдаёт 503 (6.5.2: 22 из 30 ok).
Машина стенда: 16 потоков, 61 ГБ, NVMe 915 ГБ, Ubuntu 26.04, Docker 29.

## Как устроено

```text
интернет → shop.molthun.ru → DSM на NAS (обратный прокси, сертификат)
                                   │  по локальной сети
                                   ▼
           машина стенда 192.168.28.25
             ~/kzph-prod   — прод: kz-price-hunter, порт 35540, Watchtower (образ из GHCR), без лимитов
             ~/kzph-stand  — стенд: порт 35539, 4 CPU / 15 ГБ, сборка из checkout (как сейчас)
             /srv/storage/kzph-backups — ночные копии базы и конфигурации (отдельный HDD)
NAS: вход из интернета (обратный прокси DSM, сертификат), архив прежнего контейнера у владельца
```

Выпуск не меняется: push в main → CI собирает образ → Watchtower на новой машине за 5 минут
подтягивает его в `kz-price-hunter`. Стенд Watchtower не трогает.

## Подготовка (история: шаблон kzph-prod, не применять)

1. **Машина.** Работает круглосуточно, желательно через ИБП. Docker запускается при загрузке
   (проверено: `enabled`); GNOME при питании от сети не засыпает (`nothing`). Чтобы её не усыпил
   никто и ничто:
   ```bash
   sudo systemctl mask sleep.target suspend.target hibernate.target hybrid-sleep.target
   ```
2. **Папка прода.** Файлы из `deploy/prod-host/` (после push они есть в `~/kzph-stand`):
   ```bash
   mkdir -p ~/kzph-prod && cp ~/kzph-stand/deploy/prod-host/* ~/kzph-prod/ && cd ~/kzph-prod
   ```
3. **Окружение.**
   ```bash
   cp prod.env.example .env && chmod 600 .env
   ```
   Заполните теми же значениями, что на NAS. На NAS они лежат в двух местах:
   - `/volume1/docker/kz-price-hunter/.env`;
   - прямо в `compose.yaml`: `TELEGRAM_BOT_TOKEN` и `DIAG_TOKEN`.

   **`TRUSTED_PROXIES=192.168.28.10/32`** — новое значение, прежнее `172.26.0.1/16` здесь неверно.
4. **Проверка без изменений:**
   ```bash
   ./move_from_nas.sh --check
   ```
   Проверяет `.env` (значения не печатает), SSH до NAS, размер базы и свободное место, скачивает образ.
5. **Ключ для ночных копий.** Нужен, чтобы `backup_to_nas.sh` работал из cron без пароля:
   ```bash
   ssh-keygen -t ed25519 -N '' -f ~/.ssh/id_ed25519   # если ключа ещё нет
   ssh-copy-id molthun@192.168.28.10
   ```
   На NAS создайте папку `/volume1/Backup/kzph-prod`. Другая цель задаётся в `~/kzph-prod/backup.conf`
   строкой `BACKUP_TARGET=...`. Можно указать и локальный каталог, например папку Synology Drive.

## Переезд (история: шаблон kzph-prod, не применять)

1. На машине стенда:
   ```bash
   cd ~/kzph-prod && ./move_from_nas.sh
   ```
   Скрипт один раз спросит пароль sudo на NAS и дальше:
   1. На NAS: останавливает Watchtower и прод и ставит им `restart=no`, чтобы прод не поднялся после перезагрузки NAS.
   2. Упаковывает `data` на NAS и проверяет, что прод там больше не отвечает.
   3. Переносит архив сюда и проверяет копию (`quick_check` и число товаров).
   4. Запускает прод и ждёт health ok.

   Если `data/prices.db` здесь уже есть, скрипт не перезапишет его.
2. **DSM** → Панель управления → Портал входа → Дополнительно → Обратный прокси → `shop.molthun.ru`:
   назначение `http://192.168.28.25:35540`. Было `localhost:35539`, остальные настройки правила не менять.
3. Проверка:
   ```bash
   ./verify_public.sh
   ```
   Она сверяет:
   - версию здесь и снаружи;
   - health снаружи — 10 замеров, нужно не меньше 9 ok;
   - время поиска;
   - соседей порта внутри контейнера: должен быть 192.168.28.10;
   - Watchtower: запущен и без ошибки API.
4. Вручную: войдите на сайт через Telegram и отправьте боту `/start`.
5. Ночные копии — строка в `crontab -e`:
   ```text
   30 4 * * * /home/molthun/kzph-prod/backup_to_nas.sh >> /home/molthun/kzph-prod/backup.log 2>&1
   ```
   После первой ночи проверьте `backup.log` и пульс «резервные копии» в мониторинге.
6. Прежние данные NAS (`/volume1/docker/kz-price-hunter/data`) оставьте хотя бы на 2 недели как резерв.
   Архив `move-*.tar` на NAS можно удалить после успешной проверки.

## Как сделано на деле (29.10.2026)

Владелец перенёс в `~/kzph-prod` свой compose и `.env` с NAS, а не `docker-compose.prod.yml`. Поэтому контейнеры
называются по-прежнему: `kz-price-hunter` и `kz-price-watchtower`. Claude правил в них:
- порт `35540`;
- `TRUSTED_PROXIES=192.168.28.10/32`;
- новый `DIAG_TOKEN` — только в `.env`;
- `DOCKER_API_VERSION=1.44` у Watchtower.

Контейнер на NAS владелец заархивировал и удалил. Откатиться можно только восстановлением из этого архива,
`rollback_to_nas.sh` для этого не подходит. Ночные копии идут на отдельный HDD машины стенда:
`backup.conf` с `CONTAINER=kz-price-hunter` и `BACKUP_TARGET=/srv/storage/kzph-backups`, cron в 04:30.

## Ночные копии

`~/kzph-prod/backup_to_nas.sh` по cron в 04:30, настройки — `~/kzph-prod/backup.conf`:
`CONTAINER=kz-price-hunter`, `BACKUP_TARGET=/srv/storage/kzph-backups`, `KEEP_LOCAL=2`, `KEEP_REMOTE=14`.

Порядок работы скрипта:
1. Проверяет цель до копии: каталог доступен для записи, это **другое устройство**, чем `data`, и места хватает.
   Если `/srv/storage` не смонтирован и каталог оказался на NVMe, скрипт остановится со сбоем.
2. Копию базы делает само приложение (`backup_database`, SQLite backup API + `quick_check`).
3. Переносит копию на цель и проверяет **конечный файл**: размер и `quick_check` на цели.
4. Кладёт рядом набор конфигурации `kzph-config-<та же метка>.tar` с правами 600: `compose.yaml`, `.env`,
   `settings.json`. Без него из одной базы сервис не поднять: в нём токены, настройки и ключи AI.
5. Только после этого удаляет старые копии.
6. Записывает итог в приложение: `ok` или сбой с шагом и причиной.

В мониторинге итог виден в разделе «Резервные копии», строка «Доставка на другой диск». Раздел становится
«деградацией» в двух случаях:
- последняя доставка не удалась;
- успешной доставки нет дольше 26 ч. Так виден и пропущенный cron, и остановленный контейнер.

Свежая копия рядом с базой на NVMe этого не скрывает. Пока доставок не было ни одной (стенд, разработка),
строка показывает «не настроена» и общий статус не меняет. Запись итога появится в проде с выпуском,
содержащим `backup_deliveries`; до него скрипт пишет в лог «не удалось записать итог доставки».

Для цели `host:каталог` (например, NAS) обе проверки выполняются на удалённой стороне по SSH:
`quick_check` базы через `python3` (на NAS есть) и состав набора конфигурации. Не удалось проверить —
это сбой, а не «ok»; старые копии в этом случае не удаляются.

Журнал запусков — `~/kzph-prod/backup.log`.

## Восстановление

Набор для восстановления — пара файлов из `/srv/storage/kzph-backups` с одной меткой:
`prices-nightly-<метка>.db` и `kzph-config-<метка>.tar`. Без пары скрипт требует явный `--config`.
`restore_prod.sh` проверяет набор и базу (`quick_check` и число товаров и наблюдений) **до** развёртывания.

Работает в два этапа:
- подготовка отмечает каталог файлом `.restore-state`;
- запуск продолжает именно этот подготовленный набор.

В каталог с базой без такой отметки (чужие данные) скрипт не пишет никогда.

Состояния каталога:
- `prepared` — база ещё не жила, её можно заменить более свежей;
- `starting` — запуск уже пытались, контейнер мог писать в базу, даже если проверки потом не прошли.
  Замена запрещена, допустим только повторный `--start`;
- `started` — проверки пройдены, замена запрещена.

**Репетиция** — проверить, что копия поднимает сервис. Её стоит делать раз в месяц и после крупных выпусков:
```bash
cd ~/kzph-prod && ./restore_prod.sh --to ~/kzph-restore-rehearsal --rehearsal --start
docker compose -f ~/kzph-restore-rehearsal/compose.yaml down && rm -rf ~/kzph-restore-rehearsal
```
Репетиция идёт без токена бота и AI-ключей, без суточной сводки, во внутренней сети Docker без выхода
наружу и без портов. Выключателя автообхода в приложении нет: обходы запускаются, но наружу не выходят.
Скрипт проверяет health, поиск, совпадение товаров, наблюдений цен и наблюдений пользователей с копией
и что настройки восстановлены.

**Настоящее восстановление** — на этой же машине после потери `~/kzph-prod/data` или на другой машине
с Docker и копией `/srv/storage/kzph-backups`. Скрипты запускаются из `~/kzph-prod` или из checkout
`~/kzph-stand/deploy/prod-host`: в новый каталог они не копируются.
1. **Подготовить целевую сторону, ничего не останавливая:**
   ```bash
   ./restore_prod.sh --to ~/kzph-prod-new
   ```
   Это проверка набора, проверка базы и развёртывание без запуска. На другой машине: `--from КАТАЛОГ_КОПИЙ`.
2. **Если старый прод жив, а его данные новее ночной копии** — снять свежую копию:
   ```bash
   docker exec kz-price-hunter python3 -c "import database; print(database.backup_database('manual'))"
   ```
   Скрипт напечатает путь внутри контейнера; на хосте файл лежит в `~/kzph-prod/data/backups/`.
   Затем подставить её в **тот же** подготовленный каталог:
   ```bash
   ./restore_prod.sh --to ~/kzph-prod-new --db ~/kzph-prod/data/backups/prices-manual-….db
   ```
   Конфигурация из шага 1 сохраняется. Пока экземпляр не запускался, базу можно заменять сколько угодно раз.
3. **Остановить старый прод** — до запуска нового. Иначе два бота с одним токеном (HTTP 409) и две базы.
   - На этой же машине — удалить контейнеры, данные останутся. У нового прода те же имена контейнеров,
     и `up` иначе упадёт на конфликте:
     ```bash
     cd ~/kzph-prod && docker compose down
     ```
   - На другой машине — остановить и запретить автозапуск:
     ```bash
     docker compose stop && docker update --restart=no kz-price-hunter kz-price-watchtower
     ```
4. **Запустить новый:**
   ```bash
   ./restore_prod.sh --to ~/kzph-prod-new --start --old-url http://127.0.0.1:35540
   ```
   Скрипт берёт **уже подготовленный** каталог, без повторного копирования. Он откажется, пока старый прод
   отвечает по `--old-url`; подготовленная база при этом не трогается, и команду можно просто повторить.
   После запуска скрипт проверяет health, поиск, данные и настройки и отмечает каталог как запущенный. После
   этого его база живая, и повторная подготовка в этот каталог запрещена.
5. **Прокси DSM** → `shop.molthun.ru` → назначение — адрес и порт нового прода. Порт задан в его `compose.yaml`;
   на другой машине — её адрес, а `TRUSTED_PROXIES` в `.env` должен быть адресом NAS.
6. **Проверка:**
   ```bash
   ~/kzph-prod/verify_public.sh
   ```
   Если имя контейнера или порт другие — `CONTAINER=…`, `WATCHTOWER=…` или `LOCAL_PORT=…`.

**Возврат на NAS.** Готового контейнера на NAS нет. Если понадобится:
1. Восстановить архив владельца или развернуть `restore_prod.sh` с набором из `/srv/storage/kzph-backups`.
   Скрипту нужны bash, Docker и python3; на Synology команды Docker идут через `sudo`.
2. Выполнить шаги 3–6 выше. Новый прод на NAS слушает свой порт, прокси DSM — `localhost:<порт>`,
   `TRUSTED_PROXIES=172.26.0.1/16`, как было до переезда.

`legacy/rollback_to_nas.sh` к этому неприменим.

## Чего не делать

- **Не запускать оба прода сразу.** Telegram отдаёт обновления одному потребителю: у второго
  экземпляра с тем же токеном бот ломается (HTTP 409), и каждый экземпляр пишет в свою базу.
  Поэтому старой стороне ставится `restart=no`, а `restore_prod.sh --start` не запускается, пока старый
  прод отвечает.
- **Не класть базу на сетевую шару** (NFS/SMB/Synology Drive). SQLite там ненадёжна, база — только
  на локальном NVMe. Synology Drive годится только как цель для готовых копий.
- **Не убирать `DOCKER_API_VERSION=1.44` у Watchtower.** Docker 29 отвергает API 1.25 из Watchtower 1.7.1:
  «client version 1.25 is too old», и прод перестаёт обновляться.
- **Не давать стенду токен продового бота** (см. `stand.env.example`).

## Репетиция переезда (история, 29.10.2026)

Поддельный NAS на той же машине:
- контейнер `fake-nas-app` из образа 6.5.2 с копией базы стенда (606 МБ) на порту 35541;
- заглушка `fake-nas-watchtower`;
- запуск скриптов с `NAS_SSH=local NAS_SUDO= NAS_DIR=… NAS_APP=… NAS_WATCHTOWER=… NAS_LIVE_URL=…`.

Результаты:

| Шаг | Результат |
|---|---|
| `move_from_nas.sh --check` | проверки пройдены, образ скачан, ничего не изменено |
| `move_from_nas.sh` | 1 мин 18 с: остановка, архив, перенос, quick_check ok (116 406 товаров), health ok, версия 6.5.2; у поддельного NAS `restart=no`, контейнер остановлен |
| `verify_public.sh` (на 127.0.0.1) | версии совпали, health 10/10, поиск 0,01 с, Watchtower работает |
| Watchtower | без `DOCKER_API_VERSION`: «client version 1.25 is too old»; с ним `--run-once kzph-prod` — Scanned=1, Failed=0 |
| Имя хоста контейнера | `kzph-prod`, интервал GIL 0,5 мс |
| `rollback_to_nas.sh --with-data` | 50 с: прод здесь остановлен, `restart=no`; данные на «NAS», прежние сохранены как `data.before-rollback-*`; «NAS» поднят и отвечает |
| `backup_to_nas.sh` (локальная цель) | копия 606 МБ за ~2 с; из 5 запусков локально осталось 3, в цели 2 (KEEP_LOCAL=3, KEEP_REMOTE=2) |

После репетиции её контейнеры, сеть и каталоги удалены, стенд работает. На настоящих данных база
2,2 ГБ: упаковка на HDD NAS и перенос добавят 1–3 минуты к простою.
Адрес соседа проверен на работающем стенде за тем же прокси DSM (`shdev.molthun.ru`): внутри контейнера
соединения приходят с `192.168.28.10`, поэтому `TRUSTED_PROXIES=192.168.28.10/32` верен. `ss` на хосте их
не видит (порт пробрасывается iptables), поэтому `verify_public.sh` читает таблицу TCP изнутри контейнера.
Не проверено:
- SSH и sudo на настоящем NAS — у машины стенда нет ключа к NAS, остановку настоящего NAS делает владелец;
- копирование на NAS по ключу;
- правило прокси DSM — схема та же, что у стенда `shdev.molthun.ru`.
