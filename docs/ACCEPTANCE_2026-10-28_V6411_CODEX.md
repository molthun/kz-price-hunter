## Изменение и подтверждённые инварианты

_apply_retire_transition теперь проверяет наличие, phase и gen задания внутри того же
BEGIN IMMEDIATE, в котором меняет память. Устаревший конкурент не сбрасывает was_available.
Подтверждение задания содержит product_id, phase=current и gen. Старый обработчик не удаляет
новое поколение, даже если оно уже успело перейти в current.

Подтверждено поведением, а не только чтением SQL:

| Сценарий | Результат |
|---|---|
| Оба потока прочли retire, первый завершил запись и удаление, второй продолжил | 1 событие / 1 outbox |
| Одновременное чередование двух потоков | 1 / 1 |
| Два отдельных процесса успели прочесть retire; первый завершился перед продолжением второго | 1 / 1 |
| Сбой DELETE после фиксации события, retry той же основной задачи | 1 / 1 |
| Рестарт/drain после такого сбоя, затем новый настоящий цикл снятия/возврата | без дубля первого; новый цикл даёт второе событие |
| Ошибка SQL при смене retire→current | задание остаётся retire; повтор доводит до 1 / 1 |
| Ошибка INSERT watch_events | задание current; повтор доводит до 1 / 1 |
| Ошибка INSERT notification_outbox | транзакция события откатывается; повтор 1 / 1 |
| Ошибка обновления watch_state после INSERT события/outbox | транзакция откатывается; повтор 1 / 1 |
| Ошибка DELETE watch_refresh | событие остаётся; повтор не дублирует |
| Настоящий SIGKILL дочернего процесса сразу после commit retire→current | init_db завершает обработку, 1 / 1 |
| Настоящий SIGKILL дочернего процесса сразу после commit события | init_db не дублирует событие, 1 / 1 |
| Устаревшее поколение перед фазой retire | _apply возвращает []; новое задание сохранено |
| Новое снятие после первой фазы старого обработчика | новое retire не подтверждается старым вызовом |
| Новое снятие и перевод нового поколения в current до старого ACK | новое current сохраняется; последующий настоящий возврат даёт новое событие |
| Миграция непустой watch_refresh без phase/gen | колонки добавлены, старое задание исполнено, 1 / 1 |
| Ошибка стартовой проверки, возврат до рестарта/drain | переход сохранён, 1 / 1 |
| База после снятия offers в 6.4.6 | память восстанавливается, возврат 1 / 1 |

Контролируемые ошибки SQL внедрены настоящими SQLite triggers. Барьеры потоков/процессов
меняют только расписание: оригинальные функции продолжают исполняться. SIGKILL действительно
завершает отдельный процесс; родитель проверяет код -SIGKILL и сохранённое состояние.
Вероятность такого чередования и дисковые отказы NAS этими проверками не измерялись.

Прямой путь, очередь/derived, drain/init_db, другой активный источник, limited/failed обход,
старый retry и независимый канал также проходят прежние штатные/независимые регрессии.
Суточное обслуживание вызывает тот же drain: его календарный запуск не ожидался специально.

## Ограничения и следующий шаг

Сохраняется указанная разработчиком граница общей системы наблюдений: текущее предложение
читается снимком перед evaluate_watches. Новое снятие между чтением и оценкой может дать
оценку по уже устаревшему доступному снимку. Приёмка фаз/поколений не означает линейной
согласованности всех проверок наблюдений с конкурентными записями каталога; этот уровень
согласованности отдельно не подтверждён. Также не обещается exactly-once внешняя доставка
Telegram при неопределённом результате сети.

Свежие Linux/container, frontend, CI/image и полная нагрузочная волна стенда здесь не запускались.
Их результаты в передаче разработчика остаются его самопроверкой. UI в исправлении не менялся.
Настоящий рестарт приложения/контейнера и отказ хранилища NAS не проверялись; выполнены
отдельные процессы записи и настоящий init_db после их аварийного завершения.

Следующий шаг: решение владельца о выпуске после эксплуатационной/релизной приёмки
(CI/image smoke, полная волна стенда, подтверждение конкретного образа). Новых исправлений
по G01–G05 в проверенных сценариях не требуется. Историю прежних отказов приёмки не переписывать.
