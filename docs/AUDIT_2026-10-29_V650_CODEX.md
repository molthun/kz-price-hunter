## V01 · P1 · Одобрение нового продавца перезаписывает существующего по совпадению префикса домена

Места: repositories/candidate_repo.py:approve_onboarding_candidate; SellerRepository.save_or_update.

При отсутствии matched_seller_id slug/id строятся из первого компонента domain. Продавцы
example.kz и example.com получают seller_example. save_or_update при конфликте ID обновляет
имя, домен, metadata и другие поля существующего продавца без проверки идентичности.

Независимо: создан Original retailer, id=seller_example, domain=example.kz. Подана заявка
Unrelated Outlet / https://example.com. Matcher вернул matched=None. После одобрения заявки
получено approved_id=seller_example; прежняя строка стала Unrelated Outlet / example.com.
Два прогона подтверждают перезапись. Автоматическое одобрение гостем не утверждается:
дефект возникает при штатном решении модератора подключить новый, несопоставленный магазин.

Рекомендация: независимый уникальный ID нового продавца и безопасное выделение slug;
обновление существующей сущности только по подтверждённому решению сопоставления.
Критерии: разные домены с общим префиксом/одинаковые нормализованные имена не перезаписывают
друг друга; их предложения/каналы остаются у правильных продавцов; повтор одобрения идемпотентен.

## V02 · P2 · Price History 2.0 ретроспективно меняет состояние старых наблюдений

Места: PricingRepository.get_product_price_history; offer_price_history; build_price_history_series.

Запись истории содержит offer_id/цену/время, но новая группировка берёт product/seller/channel/
condition из ТЕКУЩЕЙ offers. Изменение состояния предложения переименовывает всю его историю.

Независимо: сохранена цена 499000 для NEW; затем то же предложение стало USED с ценой 400000.
Старую точку времени разделили с другими предложениями, чтобы исключить совпадение времён.
Новый report относит первоначальные 499000 к **USED**, NEW-линия исчезает. Первый вариант
сценария дополнительно показал потерю точки при совпавших временах внутри объединяемой линии;
повтор с разными временами изолирует именно ошибку ретроспективного состояния.

Рекомендация: сохранять измерения серии на момент наблюдения или обеспечивать неизменяемую
идентичность предложения для этих измерений. Не восстанавливать прошлое по текущей condition.
Критерий: после смены NEW→USED старая цена остаётся NEW, новая USED; аналогично проверить
перепривязку product/seller/channel и одновременные точки нескольких предложений.

## V03 · P2 · Дифференцированная свежесть не подключена к реальной purchasability policy

Места: domain/freshness_v2.py; domain/purchasability.py; SearchCore/search SQL; provenance/monitoring.

Новая evaluate_offer_freshness вызывается в provenance и monitoring. Реальная доступность
поиска/наблюдений остаётся на прежнем общем data_quality-пороге, SQL тоже прежний.

Независимо: активное food_aggregator-предложение возрастом 30 часов новая функция помечает
EXPIRED, однако настоящая общая offer_purchasable возвращает True. Один объект получает
противоречивые ответы. Это проверка двух рабочих правил, не утверждение о таком товаре на проде.

Рекомендация: единое правило по source type для Python, SQL до LIMIT, watches, витрины и
помощника; обеспечить поступление metadata типа источника на эти пути. Критерии — agreement-
тесты API/YML/сайт/пост/story/used/food на границах, с реальным SQL-отбором и уведомлениями.

## V04 · P2 · Мониторинг выдаёт размер выборки 5000 за общее количество

Место: domain/monitoring_v2.py: offer_rows LIMIT 5000 → total_active_offers=len(offer_rows).

Независимо: в временной БД 5005 активных offers. Overview показывает total_active_offers=5000;
fresh/stale/expired и разбивки также считаются только по этому фрагменту, признака выборки нет.
Два прогона. На производственном каталоге существенно большего размера такая сводка будет
описывать произвольный фрагмент, а не всю систему.

Рекомендация: полные агрегаты в SQL/постраничном подсчёте либо явные sampled/coverage и отдельный
реальный total. Ошибки чтения не должны молча превращаться в достоверные нули.
Критерий: >5000 предложений, в том числе проблемные за границей выборки, отражаются в totals
и метриках либо явно обозначены как необследованная часть.

## V05 · P2 · Помощник приписывает рассрочку по типу канала и сравнивает разные состояния

Место: domain/search_assistant.py:INSTALLMENT_CAPABLE_CHANNELS, ask, _build_grounded_explanation.

Факт рассрочки выводится из channel_type=marketplace/Kaspi/Forte/Halyk либо слова kaspi в URL,
без сохранённых условий оплаты. Независимый запрос «iPhone в рассрочку» по штатным синтетическим
offers без полей рассрочки получает best_installment_offer и текст «рассрочка».
Та же выдача сравнивает USED direct за 420000 с NEW marketplace за 539000 как разницу способов
покупки 119000, не объясняя различие состояний. Это реальные строки БД, но вывод об условиях
покупки не обоснован ими. Повтор подтверждает поведение.

Рекомендация: подтверждённые признаки/условия рассрочки; при отсутствии — «условия неизвестны».
Сравнивать одинаковый товар/состояние/прочие существенные параметры, явно раскрывать различия.
Критерии: тип площадки сам по себе не доказывает рассрочку; NEW/USED не дают ложной экономии
от смены канала; поддержаны прямые продавцы с подтверждённой рассрочкой.

## V06 · P2 · S2-E10 реализован как потребитель готового OCR, а не извлечение из изображений

Места: VisionExtractionEngine.extract_from_observation; ContentObservationRepository.extract_candidates;
ai_router.TASKS. Установлено разбором связей, реальный провайдер не вызывался.

Рабочий путь читает raw_metadata.vision_items/ocr_text либо уже имеющийся текст. media_urls
не читаются и не передаются OCR/Vision. Добавленная запись vision_extraction в TASKS не имеет
вызывающего пути извлечения изображения. Изображение/сторис без готового текста не превращается
в эти данные. image_text учитывается в guard репозитория, но самим extract_from_observation
также не читается. Подготовленный OCR в тесте не подтверждает мультимодальный ввод.

Рекомендация: либо завершить image→контролируемое извлечение→валидация→candidate с лимитами,
учётом стоимости и provenance, либо обозначить этап частичным и не заявлять его завершённым.
Критерий: известное тестовое изображение без подписи/готового OCR проходит рабочий путь;
закрытая цена не угадывается, ошибки и лимиты провайдера наблюдаемы. Реальные вызовы требуют
отдельного учёта; этим аудитом никакие расходы не авторизованы и не совершались.

## V07 · P2 · Новые correlation IDs не устанавливаются рабочими обработчиками

Места: telemetry.correlation_context/get_correlation_ids; HTTP middleware, seller/source/offer paths.

Новый context manager и перенос значений в событие работают, когда тест вручную устанавливает
контекст. Поиск всех production-вызовов correlation_context и .set для новых request/seller/source/
offer contextvars не обнаружил установок: есть определение helper и его тестовое использование.
Обычные запросы/операции не получают сквозные IDs автоматически. Прежний scan_id сам по себе
не закрывает новые измерения request→seller→source→offer.

Рекомендация: вход/сброс request context в middleware, установка seller/source/offer в рабочих
операциях, перенос в executor, сброс в finally. Критерий: два параллельных настоящих HTTP-запроса
дают разные request_id, связанные события содержат нужные ID и не смешиваются; тест сам
контекст не устанавливает.
