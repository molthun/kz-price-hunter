## C-E05-01 (P1): неподтверждённый сайт объявляется найденным каталогом

`SourceProfiler.profile_url()` для любого обычного URL возвращает профиль Tier 4 с
`observed=False`. Затем `CandidateRepository.process_discovered_candidate()` проверяет только
`extraction_tier <= 4` и переводит кандидата в `CATALOG_FOUND`.

Воспроизведение без сети:

```text
URL: https://example.kz/
profile: observed=False, tier=4, format=html
candidate.status: CATALOG_FOUND
```

Это противоречит семантике статуса из плана: `CATALOG_FOUND` означает, что каталог найден,
а не предположен по адресу. При последующем подключении discovery обычная визитка, парковочная
страница или несуществующий каталог пройдут дальше как пригодный источник.

Критерий исправления:

- `CATALOG_FOUND` возможен только после подтверждённого наблюдения каталога;
- эвристический профиль без наблюдения остаётся `PROFILED`;
- добавить регрессию для обычной главной страницы и отдельно для подтверждённого feed/API/HTML-каталога.

## C-E05-02 (P1): marketplace seller ID не содержит пространство площадки

`marketplace_seller_id` хранится и сравнивается как одна строка. Источник площадки в ключ не
входит. Поэтому одинаковые локальные ID на Kaspi и Forte считаются одним сильным идентификатором:

```text
существующий продавец: Kaspi seller_id = 42
кандидат: Forte seller_id = 42, другое название
результат: AUTO_MATCH, confidence=0.95
```

Это прямой путь к ложному объединению разных продавцов, которое план отдельно запрещает.

Критерий исправления:

- ключ маркетплейса должен быть парой `(marketplace/channel, external_seller_id)` либо
  канонической строкой с обязательным namespace;
- lookup, уникальность, частотная защита и matcher должны использовать один формат;
- тесты: одинаковый ID на разных площадках — не AUTO_MATCH; одинаковый ID на одной площадке — AUTO_MATCH.

## C-E05-03 (P2): поле `observed` существует только в памяти

`SourceProfile` содержит `observed`, но в таблице `source_profiles` такой колонки нет, а
`save_source_profile()` её не записывает. Проверено поведением:

```text
SourceProfile(observed=True) -> save -> reload -> observed=False
```

Тем самым исправление F1 теряет главный признак, который должен отделять наблюдённый факт от
догадки. Любой последующий процесс после чтения из БД не сможет отличить подтверждённый источник.

Критерий исправления:

- аддитивно добавить и сохранять `source_profiles.observed`;
- явно определить, какие `hints` считаются результатом наблюдения и выставляют `observed=True`;
- round-trip тест для `False` и `True` на существующей и новой схеме.

## C-E05-04 (P2): модерация не завершает lifecycle, а статусы не валидируются

`resolve_review(..., "APPROVED")` закрывает только строку очереди. Кандидат остаётся
`REVIEW_REQUIRED`, `matched_seller_id` остаётся пустым, продавец/связь не создаются. Одновременно
`update_candidate_status()` принимает любую строку и позволяет записать, например,
`INDEXED_WITHOUT_APPROVAL`; допустимость статуса и перехода не проверяется.

То есть заявленная цепочка `REVIEW_REQUIRED -> APPROVED -> INDEXED / REJECTED` пока не является
рабочим процессом: нормальное решение не продвигает кандидата, а произвольный вызов может
перескочить проверки.

Критерий исправления:

- атомарно связать решение очереди с кандидатом и выбранным продавцом либо явно разделить
  `approve_match` и `approve_new_seller`;
- определить разрешённые переходы и отвергать неизвестные статусы/переходы;
- повторное решение должно быть идемпотентным и не оставлять stale `PENDING` после AUTO_MATCH;
- тесты обоих решений, повторной обработки и отката при сбое посередине.
