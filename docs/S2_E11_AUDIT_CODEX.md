## Итог

Статус S2-E11: **IN_PROGRESS**. Базовые FTS5-триггеры, фильтры и агрегация
работают на подготовленной тестовой выборке, а полный regression suite проходит.
Однако этап нельзя принимать: эталонный запрос из плана не находит существующий
товар, существующие строки не индексируются при развёртывании FTS, недостоверный
оффер может стать лучшей ценой, а ранний `LIMIT` скрывает подходящие товары.

## C-E11-01 (P1): эталонный запрос плана возвращает NOT_FOUND

План задаёт запрос `айфон 16 про 256 бу астана` и ожидает нормализацию модели,
памяти, состояния и города. Текущий parser определяет Apple, USED и Астану, но:

- не считает `256` памятью без суффикса `GB/ГБ`;
- оставляет `айфон` и `про` в поисковой строке без нормализации к `iPhone` / `Pro`;
- передаёт все токены в FTS как обязательные через `AND`.

На товаре `Apple iPhone 16 Pro 256GB` результат воспроизведения:

```text
clean_query = "айфон 16 про 256"
attributes = {}
outcome = NOT_FOUND
items = []
```

Тем самым основной сценарий этапа не работает, хотя отдельные unit-тесты parser
проходят.

Критерий исправления:

- нормализовать поисковые синонимы и русские формы, не теряя исходный запрос;
- поддержать модельно-зависимый разбор памяти без единицы там, где это однозначно;
- добавить сквозную регрессию ровно для запроса из плана и близких вариантов
  (`айфон`/`iphone`, `про`/`pro`, город с предлогом и склонением).

## C-E11-02 (P1): FTS не заполняется для уже существующих canonical_products

`init_schema_v2()` создаёт внешнюю FTS5-таблицу и триггеры, но не вызывает
`rebuild_canonical_products_fts()`. Триггеры работают только для последующих
INSERT/UPDATE/DELETE.

Воспроизведение на базе старой схемы:

```text
canonical_products содержит old_iphone до init_schema_v2
MATCH 'iphone' после init_schema_v2 -> []
после вставки new_iphone -> ['new_iphone']
```

Fallback на LIKE не спасает полностью: как только FTS вернул хотя бы одну новую
строку, fallback не выполняется, и старые подходящие товары исчезают из выдачи.

Критерий исправления:

- при первом создании индекса атомарно выполнить rebuild существующих строк;
- не перестраивать индекс на каждом старте без необходимости;
- проверить upgrade-сценарий: строки до создания FTS + строки после него находятся
  вместе, повторная инициализация идемпотентна.

## C-E11-03 (P1): out-of-stock и просроченный оффер становится best_offer

Выборка проверяет только `o.is_active`, `s.is_active` и `c.is_active`. Поля
`availability` и `observed_at` не участвуют в пригодности цены, хотя состав Product
Index в плане явно включает Freshness.

Воспроизведение:

```text
offer.price = 1
offer.availability = out_of_stock
offer.observed_at = 2020-01-01
результат: этот offer выбран best_offer с min_price = 1
```

Пользователь получает недоступную многолетнюю цену как лучшую. Это нарушает уже
принятое в проекте правило: устаревшая цена может быть показана с оговоркой, но не
должна участвовать в выборе лучшей цены.

Критерий исправления:

- определить и применить единый контракт availability/freshness для v2 offers;
- недоступные и слишком старые офферы не участвуют в `best_offer`, `min_price`,
  сортировке по цене и скидке;
- если остаются только устаревшие офферы, вернуть честное отдельное состояние, а не
  достоверную лучшую цену;
- добавить границы свежести и mixed fresh/stale/out-of-stock в регрессии.

## C-E11-04 (P1): LIMIT применяется до фильтров офферов и скрывает результаты

Репозиторий сначала выбирает не более `limit * 2` канонических товаров, а затем
применяет город, состояние, канал и цену к их офферам. Подходящий товар за пределами
этой произвольной кандидатной выборки уже не рассматривается.

Воспроизведение: 101 товар с офферами Алматы, затем товар с оффером Астаны;
`search('', city='Астана', limit=50)` возвращает `NOT_FOUND`.

Критерий исправления:

- применять offer-фильтры при отборе кандидатов (`EXISTS`/JOIN/CTE) до окончательного
  limit либо добирать кандидатов предсказуемой пагинацией;
- сортировка и limit должны применяться к уже пригодным агрегатам;
- добавить набор больше `2 * limit`, где совпадение находится после первых кандидатов.

## C-E11-05 (P2): Search KPI не отражает качество и ошибки

Для точного `RTX 5090` с одним продавцом воспроизведён `WEAK_MATCH`: BM25 даёт малое
число, бонус точного совпадения модели, заявленный в карточке, в коде отсутствует, а
число продавцов влияет на решение FOUND/WEAK. Тот же точный товар с несколькими
продавцами может стать FOUND без улучшения текстового совпадения.

Статус `ERROR` объявлен в контракте, но недостижим: исключение репозитория выходит
наружу. Воспроизведение с `sqlite3.OperationalError` завершилось исключением, а не
`SearchResponse2(outcome=ERROR)`.

Критерий исправления:

- отделить качество текстового/атрибутного совпадения от популярности продавцов;
- точная модель `RTX 5090` должна быть FOUND независимо от числа продавцов;
- заведомо близкий, но другой товар не должен становиться FOUND;
- определить границу обработки ошибок: либо возвращать ERROR по контракту, либо
  удалить ложное обещание и преобразовывать ошибку на вызывающем API; закрепить тестом.

## C-E11-06 (P2): Search Core 2.0 не подключён к рабочему пути поиска

Поиск по репозиторию показал только определения и экспорты `SearchCore` /
`SearchRepository`; приложение, API и существующий `search_engine.py` их не вызывают.
Следовательно, этап сейчас является изолированной библиотекой: ни один запрос
пользователя не проходит через Unified Product Index.

Критерий исправления:

- явно подключить Search Core 2.0 к контролируемому рабочему пути (feature flag,
  shadow или отдельный v2 endpoint) с сохранением совместимости;
- добавить сквозной API-тест и проверку, что выключение нового пути возвращает старое
  поведение;
- если подключение намеренно относится к следующему этапу, понизить заявление
  карточки и вынести это отдельным обязательным критерием, а не считать этап готовым.

## Что подтверждено

- FTS5 insert/update/delete triggers работают для строк, записанных после создания
  индекса.
- Ручной `rebuild_canonical_products_fts()` заполняет индекс.
- На подготовленной фикстуре работают агрегация продавцов, фильтры города/состояния/
  цены, сортировки и NOT_FOUND.
- SQL FTS строится параметризованно; прямой инъекции через MATCH в проверенном пути
  не найдено.
