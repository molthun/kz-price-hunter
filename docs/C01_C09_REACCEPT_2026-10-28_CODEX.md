## R01 · P1 · ACK снова выполняет SQLite write в цикле событий

Места: `queue_service.py:398–433`, `web/server.py:1888–1897`, `database.py:3874–3915`.

Enqueue/dequeue вынесены в asyncio.to_thread, но ack/nack/reject синхронно вызывают
SQLite DELETE/UPDATE. Воркер исполняет их непосредственно в aiohttp event loop.
Поэтому конкурентный писатель снова останавливает весь HTTP-сервер, включая liveness.

На Linux удержание BEGIN IMMEDIATE около 450 мс превратило sleep(20 мс) в **538 мс**
при реальном qm.ack. На macOS эффект также подтверждён. У соединения busy_timeout=15 с,
поэтому при более долгой конкуренции окно ожидания может быть существенно больше.
Это доказательство механизма текущего кода, не ретроспективное установление причины NAS.

Требуется: async подтверждение/отказ через ограниченный DB executor, ограничение ожидания
и распространение неуспешного ACK. Не удалять in-flight до подтверждения durable-перехода.
Приёмка: держать SQLite writer во время ACK/NACK/reject, параллельно опрашивать live/API;
сервер не блокируется, task не считается подтверждённым при неудачном DELETE.

## R02 · P1 · Принятый fallback теряет retry; ограничение spool не атомарно

Места: `queue_service.py:292–331,408–433`.

task_id назначается до попытки spool_enqueue. Если SQLite insert падает, payload с этим
task_id уходит в память/Redis, enqueue возвращает True. На сбое обработки nack вызывает
spool_nack для несуществующей строки, затем **не** возвращает задачу в память из-за наличия
task_id. Нигде не остаётся ни payload, ни ошибки dead-letter.

Воспроизведено на Linux: accepted=true, has_task_id=true, queue_after_nack=0,
все статусы spool=0, next_item=null. Кроме того сам принятый fallback по-прежнему не
переживает смерть процесса. Наличие UUID не является доказательством durable-приёма.

Дополнительная проверка admission: два параллельных enqueue одного shop при maxsize=1
оба вернули True, pending=2. Между SELECT stats и INSERT есть окно гонки. Проверка
выполнена с барьером после настоящего чтения SQL, задающим допустимый порядок конкуренции.

Требуется: при отказе durable admission либо явный False, либо другое устойчивое хранилище;
отдельный признак backend/receipt, не эвристика по task_id. Проверку ёмкости и insert делать
в одной транзакции, определить общий/помагазинный бюджет. Приёмка: отказ БД на enqueue,
ошибка обработки и restart не теряют принятую задачу; конкурентный admission соблюдает лимит.

## R03 · P1 · После SIGKILL восстановленная задача отклоняется

Места: `web/server.py:1826–1833,2258,2302`, `database.py:3917`.

lease_generation хранится в задаче, но источник поколения — счётчик Python, начинающийся
с 1 при каждом старте. Первый обход увеличивает его до 2. Recovery возвращает processing
в pending, но сохранённое поколение 2 сравнивается с новым 1 и задача переводится в rejected.
В последующих обходах возможны как несовпадения, так и случайное равенство старых поколений:
долговечность и владение процессом этот счётчик не удостоверяет.

Настоящий процесс producer принятую задачу получил в processing и завершён SIGKILL
(returncode=-9). Новый процесс прошёл initialize/recovery, получил задачу и отклонил:
item_generation=2, current=1, execution_result=false, written=0, rejected=1.
Результат одинаков на macOS и Linux. Сохранение payload в rejected улучшает наблюдаемость,
но не выполняет обещание завершить принятые задачи после crash.

Требуется: устойчивый идентификатор/эпоха владельца и отдельно определённая политика
обработки уже принятых задач после восстановления. Новый законный worker должен завершать
или явно восстанавливать такие задачи, не отбрасывать их по локальному счётчику.
Приёмка: реальные kill до/после claim/commit/ACK на нескольких поколениях; все принятые
ID получают корректный конечный исход, товары/уведомления не теряются и не дублируются.

## R04 · P1 · Fencing не защищает commit, recovery присваивает активную обработку

Места: `web/server.py:1826–1868`, `database.py:3917–3928`.

Проверка lost/generation делается один раз до await. После потери аренды последующие
save/reconcile/log и ACK выполняются без транзакционной проверки актуального владельца.
Воспроизведение с управляемой паузой между guard и сохранением: lost=true,
execution_result=true, written=1, spool пуст после ACK. Вставка товара выполнена настоящим кодом.

Также spool_recover_on_startup безусловно переводит **все** processing в pending.
Второй экземпляр приложения может получить уже исполняемую задачу живого первого:
recovered=1, same_task=true. Отдельного owner/claim lease в строке нет. Планировочная
аренда не запрещает запуск второго writer и recovery, которые стартуют до получения её сканером.

Требуется: claim owner/lease и fencing в транзакции обязательных эффектов; recovering
только доказанно осиротевших claims. Приёмка: два процесса, живой/погибший владелец,
потеря аренды непосредственно перед commit, повторный запуск второго экземпляра.

## R05 · P1 · Повтор после частичного commit теряет событие снижения цены

Места: `web/server.py:1737–1776,1845–1846`, подтверждение `database.py:3874`.

Товар коммитится до вычисления аномалий и watches; вся task при ошибке повторяется заново.
Исходная цена для повторного вычисления берётся из уже обновлённой БД. Переход цены
исчезает: changed_ids оказывается пустым. Одного durable payload недостаточно для
идемпотентного воспроизведения всех обязательных эффектов.

Воспроизведение: настоящее any_drop наблюдение и baseline=100; task меняет цену на 80;
после commit возникает synthetic исключение в check_anomaly, затем настоящий nack/retry.
Повтор успешно ACK-нут, events=0. Положительный контроль без сбоя (80→60) даёт events=1.
Оба результата подтверждены в Linux-контейнере. Telegram не отправлялся.

Требуется: атомарная фиксация перехода цены и durable outbox для производных эффектов
либо устойчивые идемпотентные стадии с исходным old_price/event ID. Приёмка: обрывы между
save, anomaly, watch, reconcile, scan log и ACK; одинаковые обязательные результаты с
безаварийным прогоном и отсутствие повторных заданий доставки.

## R06 · P1 · Барьер и readiness по-прежнему сообщают недостоверное состояние

Места: `queue_service.py:460–491`, `web/server.py:289–312`, `database.py:3931`.

Три независимых сценария одного контракта завершения:

- При исключении spool_stats код подставляет spool_pending=0 и spool_errs=0:
  drained=true при **реально pending=1**. Ошибка наблюдения интерпретируется как успех.
- Scope барьера — shop_key без scan/task ID. Старый rejected того же магазина заставляет
  новый успешно подтверждённый набор получать drained=false; операции архивирования/
  разрешения старых ошибок и привязки их к конкретному scan нет.
- ready = ok and worker_ok игнорирует dead_letters/rejected. С одним dead_letter health
  возвращает HTTP 200, status=ok, dead_letters=1. Один rejected вообще не виден в health:
  status=ok, queue_size=0, dead_letters=0.

Требуется: fail-closed при невозможности прочитать состояние; барьер по принятым ID
конкретного обхода; раздельные текущие/исторические отказы и явное degraded состояние.
Приёмка: недоступный spool не даёт complete; прежняя ошибка не приписывается новому scan;
активные нерешённые отказы отражаются в readiness и диагностике согласованно.

## R07 · P2 · Stale-only кандидат продолжает вытеснять доступный до LIMIT

Места: `repositories/search_repo.py:149–181`, `domain/search_core.py:201–216`.

NULL-first для expired/out_of_stock исправлен, но SQL не учитывает freshness и положительную
цену так же, как SearchCore. Старая цена даёт числовой MIN и обгоняет доступное предложение,
после чего агрегация превращает её в непокупаемую карточку, когда второй кандидат уже потерян.

В Linux: stale p0=1 (observed_at=2020), fresh p1=100. limit1 → p0/min=null;
limit50 → p1/min=100 первым. Это другой случай исходного критерия C07, не повтор уже
исправленного NULL-first. Требуется согласовать SQL-кандидатов/порядок с окончательной
purchasability; повторить limit1/50 для stale, нулевой цены, expired и смешанных каналов.

## R08 · P1 · Watches всё ещё уведомляют о stale предложении выключенного канала

Место: `database.py:3155–3195`.

Новые availability и expires_at проверяются, но observed_at и активность joined channel/
seller не входят в решение is_available. Воспроизведение через сохранённые V2-данные:
канал is_active=false, наблюдение цены 2020 года, цена 50; watched_offers вернул
available=1, настоящее target_price=100 создало new_events=1.

Требуется выполнить исходный критерий C08 полностью: одна purchasability policy для
поиска/витрины/watches, включая свежесть и активность источника. Приёмка должна проверять
stale, отключённый channel, отключённого seller по отдельности и восстановление back_in_stock.

## R09 · P3 · На границе TTL SQL и Python противоречат друг другу

Места: `repositories/search_repo.py:153`, `domain/search_core.py:41`.

Если expired определяется как now >= expires_at, допустимый SQL-фильтр — expires_at > now.
Разработчик поменял его на expires_at >= now, оставив просроченное ровно на границе предложение
в ключе цены. На фиксированном now SQL первым выбирает p0 с exact TTL и ценой 1, Python
одновременно возвращает expired=true. Передача now в repository, freshness и агрегацию
по-прежнему не единая. Требуется общий момент времени/UTC policy и пограничные тесты.

## R10 · P2 · Приёмочный стенд запущен без ограничений ресурсов

Фактический docker inspect: **NanoCpus=0, Memory=0**. Это отсутствие ограничений Docker,
а не 4 CPU/15 ГБ и даже не настройки файла stand.nolimits. Runtime сообщает пул 32.
Здоровый снимок в заявке сделан через 18 секунд после запуска, без сканирования; он не
доказывает работу новой модели записи при конкуренции и полном цикле на ресурсах NAS.
Источник команды развёртывания этого контейнера не установлен, поэтому причина снятия
ограничений разработчику не приписывается без доказательств.

Повторный read-only снимок 16:57 Asia/Almaty: 6.4.2, uptime около 995 с, RSS 318 МБ,
lag=0.6 мс, queue=0, problems=[] — на **этом** неограниченном активном контейнере.
Независимый аудиторский Linux-прогон выполнен отдельно с явными лимитами и всё равно
воспроизвёл дефекты; активный стенд при этом не менялся.

Требуется восстановить согласованный режим развёртывания и зафиксировать inspect/cgroup,
состав данных и нагрузку. После исправлений — полные волны/рестарты с заданными критериями.
Текущее публичное healthy не заменяет такую приёмку.

## R11 · P2 · Действующий диагностический credential записан в Git-документ

Место: `docs/AGENT_HANDOFF.md`, строка 52 исходного проверяемого `7358a1e` (после добавления
аудиторской карточки локальные номера сдвинуты). В команде заявки буквально указан токен
для X-Diag-Token. Без вывода значения проверено хэш-сравнением: **совпадает с активным
DIAG_TOKEN стенда**. Токен открывает диагностику, а не административную запись, но является
действующим секретом. Новые свидетельства содержат только булев факт совпадения.

Secret gate этого класса credential не обнаружил. Это конкретная утечка, а не гипотетическое
требование сканировать произвольные числа. Remote main пока старый; удалённая публикация
этого credential аудитом не подтверждена. Уже локальная Git-история содержит значение.

Требуется заменить токен стенда и убрать значение из документа, используя env-заголовок
или чтение настроенного контейнерного окружения. До push разобраться с содержащими секрет
коммитами; переписывание истории и смену настроек аудит сам не выполняет. Факт замены,
доступ новым токеном и отказ старого проверить без сохранения значений в отчётах.

## Дополнительная граница C06

Под реально занятым default executor проверено auth_middleware: `/api/live` и `/api/health`
с cookie проходят, `/api/readiness` с той же cookie ждёт пул. Alias должен подчиняться
одинаковой политике. Остальные сессионные API всё ещё используют asyncio.to_thread в
общем пуле; перенос auth в отдельный пул не сделан. Заявленные «гарантированные 0.18 мс»
не являются SLA: R01 может заблокировать сам event loop ещё до обработки запроса.
