## G05 · P2 · Повтор refresh после события заново создаёт искусственное снятие и возврат

Место: `database.py:refresh_retired_watches` (принудительное is_available=0 → текущее состояние →
DELETE watch_refresh), `web/server.py:_detect_after_save`.

### Независимое воспроизведение

1. Настоящей очередью сохранить товар, создать repeat back_in_stock наблюдение с cooldown=0,
   проверить доступный товар (память was_available=1).
2. Подготовить старую БД и выполнить init_db с одной внедрённой OperationalError в evaluate_watches:
   приложение продолжает работу, снятие сохранено, watch_refresh остаётся.
3. Вернуть товар по прежней цене настоящей очередью.
4. На временной БД установить SQLite BEFORE DELETE trigger для watch_refresh с RAISE(ABORT).
   Во время derived настоящее evaluate_watches уже сохраняет первое событие и outbox,
   затем DELETE задания действительно падает. Проверено: событие 1, задание остаётся 1.
5. Удалить только тестовый trigger. Настоящие qm.nack → dequeue → _execute_queue_item → ACK
   повторяют ту же задачу.
6. Получено **2 watch_events и 2 задания notification_outbox вместо одного**.

Сценарий воспроизведён в наборе и отдельно. Это контролируемый сбой SQL DELETE, не замер
реального дискового отказа; повтор и запись события/outbox выполнены рабочим кодом.
Telegram не отправлялся. cooldown=0 — разрешённая настройка; положительный cooldown может
скрыть немедленный дубль, но не обеспечивает идемпотентности при более позднем повторе.

Причина: событие и удаление watch_refresh фиксируются разными транзакциями. Повтор сначала
снова устанавливает was_available=0, затем вызывает переход в 1. У outbox разные alert_id,
поэтому UNIQUE(alert_id,user_id) не связывает эти два события с одним фактическим возвратом.

Карточка разработчика прямо называет поведение at-least-once. Здесь проблема подтверждена
до внешней отправки: два независимых внутренних задания создаёт одна обработка перехода.
Отказ от обещания exactly-once Telegram не требует дублирования внутренних событий.

### Рекомендация и критерий приёмки

Связать событие с устойчивым идентификатором перехода/поколения и уникальным ключом,
либо атомарно завершать применение перехода вместе с событием и обязательством доставки.
Повтор не должен повторно создавать искусственную недоступность для уже применённого перехода.
Не устранять дубль удалением задания до записи события: это вернёт потерю уведомления.

Критерий: событие/outbox сохранены → ошибка подтверждения/DELETE задания → retry/restart →
ровно одно событие и одно задание outbox для этого возврата. Новый настоящий цикл снятия/возврата
создаёт новое событие. Прежние G01–G04 продолжают проходить.
