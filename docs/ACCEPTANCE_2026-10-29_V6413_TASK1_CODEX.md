## S01 · P2 · _run_db_shielded повторно ожидает coroutine вместо созданной Task

Место: `web/server.py:3548–3558`; использование — startup_watch_refresh_worker;
ожидание отменённых задач — background_tasks, ≈3625.

run_db — async def. Выражение `fut = run_db(func, *args)` возвращает coroutine, а не Future/Task.
asyncio.shield(fut) создаёт собственную Task для её исполнения. После отмены внешней корутины
`await fut` повторно ожидает тот же coroutine, который уже исполняется внутри этой Task.
Возникает **RuntimeError: coroutine is being awaited already**, который `except Exception: pass`
подавляет. Внешняя задача заканчивается отменой, а защищённый вызов продолжает работать в пуле.

Трассировка фактического исполнения helper подтвердила последовательность исключений:
CancelledError → RuntimeError с указанным текстом (`cancel-exception-trace.txt`).

### Независимые проверки

1. Настоящий _run_db_shielded запускает синхронную функцию в настоящем _db_executor.
   Функция сигнализирует о начале и ждёт управляемого события. Отменяется внешняя Task.
   Через 50 мс Task уже done=true, тогда как функция ещё не завершилась.
2. Настоящий startup_watch_refresh_worker начинает первую страницу для 600 заданий.
   Подменённая обёртка страницы только задерживает вызов оригинального drain до разрешения.
   После cancel воркер уже done=true, заданий ещё 600. Затем страница освобождается и
   настоящий drain обрабатывает 500: в БД остаётся 100. То есть запись происходит **после
   завершения отменённого воркера**, вопреки обещанному ожиданию страницы.

Обе проверки FAIL дважды. В finally тесты освобождают и дожидаются потоков: фоновых операций
после завершения проверки не оставлено. Потеря/повреждение БД этим сценарием не доказаны;
доказано отсутствие гарантии корректного завершения страницы при остановке. Контейнерный
stop/таймаут Docker не моделировался.

### Рекомендация и критерий приёмки

Сохранить объект реально запущенной Task/Future, который передаётся shield, и при отмене
дождаться того же объекта; не повторно ожидать исходный coroutine. Проверить поведение
очистки приложения и повторной отмены. Сохранить короткие страницы и возможность повторить
невыполненные задания. Не заменять проблему подавлением ошибки ожидания.

Критерий: отмена во время страницы не завершает cleanup/воркер, пока эта страница не
закончилась; после её завершения отмена возвращается, новая страница не стартует, оставшиеся
задания сохраняются. Ошибка страницы при отмене корректно учтена, фоновой записи после
завершения cleanup нет. Обычный /api/live до конца drain и прежняя матрица по-прежнему проходят.
