## L03 — P2: срок проверяется между операциями, но не прерывает зависшее чтение

Progress handler и проверки между кусками — полезное частичное исправление для выполняющегося SQL/копирования. Однако `src.read(chunk)`, `dst.write(block)` и файловые открытия остаются блокирующими. Пока чтение не вернулось, `_check_deadline` не вызывается. SQL progress handler также не является предельным сроком для заблокированного файлового I/O. `_scan_task_body` продолжает ждать этот поток через asyncio.to_thread.

Независимое воспроизведение: VERIFY_TIMEOUT_SECONDS=0.01; только чтение реального source-файла обёрнуто threading.Event (остальной путь настоящий). После 0.08 с — восьми сроков — **поток restore_rehearsal всё ещё заблокирован**. Лишь после внешнего снятия блокировки возвращается timed_out=True. Тест корректно завершён, фоновых потоков не оставлено. Существующая проверка с истёкшим временем между кусками не проверяет зависшую операцию.

Рекомендация: вынести работу в управляемый отдельный процесс с внешним deadline и ограниченным ожиданием завершения; не считать отмену asyncio.to_thread остановкой операции. Обеспечить ограниченное число процессов, cleanup и освобождение рабочего цикла при зависшем I/O, не запускать новые проверки поверх старых. Приёмка: транспорт чтения не разблокируется тестом — родитель всё равно возвращает timeout в заданный срок, дальнейший цикл приложения работает; временные ресурсы учитываются/убираются по завершении.

## L01 — P1: результат старой проверки делает новую непроверенную копию зелёной

Место: `monitoring.backup_section`, `backup_health.due_for_verification`.
Отчёт выбирает newest из списка файлов и last_check из общей истории, но не проверяет, что проверялась именно эта копия. Нет проверки возраста результата проверки или изменения файла после неё. Суточный throttle тоже не учитывает появление нового файла.

Независимое воспроизведение на настоящей временной БД: создать корректную копию через database.backup_database, успешно выполнить verify_backups_if_due; затем добавить более новый файл latest-bad.db с текстом вместо SQLite. Результат: **backup_section.status='healthy', newest='latest-bad.db', verify_backup(newest).ok=False, due_for_verification=False**. Более новый mtime задавался явно, без зависимости от порядка файловой системы. Сеть не использовалась.

Рекомендация: связывать проверку с конкретной неизменной копией и её идентичностью (имя/версия/размер/время изменения либо digest); проверять давность проверки. Новая или изменённая копия должна быть unknown/pending и не наследовать успешную проверку предыдущей. Отдельно можно показать последнюю подтверждённую пригодную копию. Приёмка: старый успешный результат + новый повреждённый файл; замена содержимого под прежним именем; свежий файл + просроченный check; новый файл в пределах 24 часов. Ни один не получает ложный healthy.

## L03 — P2: заявленное ограничение времени проверки не действует

Место: `backup_health.VERIFY_TIMEOUT_SECONDS`, `restore_rehearsal`, `verify_backup`; ожидание verify_backups_if_due в `web.server._scan_task_body`.
VERIFY_TIMEOUT_SECONDS=120 нигде не используется. Копирование файла, integrity_check и COUNT(*) не ограничены общим deadline; sqlite connect timeout ограничивает ожидание блокировки, а не продолжительность запросов. Сканирование ожидает завершения этой работы через asyncio.to_thread до завершения собственного цикла. Медленный диск/большая база могут удерживать цикл неограниченно долго; отмена asyncio-await сама по себе не останавливает поток.

Контролируемая проверка: задать VERIFY_TIMEOUT_SECONDS=0.001 и обернуть реальную shutil.copy2 задержкой 0.05 с. Репетиция завершилась **restored=True за 0.062 с**, без timeout. Это проверка неприменения настроенного предела, а не нагрузочный замер.

Рекомендация: применить реальный общий срок исполнения с прекращением файловых/SQLite-операций (например, изолированный процесс с управляемым завершением и cleanup; для SQL — progress handler). Записывать timeout как неуспех и освобождать цикл; не допускать накопления зависших проверок. Приёмка: блокирующее копирование/SQL, timeout, очистка временных файлов и продолжение рабочего цикла; также проверить отказ создания временного каталога при заполненном диске.
