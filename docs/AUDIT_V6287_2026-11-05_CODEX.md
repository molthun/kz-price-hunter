## F1 · P1 · Путь отчёта не защищён от перезаписи самой БД; отчёт пишется после commit

**Код:** `scripts/recompute_gpu_models.py:87–95`; фиксация пачек — `:62–74`.

Параметры `--db` и `--report` не проверяются на совпадение. После чтения и закрытия
соединения `Path(args.report).write_text(...)` открывает целевой файл с усечением.
Если указать один файл обоим параметрам, утилита заменяет SQLite-базу JSON-отчётом.
**Флаг `--apply` для этого не нужен:** обычный заявленный dry-run тоже разрушает БД
и завершается кодом 0. Подтверждено на созданной аудитором временной SQLite:
заголовок файла становится JSON, повторный `PRAGMA quick_check` даёт
`DatabaseError: file is not a database`.

У того же порядка операций есть второй дефект: при `--apply` изменения фиксируются
до попытки записи отчёта со старыми значениями. Если родительской директории отчёта
нет, процесс завершается с FileNotFoundError, но model уже изменён, а отчёта для
отката нет. Это также воспроизведено на временной БД.

Корректный dry-run с отдельным доступным файлом отчёта проверен: содержимое БД
по SHA-256 не меняется. Следовательно, проблема именно в обработке назначения
отчёта, а не в самой возможности выполнить dry-run.

**Приёмка:**

- Отклонять совпадение БД и отчёта до любого открытия отчёта на запись,
  включая эквивалентные пути, symlink и существующие hardlink.
- Надёжно сохранить план со старыми значениями до первой фиксируемой правки;
  недоступность отчёта должна оставлять БД неизменной.
- Для раздельных пачек явно отражать реально выполненные изменения и частичную
  ошибку, чтобы повторный запуск и откат оставались проверяемыми.
- Регрессии CLI: обычный dry-run, одинаковые пути/алиасы, недоступный отчёт,
  успешный apply и ошибка после части пачек. Во всех проверках — временные данные.

## F2 · P2 · Слитный TiSuper допускается regex, но отсутствует в словаре нормализации

**Код:** `catalog_classifier.py:1045–1053`.

Regex содержит `ti\s*super`: он принимает и `Ti Super`, и `TiSuper`. Затем ключ
для словаря строится заменой существующих пробелов. Для слитного случая получается
`tisuper`, а в `_GPU_SUFFIX_NAMES` есть только `ti super`. Возникает KeyError.

**Независимые случаи:** `RX 9070 TiSuper`, `RTX 4060 TiSuper`, `GTX 1650 TiSuper`
вызывают `KeyError('tisuper')` в `canonical_gpu_model()`. Название может быть
ошибочным или неизвестным — для воспроизведения не требуется считать его реально
существующей моделью видеокарты. Парсер недоверенной строки всё равно не должен падать.
Исключение может сорвать вызывающий поиск, построение фасета или план перерасчёта.
Частоту такого входа на настоящих данных аудит не измерял.

**Приёмка:** привести все допускаемые regex варианты к одному ключу словаря;
проверить TiSuper, Ti Super, несколько пробелов и табуляцию у семейства без отдельного
готового правила. Неизвестный вариант должен обрабатываться без исключения и без
молчаливого превращения в базовую модель. Существующие проверки 9070/GRE/XT,
7900 GRE/XT/XTX и 4070 Ti Super должны продолжить проходить.

## Подтверждённые улучшения и ограничение данных чипсета

- `RX 9070 GRE` теперь даёт отдельную `Radeon RX 9070 GRE`.
- Нормализация `chipset` на полном названии с GRE даёт тот же результат.
- Прежние независимые R01–R04, остаток с пробелами и матрица **144 GPU-товаров**
  продолжают проходить. Существующая SQL-оптимизация не менялась.
- Авторские тесты подтверждают узкое исправление model, пропуск не-уточнений и
  повторный запуск без новых model-правок. Это не отменяет дефектов CLI F1.

Дополнительная проба F3 показывает границу перерасчёта: если у GRE уже записан
title-derived `chipset='Radeon RX 9070'`, `plan_changes()` исправляет model, но
chipset остаётся базовым; фильтр этого атрибута продолжает включать GRE.
Причина — нормализация только прежнего значения chipset, без повторного извлечения
из названия. Это искусственно подготовленное состояние; наличие таких строк на
живой БД и их происхождение данным аудитом не установлены. Поэтому F3 сохранена
как ограничение и рекомендация проверки копии, **не посчитана отдельным блокирующим P2**.

При подготовке стенда проверить согласованность model/derived chipset. Если найдены
старые ошибочные производные факты, спланировать их обновление по проверенному
названию. Подтверждённые факты источников и ручные решения не перезаписывать молча;
противоречия требуют отдельного разбора.
