## A. Блокирующие

### A1. Магазины с кириллическим названием сливаются в одного продавца

`resolve_seller_and_channel_meta` ищет подстроку по `KNOWN_SELLER_MAPPINGS`. Для «Вкусмарт» в таблице
есть только латинский ключ `vkusmart`, которого в названии нет. Срабатывает запасной путь:

```python
slug = re.sub(r"[^a-zA-Z0-9_]+", "_", cleaned).strip("_") or "unknown_seller"
```

Регулярное выражение вырезает **всю кириллицу**, строка становится пустой, и slug превращается
в `unknown_seller`.

Проверено на реальном реестре (37 магазинов) и на вымышленных названиях:

```
«Вкусмарт»          → unknown_seller
«Технопарк Алматы»  → unknown_seller
«Сеть Ромашка»      → unknown_seller
«Магазин у дома»    → unknown_seller
```

**Последствия.** Сегодня это ~876 предложений «Вкусмарта» под чужим продавцом. Завтра — любой новый
магазин с кириллическим названием попадает в **того же** `seller_unknown_seller` и тот же
`chan_unknown_seller_website`, то есть разные торговые сети становятся одним продавцом. Это прямо
противоречит правилу этапа 2 плана: «Нельзя автоматически объединять продавцов только потому, что
названия похожи» — здесь они объединяются даже без похожести. Падения не происходит: ключи
предложений остаются уникальными, данные просто молча смешиваются.

**Рекомендация.** Резолвить продавца по ключу реестра (`SHOP_REGISTRY` / `config.SHOP_KEYS`), а не по
отображаемому названию: ключ уже стабилен, латиничен и уникален. Сопоставление по названию оставить
как запасное. Если запасной путь не смог построить осмысленный slug — отказ и запись в телеметрию,
а не общий `unknown_seller`. Добавить тест, который проходит по всему реестру и требует, чтобы у
каждого магазина был свой slug (ровно та проверка, которой этот дефект и найден).

### A2. Сбой Dual-Write не виден никому

В обеих точках интеграции:

```python
except Exception as e:
    logger.debug("Dual-write v2 failed for product %s: %s", pid, e)
```

`logging.basicConfig` в приложении не вызывается нигде (только в `scripts/migrate_v1_to_v2.py`),
поэтому уровень DEBUG **не печатается вообще**. Счётчика неудач нет, события телеметрии нет,
в мониторинге ничего нет.

Проверено опытом: с намеренно сломанным адаптером `save_or_update_product` отработал штатно,
исключение наружу не вышло, и получилось `legacy products: 1, v2 offers: 0` — **без единого признака,
что что-то не так**.

**Последствия.** Сам принцип Fail-Open выбран правильно: сбой новой модели не должен ронять сбор.
Но в нынешнем виде v2 может расходиться с v1 неограниченно долго и незаметно. Хуже того, это
обесценивает будущую сверку: shadow-сравнение покажет согласие на тех записях, которые дошли,
и ничего не скажет о тех, которые не дошли.

**Рекомендация.** Оставить Fail-Open, но сделать отказ наблюдаемым: считать неудачи (успешно/не
успешно за обход), писать событие через `telemetry.record_system_error` — механизм в проекте уже есть
и используется именно для этого, — и показать счётчик в Центре мониторинга рядом с прочими
разделами. Пока v2 не стал основным, достаточно счётчика и события; отдельный статус не нужен.

## B. Существенные

### B1. Нормализация состояния даёт ложное «б/у» на обычных русских словах

`Condition.normalize` проверяет вхождение подстроки `"БУ"`:

```
«БУМАЖНЫЙ БЛОК» → USED
«Тумбу для ТВ»  → USED
```

Достаточно любого слова с этими двумя буквами. Сегодня ни один из 37 источников поле состояния не
передаёт, поэтому дефект спит. Он проснётся на этапе 4 (б/у рынок), где по плану «Б/у не смешивается
с новыми товарами в одной лучшей цене» — то есть ровно там, где ошибка стоит дороже всего.

**Рекомендация.** Сравнивать по границам слова (`\bб/?у\b`, `\bused\b`), а не по подстроке.
Добавить в тесты именно эти строки-ловушки.

### B2. Отсутствие данных считается более достоверным, чем сами данные

```
None       → NEW          (нет данных — считаем новым)
«новый»    → UNKNOWN      (магазин прямо сказал — считаем неизвестным)
«нет данных» → out_of_stock  (незнание превращается в факт «нет в наличии»)
None (наличие) → in_stock
```

Асимметрия перевёрнута: молчание источника даёт уверенный ответ, а явный ответ — неуверенный.
Это инверсия принципа, на котором стоит весь проект: «отсутствие наблюдения — это неизвестно,
а не в порядке».

Сегодня значения по умолчанию удобны: все 37 источников продают новое и в наличии, в legacy-модели
поля состояния нет вовсе. Опасными они станут на этапах 4 и 5 (б/у, доски объявлений, Instagram),
где неизвестное состояние — обычное дело.

**Рекомендация.** Признать умолчания осознанным допущением текущей волны и записать это в карточку
этапа 4 как обязательный к пересмотру пункт; распознавать «новый»/«new» явно; «нет данных» не
переводить в `out_of_stock`.

### B3. `get_price_history(limit)` возвращает самые старые записи

```sql
ORDER BY observed_at ASC LIMIT ?
```

Проверено: при трёх наблюдениях (январь, май, сентябрь) `limit=2` вернул январь и май. Для графика
цены или «недавней динамики» нужны последние. Потребителей пока нет, поэтому это не влияет на
сегодняшнюю работу, но контракт метода обманчив и выстрелит на этапе 26 (Price History 2.0).

**Рекомендация.** Выбирать `ORDER BY observed_at DESC LIMIT ?` и разворачивать результат, либо явно
назвать метод «с начала истории» и добавить отдельный метод для последних наблюдений.

### B4. «Parity v1/v2 подтверждено» — утверждение сильнее проверки

`test_shadow_read.py` вставляет **два** синтетических товара и сравнивает `MIN(цена)`. Это проверка
исправности проводки на одном идеальном случае, а не сверка паритета. В сочетании с A2 она прошла бы
и в том случае, если бы в v2 не попало подавляющее большинство товаров: достаточно, чтобы дошли эти
два.

**Рекомендация.** Либо смягчить формулировку в карточке до «проверен happy-path проводки», либо
сделать настоящую сверку: на снапшоте рабочей БД сравнить количество товаров и лучшие цены по
выборке канонических ключей между v1 и v2 и записать расхождение числом.

### B5. Счётчик миграции не умеет сообщать о пропусках

`sync_legacy_product_to_v2` возвращает `False`, если цена `<= 0` или `> 10 000 000`. В
`scripts/migrate_v1_to_v2.py` возвращаемое значение игнорируется, а `stats["products_migrated"]`
увеличивается на размер пачки целиком. Значит, «перенесено 42 899» означает «прочитано 42 899».

В рабочей БД товаров дороже 10 млн **ноль**, поэтому отчёт этапа сегодня точен. Но при появлении
таких позиций отчёт останется зелёным, а данные в v2 будут неполными.

**Рекомендация.** Считать возвращаемое значение и выводить пропуски отдельной строкой с причиной.

## C. Замечания и наблюдения

- **C1.** Порог `price > 10_000_000` отбрасывает предложение молча. Локально таких нет; на проде
  (124 832 товара, включая технику MasterOK и мебель) не проверялось. Стоит либо поднять порог,
  либо считать отброшенные.
- **C2.** Upsert продавца обновляет только `updated_at`: имя, домен и телефон после первой записи
  не меняются никогда. При переименовании магазина v2 останется со старым именем.
- **C3.** Индексы `idx_sellers_slug` и `idx_canonical_products_key` дублируют неявные индексы,
  созданные ограничением `UNIQUE`. Лишняя запись при каждом обновлении.
- **C4.** `REFERENCES` в схеме декоративны: внешние ключи SQLite в проекте выключены (известный
  отложенный пункт). Осиротевшие предложения возможны и ничем не отслеживаются.
- **C5.** `BaseRepository.__init__` меняет `row_factory` у **переданного** соединения. Для общего
  соединения приложения это побочный эффект за пределами репозитория.
- **C6.** `count_offers` читает колонку по имени `"COUNT(*)"`. Надёжнее `COUNT(*) AS cnt`.
- **C7.** Upsert продавца и канала выполняется для **каждого** товара, хотя они постоянны в пределах
  магазина. На производительность не влияет (см. ниже), но шумит в журнале транзакции.

## D. Проверено особо и признано корректным

Эти места выглядели подозрительно при чтении, но проверка их оправдала — фиксирую, чтобы к ним
не возвращались.

- **`executescript` в `_create_schema`.** Он делает неявный COMMIT, но вызывается в собственном
  блоке только с DDL и **до** `run_migrations`, у которых свои `BEGIN IMMEDIATE`. Гарантии
  транзакционности миграций не нарушены.
- **История цен пишется только при изменении.** Это не расхождение с v1: legacy
  `_record_observation` ведёт себя так же. Проверено: четыре сохранения (1000, 900, 900, 900) дали
  по 2 записи и в `price_observations`, и в `offer_price_history`.
- **Уникальность предложений.** `offer_id = off_<legacy_id>` и `external_sku = legacy_id`
  согласованы с индексом `uq_offers_channel_sku`, потому что legacy-идентификаторы уже содержат
  префикс магазина. Конфликта между `ON CONFLICT(id)` и уникальным индексом не возникает.
- **Откат флагом.** `DUAL_WRITE_V2=0` действительно прекращает запись в v2 (проверено: пачка,
  записанная с флагом `0`, не создала ни одного предложения).
- **Производительность Dual-Write.** Замер на 3000 товаров: 0.23 с → 0.33 с, **×1.5**. В пересчёте
  на полный обход прода (124 832 товара) это **около +5 с** на цикл. Препятствием не является.

## Новые замечания этого круга

### N1. Сопоставление по подстроке всё ещё объединяет разных продавцов (средний)

Шаг 4 резолва (`KNOWN_SELLER_MAPPINGS`) по-прежнему ищет вхождение подстроки. Проверено:

```
«Форте Банк»   → fortemarket  (канал forte)
«Мир Каспия»   → kaspi        (канал kaspi)
«Alser Plus»   → alser
«Мечта Мебель» → mechta
```

Для форматов одной сети («Магнум Экспресс») это желаемое поведение, но «Форте Банк» и «Мир Каспия»
— посторонние организации, склеенные по совпадению букв. Сегодня таких магазинов в реестре нет,
поэтому влияния на данные нет. Замечание станет важным на этапе S2-E05 (Seller Discovery), где в
систему начнут попадать произвольные названия — то есть ровно там, где правило «не объединять
продавцов по похожести названий» и должно работать.

Рекомендация: на шаге 4 требовать совпадения по границам слова, либо применять его только к
известным 37, а произвольные названия сразу отправлять на транслитерацию (шаг 5) — она уже даёт
различимые и безопасные slug.

### N2. Тест A2 не проверяет телеметрию, хотя так называется (средний)

`test_dual_write_failure_telemetry_and_stats` проверяет только `get_dual_write_stats()`. Событие
телеметрии не проверяется ни разу. При этом вызов обёрнут в `except Exception: pass`, то есть любая
поломка (переименование константы, смена сигнатуры) отключит телеметрию **молча** — и ни один тест
этого не заметит.

Рекомендация: в тесте сбросить буфер (`telemetry.flush()`) и убедиться, что событие
`dual_write_error` есть в `telemetry_events`; либо считать неудачи самой телеметрии, а не гасить их
пустым `pass`.

### N3. Резолв по системному ключу в рабочем пути не срабатывает (низкий)

`sync_legacy_product_to_v2` передаёт `product.get("shop_key")`, но ни один скрапер и ни одна точка
конвейера не кладёт `shop_key` в словарь товара. Значит, шаг 1 сегодня мёртв, а продавец
определяется по отображаемому имени (шаг 3). Работает верно, но самое надёжное звено не
используется; при переименовании магазина slug изменится и продавец «переедет».

Рекомендация: передавать ключ магазина в точке вызова — он там известен.

### N4. Мелочи

- Запасной slug из хеша даёт `seller_<hash>`, а затем `seller_id = f"seller_{slug}"` → `seller_seller_<hash>`.
- В режиме `--dry-run` миграция считает все строки перенесёнными: пропуски не моделируются.
- «уценк» отнесено к `USED`. Уценённый товар часто новый с повреждённой упаковкой (раздел «Уценка»
  у MasterOK — именно такой). На этапе S2-E04 это исключит их из «лучшей цены на новое».
