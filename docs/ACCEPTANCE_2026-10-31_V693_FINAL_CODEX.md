## V693-01: сохранность каталога и безопасная очистка — принято

Код: `scripts/scrub_social_content.py:50–110`.

- Вместо `_zero_out_residual_bytes` используются только SQLite UPDATE/secure_delete/checkpoint/VACUUM. Произвольного чтения/перезаписи файлов больше нет.
- Прежний независимый сценарий, в котором текст удаляемого поста совпадает с **Samsung Galaxy S24** в canonical_products, проходит. Название перечитывается новой SQLite-сессией и сохраняется; текущие поля observation очищены.
- Новая независимая `acceptance.py` проверяет одновременно короткое совпадающее название, overflow-пост, base64-изображение, разрешённую ссылку, integrity/FK и согласованный SQLite backup. После завершённой offline-очистки уникальные маркеры отсутствуют в файлах БД/WAL и новой копии backup, название/технические поля сохранены.
- При открытом старом WAL-снимке результат содержит **physical_complete=False, reason=wal_busy**. Текущий SQL очищен, но старые страницы не переписываются за спиной SQLite. Независимый тест намеренно подтверждает наличие удерживаемого маркера на этой стадии.
- После rollback читателя повторный `--apply` с **0** новых грязных строк возвращает **physical_complete=True**, маркеры исчезают, данные каталога остаются корректны.
- Настоящий CLI в дочернем процессе возвращает **exit 3** при занятом WAL и **exit 0** после снятия читателя. Dry-run не меняет данные/хэш основного файла и возвращает physical_complete=None.
- Ошибки checkpoint/VACUUM/integrity не превращаются в физический успех; эти сценарии также покрыты авторскими тестами общего suite.

Эксплуатационная граница теперь прямо описана: запуск по решению владельца при остановленном приложении; незавершённость требует закрыть удерживающие соединения и повторить процедуру. Старые резервные копии, снимки файловой системы и остатки на носителе скрипт не очищает. Аудитор не запускал его на рабочих данных.
