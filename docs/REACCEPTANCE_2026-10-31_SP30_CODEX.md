## Остаток SP30-04 · P2 · Неполные измерения ещё могут означать «SQLite достаточно»

Места: `domain/scale_bench.py:91–98,110–139`; `scripts/benchmark_scale.py:79–80`; `web/templates/monitoring.html:1929–1932`.

1. Для search_p95=NaN функция теперь правильно возвращает decision=NOT_MEASURED, но одновременно **is_sqlite_sufficient=true**. CLI выбирает зелёный значок по этому boolean. Новый regression-тест проверяет строку decision, но не противоречащий ей boolean.
2. Проверка валидности ограничена p95. С нормальным p95=20 мс, но backup_duration_s=NaN либо write_latency_1k_ms=NaN получается **STAY_ON_SQLITE**, и NaN назван нормальным значением в reasons. Аналогично принимается отрицательный размер БД. При target=100k и actual_offers=0 или 500 оценщик тоже подтверждает эту контрольную точку. Это воспроизведения контракта оценщика, не утверждение о том, что штатный CLI уже получил NaN на стенде.
3. Шаблон мониторинга всегда рисует зелёный значок ✅, в том числе для **NOT_MEASURED и ERROR_NO_SCHEMA**. Если scale_level не передан, шаблон по-прежнему подставляет **HEALTHY_SQLITE / «SQLite полностью справляется с объёмом»**. Chrome-проверка реального renderPlatformV2 сохранила все три результата. Backend больше не отдаёт безусловное HEALTHY_SQLITE, но недостоверный fallback в интерфейсе остался.

**Критерий закрытия:** UNKNOWN/NOT_MEASURED/ERROR не должны давать положительный boolean или зелёный success-индикатор; для неизвестного результата использовать null/явный статус, не подменяя его утверждением о необходимости миграции. Проверять конечность, знак и наличие всех метрик, участвующих в решении, а также соответствие объёма заявленной контрольной точке. На отсутствующем scale_level показывать отсутствие данных. Добавить отрицательные тесты для каждого поля и реальный DTO → UI для неизвестного/ошибочного состояния.

## Остаток SP30-06 · P2 · Замеры всё ещё не соответствуют заявленной полноте

Места: `domain/scale_bench.py:281–310,317–362`; `scripts/benchmark_scale.py:69–74`.

- **Размер истории без индекса.** dbstat-запрос включает только таблицу offer_price_history, исключая её PK-индекс. На 100k таблица — **11 214 848 байт**, индекс — **5 787 648 байт**, всего **16,21 МиБ**, тогда как отчёт показывает **10,70 МБ**. История измеряется неполно относительно исходного требования «таблица и индексы».
- **Непомеченные оценки.** При недоступности dbstat остаются rows*256 и rows*64. В DTO нет поля методики/точности/ошибки, CLI подписывает их как обычные измеренные размеры. В аудиторском сценарии отказа dbstat этот путь воспроизведён.
- **Выдуманная память.** При ошибке resource.getrusage возвращается прежняя константа **45,0 МБ**. Отказ измерителя воспроизведён обёрткой: значение выглядит измеренным. На штатном пути используется ru_maxrss — пиковая память процесса, хотя CLI называет её RSS без уточнения.
- **Остальные критерии первичного аудита не реализованы.** «Холодный старт» по-прежнему измеряется до наполнения базы; поиск — десять последовательных запросов; нет сканирующих/пишущих конкурентов во время backup, измерения scan concurrency, проверки результата поиска/доли ошибок или сохранения протокола этих нагрузок. Вызов SQLite backup API после commit корректен для проверенного изолированного сценария и завершился за 0,092 с. Отсутствие блокировок под конкурирующими сканами этим не доказано. Точки 500k/1m/5m/10m не запускались.

**Критерий закрытия:** включить относящиеся к истории индексы; явно передавать measured/estimated/unavailable и методику каждой метрики. При невозможности измерить память — unavailable, без числовой заглушки; различать peak/current RSS. Измерять запуск заполненной базы. Добавить ограниченный по времени воспроизводимый сценарий сканов/писателей и backup с проверкой целостности копии, ошибок и задержек писателей; отражать объём выборки и ограничения. Контрольные точки, которые не проводились, оставить явно непринятыми. Если такой охват откладывается, изменить статус этапа и передачу на частичную реализацию, а не заявлять SP30-06 закрытым.
