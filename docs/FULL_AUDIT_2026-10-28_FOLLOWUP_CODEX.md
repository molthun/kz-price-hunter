# Полный повторный аудит после запуска стенда — 28.10.2026

Исполнитель: Codex. Поручение: «Были изменения, прод зависал, создали стенд для выявления
проблем, нужен полный аудит проекта». Проверка независима от авторов последних исправлений.

## Решение

**Полную стабилизацию не принимать: подтверждены 9 остаточных дефектов (C01–C09),
из них C01–C05 и C08 — P1, C06–C07 — P2, C09 — P3.** Основной риск — потеря результатов
сканирования с последующим ложным сигналом успешного завершения. Зелёные тесты этот риск
не перекрывают. Требуется отдельное поручение на исправления; приложение в ходе аудита не исправлялось.

При этом исправления действительно улучшили систему: синхронное получение аренды вынесено
из цикла событий, Redis-команды ограничены временем, старую Redis-очередь дочитывают после
fallback, сортировка обычных доступных предложений исправлена, идентичность V2 доходит до
watches, ложное снижение между неизменными предложениями устранено. C-TLS-01 принимается
в заявленном объёме: оба исправленных пути работают в Linux-контейнере с проверкой TLS.

**Единственная точная причина исторического зависания NAS этим аудитом не установлена.**
Воспроизводимые механизмы отказа приложения найдены, но без закрытой диагностики прода,
замеров хоста/диска во время зависания и испытаний на сопоставимой копии данных нельзя
приписать тот инцидент одному из них. Версия HTTP также не удостоверяет digest образа.

## 2. Подтверждённые дефекты

### C01 · P1 · Очередь теряется при перезапуске, а ACK не переживает смерть процесса

Места: `queue_service.py:51–59,277–315`, shutdown в `web/server.py:3384` и далее.

Redis запущен с `--save '' --appendonly no`; его данные не сохраняются. Рабочее извлечение
использует `LPOP`, после которого задача существует только в Python. `_in_flight` хранит
`id(item)`, не данные и не устойчивый идентификатор. ACK удаляет этот локальный маркер.
Отмена воркера делает nack в память, которая также исчезает при остановке процесса.

На настоящем Redis в отдельном контейнере стенда: после dequeue новый менеджер получает
`null`, старый хранит только `in_flight=1`; после перезапуска Redis `before=1 → after=0`.
Это два независимых окна потери: ожидающие пачки и уже взятые в обработку.

Исправление: устойчивый журнал принятых задач и атомарное перемещение pending → processing,
возврат незавершённых задач после рестарта, ACK после фиксации всех обязательных эффектов.
Варианты реализации выбирать по требованиям: SQLite spool/outbox либо persistent Redis
с надёжным processing/consumer protocol. Одного включения AOF недостаточно для окна после LPOP.
Приёмка: kill процесса между получением/записью/ACK и restart контейнера; все подтверждённо
принятые task ID восстановлены, повтор обработки не дублирует историю и задания уведомлений.

### C02 · P1 · Исчерпанные повторы превращаются в «очередь записана»

Места: `queue_service.py:317–350`, `web/server.py:289–311,2217–2226`.

После трёх повторов задача уходит в `dead_letter_queue`. Ни qsize, ни wait_drained,
ни readiness эту очередь не учитывают; постоянного хранилища или восстановления нет.
Воспроизведение: dead_letters=1, queue_size=0, drained=true, readiness=200.
Дополнительно проверен настоящий `_scan_shop_categories` с настоящим воркером и устойчивой
ошибкой записи: **shop_status=complete, saved=0, dead_letters=1**.

Исправление: хранить исход каждой принятой задачи; ошибка записи должна доходить до статуса
своего обхода, dead-letter — учитываться в мониторинге и сохраняться с процедурой повторения.
Барьер завершения должен ждать задачи конкретного scan/shop, а не только глобальную пустоту.
Приёмка: постоянная блокировка БД не даёт complete при нуле записей; readiness/диагностика
показывают потерянную производительность и неразобранные ошибки, а restart их не скрывает.

### C03 · P1 · Переполненный fallback молча отбрасывает принятую сканером пачку

Место: `queue_service.py:271–275`, вызов `web/server.py:2155`.

После 5 секунд ожидания memory_queue.put выводится сообщение и возвращается None — ровно
как при успешном enqueue. Сканер уже увеличил collected/total_scanned и не получает ошибки
приёма. Воспроизведение с maxsize=1: первая и вторая enqueue вернули null, очередь содержит
одну пачку, вторая исчезла через 5.0 с.

Исправление: явный результат принятия/исключение и ошибка категории либо устойчивое сохранение
для последующего приёма. Счётчики received/accepted/committed должны иметь разный смысл.
Приёмка: медленный писатель + полный fallback не теряют пачку незаметно; complete невозможен
при неподтверждённом enqueue; память ограничена и число отброшенных задач наблюдаемо.

### C04 · P1 · Ошибки reconcile/scan log проглатываются до ACK

Места: `web/server.py:1832–1864,1880–1883`.

После сохранения товаров `_execute_queue_item` отдельно вызывает reconcile_source и
record_source_scan, но ловит их исключения и возвращает успех. Рабочий цикл подтверждает
задачу. Результат: устаревшие товары могут оставаться активными, история качества/полноты
может отсутствовать, повтор не выполняется.
Проверен реальный воркер с OperationalError в reconcile: queued=0, in_flight=0, retries=0,
drained=true. Телеметрия ошибки не является восстановлением обязательной операции.

Исправление: определить обязательные атомарные части task и повторяемые стадии; обязательная
ошибка должна запрещать ACK. Повтор стадии должен быть идемпотентным, чтобы уже записанные
цены/наблюдения не дублировались. Приёмка: отдельно уронить товары, reconciliation и scan log;
после восстановления все стадии завершены, complete и ACK появляются только после этого.

### C05 · P1 · Fencing подтверждает отброшенные задачи и не различает владельцев

Места: `web/server.py:1818–1820,1881–1883,2294`, payload `queue_service.py:252–260`.

При lost=True обработчик просто возвращает None, после чего воркер выполняет ACK.
Проверено: saved=0, queued=0, drained=true. При следующем запуске глобальный lost снова False;
payload не содержит lease generation/owner, а обработчик не сверяет task с текущей арендой.
Старая задача после сброса флага принимается: old_task_saved=1.

Исправление: lease token/generation в задаче и транзакционная проверка права записи,
отдельный исход stale/rejected, не успешный ACK. Задачи потерявшего аренду обхода должны
разбираться явно. Проверка одного флага до первого await не обеспечивает fencing во время записи.
Приёмка: два независимых процесса/владельца, потеря аренды между стадиями записи и её повторное
получение; старое поколение не пишет и не считается успешно сохранённым.

### C06 · P2 · Пользователь с cookie ждёт общий пул даже на /api/live

Место: `auth.py:187–189`; аналогично под влияние middleware попадает остальной HTTP API.

SQLite lookup сессии перенесён в asyncio.to_thread, то есть в тот же default executor,
который обслуживает тяжёлые скраперы. Выделенный run_db это место не изолирует.
Даже заведомо неверная cookie заставляет ждать пул до вызова live_handler.
При занятом общем пуле запрос /api/live с cookie не завершился за 200 мс; после освобождения
пула завершился сразу. Это воспроизведение зависимости, не замер задержки NAS под реальной волной.
Docker HEALTHCHECK обычно идёт без cookie и этим конкретным сценарием не задерживается.

Исправление: bypass auth для публичного liveness; отдельный ограниченный пул и сроки ожидания
сессионных/коротких HTTP-операций. Проверить остальные asyncio.to_thread на HTTP-пути.
Приёмка: занять реальный default pool при заданных CPU-лимитах; live без cookie и с валидной/
невалидной cookie сохраняет оговорённую задержку, кабинет и короткие API отвечают либо явно
ограниченно отказывают, а не ждут все сетевые таймауты скраперов.

### C07 · P2 · Просроченный кандидат вытесняет доступный товар перед LIMIT

Место: `repositories/search_repo.py:140–154,190–202`.

Доступность добавлена в подзапрос цены ORDER BY, но отсутствует в EXISTS, отбирающем продукты.
Для товара только с expired/offline offers MIN возвращает NULL; при ASC этот кандидат идёт
перед числовой ценой. Дальнейшая агрегация уже не возвращает пропущенного кандидата.

Воспроизведение: p0 имеет только expired price=1, p1 доступен за 100. limit=1 возвращает
только p0 с min_price=null и purchasable=false; limit=50 первым возвращает p1 за 100.
Предыдущая регрессия B10 проверяла товар, у которого наряду с expired оставалось живое
предложение, и этого случая не покрывала.

Исправление: согласовать политику видимости, SQL-кандидатов и ключ сортировки; если архивные
товары нужны в поиске, сортировать доступные перед ними до LIMIT. Также согласовать freshness,
price>0, UTC TTL и выбор цены в SQL с окончательной агрегацией.
Приёмка: expired-only, out_of_stock-only, stale-only и смешанные каналы; первая доступная
цена не меняется от limit=1/50, фильтры города и состояния применены на обоих этапах.

### C08 · P1 · Watches уведомляют о недоступном просроченном предложении

Место: `database.py:3150–3156`, правила `watches.py:302–314`.

watched_offers подставляет is_available из o.is_active. Наличие out_of_stock и expires_at
не передаются/не проверяются; активная строка превращается в доступное предложение.
На сохранённой V2-строке с availability=out_of_stock и expires_at=2020, price=100:
input_available=1, поля expiry/availability отсутствуют; настоящее наблюдение target_price=150
создало notification_events=1. Реальная отправка Telegram не выполнялась.

Исправление: единая политика purchasability для поиска, витрины и уведомлений, учитывающая
TTL, состояние предложения/канала/продавца и свежесть. Для back_in_stock сохранить корректный
переход недоступно → доступно. Приёмка: тесты через сохранение Offer → watched_offers →
evaluate_watches → outbox для expired/out_of_stock/stale/disabled и повторного появления.

### C09 · P3 · Граница TTL различается между поиском и витриной

Место: `domain/search_core.py:38`, сравнить `domain/seller_showcase.py:27` и
`domain/social_content.py:82`.

При now == expires_at SearchCore возвращает expired=false (`>`), витрина — true (`>=`).
Наблюдения content также используют >=. Проверка воспроизводится с одним фиксированным now.
Кроме того SearchCore передаёт now в repository, но не в freshness/offer_expired агрегации;
контролируемое время разных стадий требуется унифицировать.

Исправление: общий UTC helper и единый передаваемый now. Приёмка: -1 мкс, ровно TTL, +1 мкс,
naive/Z/offset и единое состояние во всех представлениях.

Операционные ограничения стенда:

1. CPU/RAM-лимиты повторяют бюджет, но NVMe и отсутствие прочей нагрузки NAS не повторяют
   задержку диска, конкуренцию DSM и cgroup/host pressure. Для причинной связи нужны замеры
   CPU throttling/PSI, I/O и SQLite transaction latency, а не один здоровый снимок.
2. В реестре копия производственной базы ещё не перенесена. Текущая база появилась от
   настоящих обходов; равенство размера, индексов, watches/outbox и истории продовой базе
   не подтверждено. Нельзя закрыть нагрузочную приёмку пустой очередью на ней.
3. TEST_STAND разрешает внешний адрес, но комментарии compose и старые карточки запрещают
   внешнюю публикацию. Привести политику к фактическому состоянию. Проверено, что функции
   TLS работают; отдельно не проверены DSM/firewall/внешняя достижимость backend-порта.
4. Инструкция scp копии сразу в stand-data/prices.db не требует остановить уже работающий
   контейнер. Нельзя заменять основной файл живой WAL-базы, оставляя её соединения и журнал.
   Нужны остановка потребителя, резервирование старого комплекта, staging, integrity_check,
   установка согласованной копии и последующий запуск. В аудите перенос не выполнялся.
5. Стенд сам обходит реальные магазины. Частоту, сценарии и внешние побочные эффекты следует
   контролировать; тесты отказов проводить на синтетических источниках. Не копировать рабочие
   sessions/Telegram outbox и личные данные в публичный стенд без очистки/изоляции доставки.

План проверки причины зависаний: согласованная обезличенная копия → synthetic/replay источники
→ одновременно сканер/короткие API/авторизация → управляемая блокировка писателя и занятый
пул → рестарты только изолированной копии → несколько полных волн и измерение RSS после волн.
До теста определить критерии (например live p99 <250 мс, короткий API <2 с или явный 503,
0 потерянных принятых task ID, 0 повторных заданий уведомления); значения согласовать с владельцем.
Диагностику прода снять в момент симптома с problems и сопоставить с временными метками хоста.

## 4. Архитектура, безопасность и выпуск

Single DB-Writer сериализует задачи скраперов, но не все записи приложения: telemetry,
сессии, фоновые AI/watch/settings и maintenance работают отдельно. Поэтому архитектурное
обещание «полного отсутствия database is locked» в docstrings не подтверждено и некорректно.
WAL + synchronous=NORMAL + ограниченные пулы уменьшают задержки, но не заменяют протокол
сохранения, корректную область аренды и bounded admission. Не требуется переписывать весь
проект: сначала закрыть границы task acceptance/commit/ack и HTTP isolation.

web/server.py остаётся крупным узлом с глобальными scan/lease/queue state; трудно проверить
межпроцессные гарантии тестами одного event loop. После аварийных исправлений выделить

## 6. Передача разработчику

Порядок: C01–C05 (единый контракт надёжности очереди) → C08 (ложные уведомления) →
C06 (изоляция HTTP) → C07/C09 (единая доступность/время). Каждое исправление закрепить
регрессией по рабочему пути и повторить независимую приёмку. B01/B05/B07/B08/B09/B10/B11
имеют подтверждённые положительные результаты в прежних сценариях; они не дают права
закрывать остаточные C01–C09 либо считать испытания стенда завершёнными.

Следующий точный шаг: назначить исполнителя на контракт accepted → committed → ACK и
перенести воспроизведения C01–C05 в независимые регрессии с настоящим Redis/рестартом.
Решение о выпуске и любые изменения прода остаются за владельцем.
