## MW-01 — смена пространства числовых ID разрывает идентичность (P1)

`scrapers/marwin.py`, `_extract_item`: ключ строится из нового `raw.id`; fallback на `sku` применяется лишь при отсутствии id. Префикс `marwin_` и суффикс `@unknown` сохранены, но само число изменилось по признанию автора. Сохранение формата ключа не означает сохранение ключа товара. Миграции/alias по старым ID в патче нет.

На настоящей временной БД воспроизведён **синтетический переход одного товара** с `marwin_3495958@unknown` на `marwin_221538@unknown`: старый имел цену 10 000, новый — 9 000. После записи остались две активные строки; `first_seen_price` нового = 9 000, история — по одной точке на каждый ID, избранное осталось на старом ID. История не уничтожена физически, но не продолжена на новой записи. Проверка не утверждает, что эти два числа действительно соответствуют одному живому товару: это иллюстративные ID из сценария смены идентификатора. Масштаб существующих связей в production не измерялся.

Для PRODUCT-наблюдений код `watches._matches` допускает `former_product_ids`, но новый адаптер такой переход не предоставляет; автоматическую связь по совпадению названия предполагать нельзя. Возможные совпадения чисел старого и нового ID разных товаров также требуют контроля до записи; наличие такой коллизии на живой БД здесь не установлено.

**Требование к исправлению:** установить и подтвердить на реальных парах устойчивый артикул/кросс-маппинг старый→новый; сохранять storage ID либо выполнить отдельный проверяемый переход с сохранением истории, избранного и наблюдений. Не сопоставлять товары только по похожему названию. Неизвестные и неоднозначные пары не должны молча переименовываться или перезаписывать другую запись. Если безопасная совместимость невозможна, нужна явная согласованная политика отдельного нового источника и судьбы старых связей; текущая карточка «штатная замена» этого не задаёт.

**Приёмка:** на временной копии/БД с реальными проверенными парами — одна логическая идентичность, продолженная история и актуальные связи favorites/PRODUCT watches; контроль отсутствия ложного объединения/коллизии; отдельно неизвестная пара. Реальные персональные данные в отчёт не включать.

## MW-02 — новые URL не снимают записи старых источников (P2)

`config.py`, все девять `MARWIN_CATEGORIES`: URL меняются одновременно с API. `database._reconcile_source_conn` сверяет строго пару `(shop_key, source_url)`. Патч не переводит старые `product_sources` и baseline на новые URL и не сохраняет прежний логический ключ источника.

Реальная временная БД: запись привязана к `/books/`, затем чистый полный обход `/knigi-32627` её не возвращает. Результат — `retired=[]`, старая запись и привязка остаются активными. Дополнительный сценарий с **неизменным ID** отсутствующего товара тоже оставляет его активным: проблема не зависит от MW-01. Следовательно заявление передачи «при первом полном обходе старые ненайденные будут штатно заменены» не соответствует текущей сверке. Возрастная фильтрация позже может скрыть старые записи, но не является результатом полного обхода и не переносит baseline.

**Требование:** сохранять стабильный ключ источника при смене fetch URL либо подготовить явно ограниченный переход URL/привязок. Не считать новую категорию эквивалентной старой без проверки границ ассортимента. Не выполнять массовое снятие без подтверждённой полноты.

**Приёмка:** переход old source→new endpoint на временной БД: встреченный товар обновлён и сохраняет историю; действительно отсутствующий снимается только полным качественным обходом сопоставимого источника; partial/unparsed не снимает ничего. Старые ссылки источника не удерживают исчезнувший товар бесконечно активным. Baseline не использовать для нового ассортимента автоматически без проверки сопоставимости.

## MW-03 — bool и дробное pages подтверждают ложный полный обход (P2)

`scrapers/marwin.py`, `_fetch_page`: `int(pagination.get("pages") or 0)` преобразует `True` и `1.9` в `1`. Страница с одним товаром и метаданными `page=1, total=1000, pages=True` либо `1.9` превращается в `complete=True, unparsed=0`.

Независимая проверка настоящего `_scrape_sync` и `_reconcile_source_conn` на временных данных: оба ответа разрешили `may_retire=True` и сняли отсутствующий `marwin_102@unknown`. Карточки валидны; существующий unparsed guard этот дефект не ловит. Это синтетические повреждённые ответы, а не утверждение, что живой API уже присылал bool/дробь.

**Требование:** строго проверять целочисленный положительный `pages`, исключая bool и дроби, а также согласованность метаданных текущей/последней страницы и заявленного total, если они используются для доказательства конца. Невалидная/противоречивая пагинация означает partial/ошибку, а не complete.

**Приёмка:** bool, дробь, отрицательное/нулевое/нечисловое pages и противоречивые page/total не разрешают снятие; корректная одно- и многостраничная выдача завершается и законно снимает отсутствующий товар.

### MW-03 — осталось ложное complete при усечённой последней странице (P2)

`parse_marwin_pagination` проверяет `total > raw_count` лишь для **одностраничного** результата. В двухстраничном случае `page=2, pages=2, total=40, limit=20, raw_count=1` считается валидным. `_scrape_sync` завершает обход после этой страницы, не сопоставляя число уникальных полученных товаров с total или ожидаемый размер страницы.

Независимое воспроизведение:

1. Первая страница: 20 уникальных валидных товаров, `page=1, pages=2, total=40, limit=20`.
2. Вторая: один новый валидный товар, `page=2, pages=2, total=40, limit=20`.
3. Итог: **21 из заявленных 40**, `complete=True`, `unparsed=0`.
4. Настоящая сверка на временной БД с 40 прежними товарами: quality=warning (52,5% нормы), **may_retire=True, снято 19**. Порог degraded не спасает от такого сценария.

**Доработка:** полное подтверждение должно проверять согласованность размеров/total на всех страницах; потеря части карточек или противоречивые метаданные на любой странице не должны разрешать снятие в итоговом обходе.
