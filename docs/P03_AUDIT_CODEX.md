## D01 — P1: несвязанное успешное событие закрывает инцидент

Место: monitoring.py:534–537, 566–572, функция incidents.

Восстановление магазина определяется одной последней INFO-категорией без сопоставления с затронутыми категориями/хостами и без проверки complete/quality. Воспроизведено через настоящий TelemetryService и временную БД: WARNING HTTP 403 магазина A в категории Phones два часа назад → INFO scan_category того же магазина в категории TV час назад. Инцидент Phones получает **open=False и recovered_at**, хотя повторного успешного наблюдения Phones не было. Несколько затронутых категорий также закрываются одним успехом. В реальном producer scan_category имеет INFO и при limited без error, так что severity сама по себе не доказывает восстановление.

Компонентная ветка аналогично считает любой INFO/DEBUG успехом; например, событие о пропуске вызова AI не доказывает восстановления упавшего воркера. Это вывод по коду, отдельное воспроизведение компонентного случая не выполнялось.

Рекомендация: соотносить восстановление с областью и причиной инцидента. Успех другой категории не закрывает проблему; ограниченный результат без подтверждения восстановления не считать полным успехом. Для нескольких затронутых областей проверять каждую либо использовать явно подтверждённое восстановление всего магазина. Для компонентов определить допустимые успешные исходы вместо произвольного INFO.

Приёмка: Phones failed → TV success оставляет инцидент открытым; limited/quality warning не даёт ложного восстановления; подтверждённое восстановление соответствующей области закрывает инцидент; частичный успех при нескольких проблемных категориях не закрывает весь инцидент. Тест test_group... в текущем наборе фактически закрепляет слишком широкое правило — обновить ожидания по смыслу восстановления.
