## F1 / P2 — неизвестная пара id/name становится новой категорией

Место: `local_search.py:38–39`, далее `44–55`, уточнение `220–225`, применение уверенной категории `search_sync`.

Путь `subcategory/category` ограничен существующими ID. Для нового пути `id/name` такого ограничения нет: если ID неизвестен и имя не совпало с каталогом, пара попадает в прежнюю ветку создания `ai_<hash>`. Обычный объект товара `{"id":"rx_9070_gre","name":"RX 9070 GRE"}` теперь принимается как предложение новой категории, хотя это точная модель видеокарты. Прежний декодер этот ответ отклонял.

**Независимая реальная проверка выполнена дважды** с локальной `qwen3-vl:8b-instruct`, полным актуальным каталогом **89 категорий**, кодом кандидата в отдельном диагностическом процессе контейнера стенда. Сервис продолжал обслуживать v6.28.9; кандидат не развёрнут.

Во втором прогоне сохранены значимые поля обоих настоящих ответов модели:

1. Запрос `RX 9070 GRE`; первичный ответ: `id=rx_9070_gre`, `name=RX 9070 GRE`, `parent_id=electronics`. Старая версия не принимает его; кандидат создаёт план новой категории модели.
2. Вспомогательный вызов схемы отвечает `new_category_name=Геодезическое оборудование`, `parent_id=ai_706f8863ee306bd0`.
3. Итог кандидата: `status=ok`, **category_id=ai_706f8863ee306bd0**, category_name=«Геодезическое оборудование», **confidence=0.95**, search_query=`RX 9070 GRE`. Та же ошибочная конечная категория получена и в первом прогоне. В первом прогоне confidence и дополнительные поля второго ответа не сохранялись; они подтверждены вторым.

Поскольку раздел уже существует в реальном каталоге, `search_sync` при confidence ≥0.85 применит его как обязательную категорию. Независимая **только читающая** проверка `SearchCore` на живой БД для того же запроса и Астаны:

| Ограничение категории | Результат |
|---|---:|
| Без категории | 7, FOUND |
| gpus — Видеокарты | 7, FOUND |
| ai_706f8863ee306bd0 — Геодезическое оборудование | 0, NOT_FOUND |

Это реальный план кандидата и реальные SQL-результаты соответствующих областей поиска. HTTP/UI кандидата не проверялись, поскольку он не развёрнут. Полный `search_sync` на живой БД не вызывался: он сохраняет intent/analytics/предложения. Читающая проверка не создавала эти записи.

**Рекомендация:** разделить нормализацию формы ответа и разрешение новой категории. Принимать alias-only `id/name` как существующий ID либо точное имя существующего раздела; неизвестный объект не считать неявным запросом создания нового раздела. Сохранить отдельный явный контракт предложений новых видов товара. Не позволять вспомогательному ответу схемы превращать неподтверждённую модель товара в уверенное ограничение посторонней категорией. При сомнении оставить буквальный поиск и честное состояние помощника. Не решать проблему зашитой проверкой одной строки RX 9070 GRE.

**Критерий повторной приёмки:** сохранённые реальные ответы этого сценария больше не приводят к неверной уверенной категории; `RX 9070 GRE` сохраняет 7 доступных товаров Астаны; unknown alias-only пара не создаёт категорию модели; корректные известные alias-пары и явные предложения новых видов продолжают работать. Затем повторить матрицу живой модели с полным контекстом и проверить интерфейс после выкладки принятого коммита на стенд.
