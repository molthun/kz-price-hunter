Воспроизведение только на синтетике: временный .github/workflow.yml с TOKEN и строкой формы GitHub PAT; check_secrets(root).ok=True. Никакие настоящие ключи не читались и в отчёт не включены.

Исправление: обходить отслеживаемые git-файлы, включая .github и прочие скрытые пути; исключать служебные каталоги адресно. Исключения для примеров должны относиться к значению/конкретной фикстуре, не ко всей строке произвольного файла.
Приёмка: синтетический токен в отслеживаемом workflow блокирует gate, реальная локальная игнорируемая конфигурация не выводится и не сканируется как часть публикации.

## M09 — P2, P16: непроверенные зависимости принимаются как успешная проверка

Место: `release_gate.py:151–178`.

Парсер проверяет только найденные vuln-элементы, не полноту аудита. Пакет со skip_reason и без vulns принимается. Пустой/неподходящий объект JSON также даёт пустой список пакетов и успех. В workflow код выхода pip-audit подавляется через || true, поэтому отчёт обязан различать эти случаи.

Воспроизведение: JSON dependencies=[{name: demo, skip_reason: Could not audit package}] → ok=True.

Исправление: валидировать структуру отчёта, учитывать skipped/error и исходный статус аудита; необследованная зависимость должна блокировать либо иметь отдельное обоснованное ограниченное по сроку исключение.
Приёмка: пустой/повреждённый по структуре отчёт, ошибка резолвинга и skipped-пакет не дают зелёный gate; чистый полный отчёт проходит.

## M10 — P2, P07 V2: обычная сводка из 25 срабатываний разбивается на два сообщения

Места: `database.py:2174`, `notifier._deliver_watch`.

claim_watch_digest забирает максимум 20 дополнительных заданий к первому. Допустимый за один вызов evaluate_watches пакет из 25 событий поэтому разделяется на 21 и 4; оставшиеся задания сразу выбирает та же доставка.

Воспроизведение на настоящей временной очереди через DigestDeliveryTest.queue_digest(count=25) и send_all: queued=25, mock_messages=2. Telegram полностью подменён, сообщений людям не было.

Исправление: определить единый пакет на период сводки и атомарно закреплять его за отправкой; при ограничении текста давать общий счётчик и сокращённый список. Остальные события того же пакета не должны создавать второе письмо.
Приёмка: 25 и больше накопленных событий одного наблюдения → одно сообщение за период; retry сохраняет тот же пакет; параллельные workers и устаревшие цены проверяются отдельно.

## M11 — P2, AI-часть P09: округление повышает уверенность до разрешающего порога

Место: `catalog_ai.py:103`.

parse сначала округляет confidence до трёх знаков; accepted затем сравнивает уже округлённое значение с 0.90. Ответ {same: true, confidence: 0.8999} превращается в 0.9 и разрешает сравнение, хотя согласованный порог не достигнут.

Исправление: сравнивать исходную конечную числовую уверенность; округлять только отображение. Не разрешать bool вместо числовой уверенности.
Приёмка: 0.8999 и True не принимаются, ровно 0.90 принимается; границу проверить по пути parse→save→matching_decision→accepted. Живой замер precision/recall остаётся отдельным условием первого включения on.
