## P17ER-03 [P1] Ошибка после запуска оставляет разрешение перезаписать жившую базу

Места: `deploy/prod-host/restore_prod.sh:65–70,163–164,197–198,213–233`.

Защита новой версии различает `prepared` и `started`. Но `write_state started` выполняется
только после health, поиска, счётчиков и настроек. Между `docker compose up -d` и этой записью
контейнер уже может работать и менять восстановленную БД. Любая ошибка проверок, завершение
shell-процесса или частично успешный compose оставляют прежнюю отметку `prepared`.

Следующий запуск с `--db` видит `prepared`, считает базу «ещё не жившей» и выполняет
`rm -f prices.db prices.db-wal prices.db-shm`, затем копирует другой файл. Проверки использования
базы контейнером и остановки экземпляра перед этим нет. Отказ при живом старом `--old-url`
также не защищает этот путь: замена происходит в подготовке, а без `--start` до проверки
старого URL выполнение вообще не доходит.

**Независимое воспроизведение на синтетической SQLite:**

1. Подготовка проходит, state=prepared.
2. Запуск проходит `compose up`; health и поиск успешны, но следующая проверка счётчиков
   возвращает несовпадение, и скрипт завершается с exit 1.
3. Состояние остаётся `prepared`. Для моделирования записи уже запущенного приложения
   в подготовленную SQLite добавляется таблица с новой строкой.
4. Повторная подготовка `--db <другая копия>` возвращает **0**, не останавливает приложение
   и удаляет добавленные после запуска данные из файла по пути восстановленной базы.

Результат: `start_exit=1`, `compose_up_ran=true`, `state_after_poststart_failure=prepared`,
`replacement_exit=0`, `runtime_data_preserved=false`.
Свидетельства: `late_start_failure.py`, `late_start_failure.txt`.

Внешние команды Docker в этом воспроизведении заменены заглушками; состояние и реальная
синтетическая SQLite меняются неизменённым shell-скриптом. Настоящий прод не запускался,
не останавливался и не перезаписывался. Риск следует из переходов состояния shell после
факта вызова compose, а не из гипотезы о повреждении исходной рабочей БД.

**Рекомендация:** сохранять состояние, запрещающее замену базы, **до первой попытки запуска**
контейнеров, отдельно от успешной приёмки сервиса. Например, различать prepared / starting /
started / verified; starting тоже означает, что база могла стать живой. Не возвращать prepared
автоматически при провале smoke. Замена допустима только при доказанном отсутствии экземпляра,
использующего каталог, и в явном безопасном процессе подготовки. Состояние записывать устойчиво;
учесть частичный успех compose и прерывание shell.

**Повторная приёмка:** успешная подготовка/запуск и отказ при живой старой стороне сохраняются;
ошибка после compose up, частичный отказ compose, SIGTERM и провал каждой последующей проверки
не позволяют `--db/--config` удалить или изменить уже использовавшуюся БД/WAL. Повторный запуск
без замены данных безопасен. Неподготовленная чужая база по-прежнему защищена.

## Прежние замечания

### P17ER-01 закрыт в исходном воспроизведении

Сценарий `prepare → --start` теперь проходит: exit 0 → exit 0, compose вызывается один раз.
Подготовленный каталог сохраняет состояние, можно повторить отказ при живой старой стороне,
заменить ещё не запускавшуюся подготовленную копию более свежей и затем начать запуск.
Штатные регрессии этих переходов прошли. Новое замечание P17ER-03 проверяет отдельный путь —
отказ **после** запуска; он не отменяет подтверждение исправления прежнего сценария.

### P17ER-02 закрыт в проверенном объёме

Удалённая ветка теперь выполняет quick_check по SSH и читает состав целевого config-архива
до retention/ok. Дополнительная матрица с временным каталогом и локальной заглушкой SSH:

| Сценарий | Код / итог | Прежние копии | quick_check на удалённой стороне |
|---|---|---|---|
| Исправный набор | 0 / ok | 13 из 16, плюс новая — retention соблюдён | Выполнен |
| DB повреждена при том же размере | 1 / failed | 16 из 16 сохранены | Выполнен |
| Python для проверки недоступен | 1 / failed | 16 из 16 сохранены | Попытка выполнена, отказ обнаружен |

`remote-matrix.json` подтверждает эти результаты. Старый сценарий `remote_delivery.py` тоже
перестал принимать повреждённую копию; его собственная заглушка SSH не ведёт журнал вызовов,
поэтому наличие реальной попытки quick_check проверено отдельной матрицей выше.
Настоящий NAS по SSH не использовался; это приёмка логики удалённой ветки, не живой интеграции NAS.

Непарный архив конфигурации больше не выбирается молча при первичной подготовке: нужна пара
той же метки или явный `--config`. Для обновления уже подготовленного каталога без новой пары
сохраняется его проверенная конфигурация.
