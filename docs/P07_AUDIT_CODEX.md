## G01 — P1: одноразовое наблюдение отменяет собственную доставку

Место: `database.py:evaluate_watches` (2631), `notifier.py:_deliver_watch` (188).
При постановке события в очередь `repeat=False` сразу устанавливает `watches.is_active=0`. Доставка запрещает отправку для неактивного наблюдения. Поэтому успешный trigger одноразового наблюдения заканчивается cancelled без сообщения; после перезапуска результат тот же.

Воспроизведение: fixture `test_watches.DeliveryTest`, `add(repeat=False, quiet_from='00:00', quiet_to='00:00')`; последовательно `evaluate_watches([offer(100000)])` и `evaluate_watches([offer(90000)])`. Сделать outbox готовым (`next_attempt_at=0` на тестовой БД), вызвать настоящий `deliver_pending` с подменой только транспорта (`DeliveryResult('sent')`). Результат: **send_watch_message вызван 0 раз, outbox.status='cancelled'**. Пользователь включил Telegram, товар существует с текущей ценой 90000.

Рекомендация: различать ручное выключение и завершение одноразового наблюдения. Резервировать trigger от повторной постановки, но разрешать доставку уже созданного события; либо переводить в завершённое состояние после успешной отправки с защитой от повторных trigger. Приёмка: end-to-end one-shot → одна отправка; временная ошибка/429 и restart сохраняют повтор доставки, ручное выключение отменяет её, новые события не создаются.

## G02 — P1: параллельная оценка создаёт два события одного снижения

Место: `database.py:evaluate_watches` (2558), чтение `_watch_states` перед записью события.
Оба исполнителя могут прочитать прежнюю цену до записи первого. Каждый вставляет свой watch_event с новым ID и свой outbox с `alert_id=-event_id`. UNIQUE(alert_id,user_id) защищает только одинаковый event_id, а два ID здесь разные.

Воспроизведение: fixture `test_watches.StorageTest`; создать repeat-наблюдение, baseline 100000. В двух потоках одновременно выполнить `evaluate_watches([offer(90000)])`; обернуть `_watch_states` барьером `threading.Barrier(2)` после настоящего чтения, чтобы оба потока увидели один baseline. Оба вызова вернули **1**, в outbox **2 строки**. Настоящие SQLite-соединения/insert/commit, mock только синхронизирует момент чтения.

Рекомендация: атомарно выполнять чтение состояния, принятие trigger и запись события/нового состояния (например, корректная транзакция BEGIN IMMEDIATE), либо добавить устойчивый уникальный идентификатор логического перехода. Приёмка: конкурентный тест с независимыми соединениями → ровно одно событие и одно задание; после restart повторная оценка не создаёт дубль. Не заявлять exactly-once для внешнего сетевого timeout.
