# Выкат и возврат

Документ отвечает на два вопроса владельца: **как выкатывается новая версия** и **как вернуться назад**,
если она не понравилась. Обе процедуры отрепетированы автоматикой, а не описаны по памяти.

## Что проверяется до публикации образа (шлюз P16)

Публикация в GHCR (`build-and-push`) начинается только после того, как прошли все обязательные проверки:

| Проверка | Что делает | Где |
|---|---|---|
| `test` | компиляция всех файлов и весь набор `test_*.py` | `.github/workflows/docker-publish.yml` |
| `frontend` | браузерные регрессии `test_frontend*.cjs` в Chrome раннера | там же |
| `secret-scan` | ищет ключи и токены во всех файлах, которые хранит git, включая `.github` | `release_gate.py secrets` |
| `dependency-audit` | уязвимости зависимостей (`pip-audit`) с учётом списка пропусков | `release_gate.py deps` |
| `upgrade-rehearsal` | база предыдущего релиза → новый код → миграции → запросы приложения → целостность, затем запуск САМОГО прежнего релиза на обновлённой копии | `release_gate.py upgrade`, `release_gate.py rollback` |
| `image-smoke` | образ собирается, запускается и проверяется до публикации | `release_gate.py smoke` |

Непрошедшая проверка останавливает публикацию: образ в реестр не попадает, Watchtower на проде ничего
не подхватывает. Это ровно то, что имеется в виду под «шлюзом»: предупреждений, которые можно не заметить,
здесь нет.

### Что считается непройденной проверкой зависимостей

Зелёный результат даёт только полный и понятный отчёт. Пустой отчёт, повреждённая структура, ошибка
резолвинга и пакет, который не удалось проверить (`skip_reason`), считаются **непроверенными** и
останавливают публикацию: «не смогли проверить» — это не «проверено и чисто».

### Пропуск известной уязвимости

Список — `docs/dependency_allowlist.json`. Запись действует только если у неё есть **причина** и **дата
окончания** (`until`, UTC). После этой даты шлюз снова останавливает публикацию. Бессрочных пропусков нет.

## Выкат

1. Слить изменения в `main` (после аудита) — запускается конвейер публикации.
2. Дождаться зелёного `build-and-push`: он публикует `latest` из `main` и версию из тега `vX.Y.Z`.
3. На проде Watchtower подхватывает `latest` в течение ~5 минут.
4. Проверить чтением: `/api/version`, `/api/stats`, `/monitoring` — версия и состояние разделов.

## Возврат

Возврат зависит от версии схемы базы. Её сообщает та же репетиция обновления:

- **Схема не изменилась** (`rollback_compatible: true`) — прежний образ такую базу откроет. Это условие
  необходимое, но не достаточное, поэтому конвейер отдельно запускает код прежнего релиза на обновлённой
  копии (`release_gate.py rollback`) и проверяет на ней настоящие запросы приложения. Если обе проверки
  зелёные, достаточно запустить прежний образ (`ghcr.io/<репозиторий>:<прежняя версия>`): восстанавливать
  базу не нужно, данные не теряются.
- **Схема выросла** — прежний образ такую базу не поднимет. Тогда: остановить контейнер, восстановить
  согласованную копию из `data/backups/`, запустить прежний образ. **Теряется всё, что накопилось после
  этой копии** — новые товары, наблюдения цен, срабатывания наблюдений, очередь уведомлений.

Пригодность копии — не догадка: самопроверка (P15) ежедневно разворачивает свежую копию во временную базу
и прогоняет на ней настоящие запросы приложения. Состояние видно в Центре мониторинга, раздел «Система».

## Проверить шлюз вручную

```bash
python release_gate.py secrets --root .
python release_gate.py upgrade /путь/к/базе_предыдущего_релиза.db
python release_gate.py rollback /путь/к/обновлённой_базе.db /путь/к/коду_прежнего_релиза
python release_gate.py smoke http://127.0.0.1:35539
```

Копия базы для репетиции снимается через SQLite Backup API, а не копированием файла: при активном
журнале WAL подтверждённые транзакции иначе не попали бы в копию, и проверка целостности этого бы не
заметила. Исходный файл базы репетиция не трогает.

Каждая команда печатает отчёт и возвращает ненулевой код при провале — так же, как в конвейере.

## Намеренная ошибка

Чтобы убедиться, что шлюз действительно держит, достаточно временно сломать одну проверку (например,
добавить в ветку файл с ключом-образцом настоящего вида) и убедиться, что задание `secret-scan` падает,
а `build-and-push` не запускается вовсе. Такую проверку делают на отдельной ветке, а не на `main`.
