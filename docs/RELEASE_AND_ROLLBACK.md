# Публикация версии, обновление сервера и откат

С 22.11.2026 Git — основная копия принятых исходников и история релизов. Рабочая бета — один сервер. Публикация репозитория/образа **не означает** обновление приложения с пользователями.

## Подготовить кандидат

1. Зафиксировать проверяемый коммит и его версию. При изменениях приложения обновить `version.py`/CHANGELOG; для одной документации номер приложения не повышать.
2. Проверить кандидат на временных данных в [изолированном контейнере](TEST_STAND.md). Никаких рабочих БД, реальных токенов бота и второго планового обхода.
3. Приложить результаты подходящих тестов, проверки секретов и зависимостей, совместимости схемы/отката. Mock-проверку не выдавать за проверку реального магазина, Telegram или AI.
4. Провести требуемую приёмку, просмотреть diff и включить только относящиеся к задаче файлы.

## Опубликовать в Git

По поручению владельца отправить принятые коммиты в `origin/main`. Релизные теги `vX.Y.Z` ставить на согласованный коммит с той же версией в `version.py`; не перемещать существующий опубликованный тег.

В `.github/workflows/docker-publish.yml` push в main/релизный тег запускает проверки и публикацию GHCR. Main публикует `latest`; semver-тег не меняет `latest`. Живой сервер не использует Watchtower и обновляется явно. Это свойство текущей установки: чужая установка может подписываться на `latest` самостоятельно.

Документация должна попадать в тот же Git, что и соответствующий код. Наличие изменений только в локальном checkout не считается публикацией. После push сверить удалённый SHA/файлы и статус CI. Не включать в Git `.env`, рабочую БД, cookies, ключи и backup.

## Что проверяет workflow

Фактический источник — [docker-publish.yml](../.github/workflows/docker-publish.yml), а не число тестов в старом отчёте.

| Проверка | Назначение |
|---|---|
| Python tests + coverage | Поведение приложения и минимальный порог покрытия |
| Frontend | Все tracked `test_frontend*.cjs` |
| Secrets | Поиск ключей, включая скрытые tracked-файлы |
| Dependency audit и pins | Допустимость зависимостей и соответствие фиксациям |
| Upgrade / rollback rehearsal | Проверка миграции и совместимости прежнего кода на копии |
| Image smoke | Запуск и HTTP-проверка собранного образа |

До прохождения обязательных jobs публикация образа не завершена. Зелёный локальный тест не гарантирует успех GitHub Actions. Фактическое число наборов и сроки проверки берутся из конкретного запуска.

## Обновить нашу рабочую бету

Разрешение на публикацию Git не является автоматическим разрешением на перезапуск сервера. Для уже порученного обновления повторного согласования не требуется.

1. Сохранить текущие image digest, SHA, версию, применённые compose/overrides и путь backup.
2. Сделать согласованную копию БД и сохранить конфигурацию по [OPERATIONS.md](OPERATIONS.md#резервная-копия-и-восстановление).
3. Подготовить чистый checkout принятого коммита. Не выполнять reset/clean поверх чужих изменений или локальной конфигурации. Перенести код через Git/bundle; не подменять рабочие данные.
4. Собрать и переключить только приложение с обоими compose-файлами:

```bash
cd /path/to/checkout
docker compose -f docker-compose.stand.yml -f docker-compose.live.yml build app
docker compose -f docker-compose.stand.yml -f docker-compose.live.yml up -d app
```

5. Проверить фактический image/SHA, `/api/version`, `/api/health`, журнал, вход, поиск/карточку, бот и сохранение настроек. Наблюдать очереди и следующий обычный обход без принудительного сброса cooldown.
6. Записать результат в текущую передачу: что именно проверено, что остаётся гипотезой, как откатить. Не запускать старый контейнер и его Watchtower.

## Откат

Сначала выяснить, совместима ли текущая схема с прежним образом. При совместимости использовать сохранённый image digest и тот же каталог данных. Не запускать build из «старого» тега с изменёнными файлами и не считать `latest` точкой отката.

Если нужна прежняя БД, следовать [восстановлению](OPERATIONS.md#резервная-копия-и-восстановление): остановить приложение, сохранить текущее состояние и новые записи пользователей, восстановить согласованную копию, затем проверить совместимый образ. После отката повторить те же пользовательские проверки.

Возврат к отдельному старому прод-контейнеру — разовый аварийный сценарий перехода, описанный в [SINGLE_LIVE_MIGRATION.md](archive/SINGLE_LIVE_MIGRATION.md), а не обычный способ выпуска.
