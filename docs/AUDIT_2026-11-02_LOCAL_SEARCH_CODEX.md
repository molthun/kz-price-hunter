### LSA-01 — автоподстановка атрибута уменьшает подтверждённую выдачу

**Код:** `local_search.py:209–223`, `repositories/search_repo.py:225–237`.

При появлении хотя бы одного сохранённого значения признака в категории в SQL включается атрибут
из ответа модели. `EXISTS` требует фактического значения у каждого товара, в том числе у тех,
для которых `catalog_expansion_matches` уже подтвердил соответствие полному запросу.

**Воспроизведение:** `inferred_attribute_hides_verified`. Два товара подтверждены для «зимняя резина»;
у «RoadGrip Audit с шипами» нет явно записанного сезона. Без заполненных сезонов поиск возвращает 2;
при наличии сезона у другого товара — только 1. Пользователь фильтр вручную не выбирал.
На стенде из 24 подтверждений зимнего запроса явный сезон есть лишь у 15; это реальная предпосылка
дефекта, но приведённое сравнение 2 → 1 выполнено на временной БД с контролируемым разбором ИИ.

**Исправление/приёмка:** разделить ручной строгий фильтр и смысловое условие исходного запроса.
Не терять подтверждённый query-match только из-за отсутствующего дублирующего атрибута.
Заполнение факта у соседнего товара не должно уменьшать ранее подтверждённый набор.
Ручной фильтр при этом вправе исключать неизвестные значения, с явным объяснением пользователю.

### LSA-02 — завершается неполный обход

**Код:** `local_search.py:380–392, 438–442, 454–470`.

Сохраняется текст отбора, но не состав кандидатов. Каждый batch заново выполняет поиск с OFFSET.
При уточнении категории часть уже обработанных строк перестаёт соответствовать FTS:
например, слово «тахеометр» было только в исходной категории, а целевая категория называется
«Геодезическое оборудование». Следующая порция с прежним OFFSET пропускает необработанные строки.

**Воспроизведение:** `shrinking_batch_skips`. Из 50 приборов первая порция обрабатывает 30,
после смены категорий в запросе остаётся 20. OFFSET 30 возвращает пусто. Итог — `indexed`,
«Проверено 30 из 50, подходящих: 30»: 20 товаров вообще не проверены.

**Исправление/приёмка:** устойчивый набор ID на запуск проверки либо курсор по неизменяемому
порядку с отдельным журналом обработанных ID. При смене категории/названия между порциями
каждый исходный кандидат проверяется один раз; `indexed` не ставится при необработанном хвосте.

### LSA-03 — устаревшее смысловое подтверждение

**Код:** `repositories/catalog_expansion_repo.py:21–24, 149–174`, `local_search.py:215–237`.

В подтверждении есть только ID заявки и товара. Версии названия/ключа/значимых признаков и времени
решения нет. Проверка свежести `source_title`, присутствующая у атрибутов, к подтверждениям не применяется.

**Воспроизведение:** `stale_confirmation`. После подтверждения TopCon его название меняется на
«Отражатель для прибора Audit». Короткий поиск «тахеометр» продолжает включать отражатель и возвращает
FOUND. Воспроизведён риск смены данных при том же canonical ID; наличие такой неверной карточки
на реальном стенде не утверждается.

**Исправление/приёмка:** привязать решение к версии входных данных и инвалидировать при значимом
изменении товара. Обновлённое название/модель/тип должны пройти повторную проверку до выдачи FOUND.

### LSA-04 — поиск и подписка расходятся

**Код:** `local_search.py:254–260, 491–536`, `watches.py:264–270`.

Поиск использует `catalog_expansion_matches`, но watch-target возвращает текст `plan.search_query`.
`matches_watch` проверяет только FTS и атрибуты; подтверждённый product-scope не используется.
Это ранее отмеченный Claude открытый остаток, теперь воспроизведён отдельно.

**Воспроизведение:** `watch_disagrees`: поиск показывает 3 товара. По короткому watch-тексту совпадает
лишь FOIF (1 из 3), по полному «геодезический тахеометр» — 0 из 3. Чтение стенда с сохранённым
планом заявки: 8 подтверждённых ID и 0 совпадений watch-предиката. Это проверка предиката,
а не доказательство отправки/неотправки конкретного Telegram-сообщения существующему пользователю.

**Исправление/приёмка:** единое представление условий и смысловых подтверждений для поиска и watches.
Подписка, созданная до появления товара, должна распознать те же подходящие модели после проверки,
с сохранением города/состояния/цены и без повторных событий доставки.

### LSA-05 — не завершена граница хранения контента

**Основание:** ранее зафиксированное условие владельца — не накапливать чужие полные описания,
фотографии и копии исходных постов, включая резервные копии; извлечённые сравнимые данные разрешены.

**Код:** `database.py:3438–3449`, `domain/adapter.py:289, 410–437`, `database.py:1822–1825`.

Ingestion передаёт `product.description` без отсечения в legacy и canonical storage; backup API
копирует эти значения. Новый социальный путь уже очищает текст/медиа, но не закрывает общий путь товаров.

**Воспроизведение:** `source_description_retained`: искусственная исходная строка сохраняется
побайтно в legacy, canonical и новой временной резервной копии. На стенде заполнено 28 737
`canonical_products.description`, из них 14 947 длиннее 200 символов. В контрольной копии
`before-local-growth-62442c8.db` — 14 951 такое описание. Длина сама по себе не доказывает, что
каждая строка — полный чужой текст; тест ingestion доказывает отсутствие запрета на его сохранение.
Содержимое реальных описаний в отчёт и доказательства не копировалось.

**Исправление/приёмка:** закрыть новый persistence на входе; инвентаризировать legacy/canonical,
очереди, WAL, копии и snapshots. Отдельно согласовать очистку уже накопленного без потери цен,
наблюдений и идентификации. После неё проверять не только логические поля, но и физические копии.
Ничего в рамках этого аудита не удалялось и не очищалось.

### LSA-06 — сбор запускается для другого города

**Код:** `local_search.py:225–230, 266–267, 373–375`.

Поиск учитывает город из исходного текста, однако `propose` получает `arguments.city`, а не
вычисленный `search_args.city`. Если в селекторе «Все», а город введён словами, заявка теряет его.

**Воспроизведение:** `embedded_city_lost`: «тахеометр в Шымкенте» разбирается как Шымкент,
поиск выполняется для Шымкента, но очередь получает `city=Все`. Живой опрос с таким городом
разрешает город по умолчанию, а не требуемый. Аналитика также берёт исходный аргумент города.

**Исправление/приёмка:** один вычисленный город для поиска, очереди, источников и аналитики;
явный селектор имеет документированный приоритет. Проверить «Все» + город внутри запроса.

### LSA-07 — отменённая задача может стать завершённой

**Код:** `repositories/catalog_expansion_repo.py:88–143`.

Чтение статуса в `review` и последующая запись не защищены условным переходом. Worker может
захватить заявку между ними. `finish` затем безусловно перезаписывает решение администратора.

**Воспроизведение:** `rejection_race`, два соединения к временной SQLite. После чтения approved
worker захватывает checking; review принимает отказ и пишет rejected; старый worker завершает
работу и пишет indexed. Запрет отклонения checking проверялся по устаревшему чтению.

**Исправление/приёмка:** атомарные переходы review и поколение/lease token для записей worker.
Старая попытка не вправе менять состояние, подтверждения и данные новой/отклонённой попытки.
Повторить детерминированное чередование и конкурентный сценарий с реальными workers.

### LSA-08 — предупреждение источника теряется

**Код:** `local_search.py:368–377, 462–470`.

`health` обнуляется при каждой порции, а живой опрос проводится только при `scan_offset=0`.
Результат сбоя источников не сохраняется как часть запуска проверки.

**Воспроизведение:** `source_failure_forgotten`: первая порция содержит предупреждение
«Часть источников не ответила; проверка неполная». После следующей порции итог indexed
«Проверено 50 из 50» уже не содержит предупреждения, хотя источники не восстанавливались и не повторялись.

**Исправление/приёмка:** хранить состояние покрытия источников на уровне попытки и переносить
его во все последующие порции/итог. Повторная попытка источника может закрыть предупреждение;
простое завершение обработки локальных кандидатов — нет.

### LSA-09 — подтверждения доступны только вместе с работающим ИИ

**Код:** `local_search.py:201–215`.

Даже точное сохранённое подтверждение читается только внутри ветки успешного нового разбора.
При паузе/отказе модели каталог возвращается к текстовому поиску и забывает уже проверенные связи.

**Воспроизведение:** `ai_unavailable_loses_confirmations`: полный запрос в том же каталоге
возвращает 3 результата с работающим разбором и 0 при `status=unavailable`. Никакие данные/цены
при этом не меняются. Интерфейс показывает предупреждение об ИИ, но полезная выдача теряется.

**Исправление/приёмка:** точные сохранённые запросы/подтверждения и их ограничения использовать
независимо от нового вызова модели. Новую интерпретацию без ИИ не выдумывать. Проверить отказ/паузу
при неизменных данных и ранее проверенном запросе.
