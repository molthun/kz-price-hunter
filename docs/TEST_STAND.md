# Испытательный стенд

Отдельная Linux-машина, на которой можно ломать приложение не трогая прод: с настоящим
Docker, настоящим Redis внутри контейнера и **намеренно урезанными ресурсами**.

Зачем он понадобился: разбор отказов 27–28.10.2026 шёл вслепую. Тесты гоняются на macOS,
где нет ни Docker, ни Redis; образ локально никто не собирал; воспроизвести конкуренцию за
базу было негде, и каждая заявка на аудит заканчивалась строкой «не проверялось: сборка
образа, поведение под нагрузкой». Аудит Codex от 28.10.2026 требует стенд прямым текстом
(раздел 7): «Добавить Linux/container стенд с настоящим Redis и оговорённым лимитом CPU/памяти».

Машина: `192.168.28.25`, Ubuntu 26.04 LTS «resolute» — **та же система, на которой собран
наш образ** (`playwright/python:v1.63.0-resolute`), та же архитектура. Поведение совпадёт
с продом, в отличие от Мака на ARM, где amd64-образ пришлось бы эмулировать.

## Главное правило стенда

Ресурсы урезаны до прода: **4 ядра и 15 ГБ**, как на NAS. Это не экономия, а условие
осмысленности. На свободной машине блокировки короче, волна перестаёт обрываться, очередь
не растёт — и стенд показывает «всё работает» там, где прод теряет данные. Лимиты заданы
в `docker-compose.stand.yml` и снимаются только осознанно, отдельным файлом.

Стенд **не перезапускает контейнер сам** (`restart: "no"`): упавший должен остаться упавшим,
иначе сценарии с рестартом и потерей задач нечем наблюдать.

## Доступ

**SSH слушает порт 2222**, не 22. Подключение:

```bash
ssh -p 2222 molthun@192.168.28.25
```

Чтобы агент мог работать со стендом сам, на машине должен лежать его публичный ключ —
иначе остаётся только пароль, а пароли агент не вводит. Один раз с Мака:

```bash
ssh-copy-id -p 2222 molthun@192.168.28.25
```

## Внешний доступ: https://shdev.molthun.ru

Стенд открыт наружу обратным прокси DSM на NAS (`192.168.28.10`). Снаружи приходят только
443 и 80; порт `35539` остаётся для NAS в локальной сети и на роутере не открывается.

| | |
|---|---|
| Источник (DSM: Портал входа → Обратный прокси) | HTTPS, `shdev.molthun.ru`, 443 |
| Назначение | HTTP, `192.168.28.25`, 35539 |

Сертификат — Let's Encrypt на самой DSM, назначенный этой службе; выпуск требует внешнего
порта 80. Валидный сертификат обязателен: виджет входа Telegram с самоподписанным не работает.
Порт 80 в остальном только под редирект на HTTPS. WebSocket-заголовки не нужны — приложение
их не использует; таймаут прокси стоит держать около 120 с, запросы к AI бывают долгими.

**Отдельный бот.** Вход идёт через официальный виджет Telegram, а Telegram пускает виджет
только с домена, привязанного к боту (`/setdomain` → `shdev.molthun.ru`). Поэтому у стенда
свой бот `@kzph_dev_bot`, и продовому боту домен не меняется. Один и тот же токен в двух
местах недопустим: Telegram допускает одного потребителя `getUpdates`, второй экземпляр
сломает бота на проде (в логах — «Конфликт polling/webhook (HTTP 409)»).

`.env` стенда под внешний доступ:

```bash
APP_URL=https://shdev.molthun.ru
PUBLIC_ORIGIN=https://shdev.molthun.ru
TRUSTED_PROXIES=192.168.28.10/32
ALLOW_DEV_LOGIN=0
TELEGRAM_BOT_TOKEN=<токен @kzph_dev_bot>
ADMIN_TELEGRAM_IDS=<ваш id>
DIAG_TOKEN=<openssl rand -hex 24>
```

Почему именно так:

- `PUBLIC_ORIGIN` без слэша на конце — он проверяется при старте и служит ожидаемым `Origin`
  для всех POST-запросов; схема `https` здесь же включает флаг `Secure` на сессионной cookie.
- `TRUSTED_PROXIES` — адрес NAS, потому что именно его видит aiohttp: запрос приходит с
  Synology на опубликованный порт стенда. С пустым значением `X-Forwarded-For` не считается
  доверенным, и все посетители попадают в один общий лимит по IP. Проверить, кого реально
  видит приложение, можно без sudo во время загрузки страницы: `ss -tn "sport = :35539"`.
- `ALLOW_DEV_LOGIN=0`: при заданном `PUBLIC_ORIGIN` вход разработчика отключается кодом
  в любом случае, остаётся только вход через Telegram.
- Пустой `DIAG_TOKEN` закрывает `/api/diag` полностью — снаружи это тем более важно.

`.env` читается при создании контейнера, поэтому после правки нужен не `restart`, а
`docker compose -f docker-compose.stand.yml up -d`. Проверка, что токен принят:

```bash
curl -s https://shdev.molthun.ru/api/me | grep -o '"bot_username":[^,]*'
```

Помните, что `restart: "no"` теперь касается внешнего сайта: после падения контейнера
`shdev.molthun.ru` будет отдавать 502 до ручного подъёма.

## Подготовка машины

Docker не установлен. Эти команды требуют прав администратора, то есть пароля,
и выполняются владельцем — один раз:

```bash
ssh -p 2222 molthun@192.168.28.25
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2 git rsync
sudo usermod -aG docker "$USER"
exit
```

После `usermod` нужно перезайти по SSH, иначе `docker` будет требовать `sudo`. Проверка:

```bash
docker run --rm hello-world
```

Всё дальнейшее — перенос кода, сборка, запуск, наблюдение — прав администратора уже
не требует: достаточно членства в группе `docker`.

## Код и окружение

```bash
git clone https://github.com/molthun/kz-price-hunter.git ~/kzph-stand
cd ~/kzph-stand
cp stand.env.example .env
```

Дальше заполнить `.env`. Три места, где легко сделать больно:

- **`TELEGRAM_BOT_TOKEN` — не продовый.** Telegram допускает только одного потребителя
  `getUpdates`: второй экземпляр с тем же токеном **сломает бота на проде**. В логах это
  выглядит как «Конфликт polling/webhook (HTTP 409)». Либо отдельный тестовый бот, либо пусто.
- **`TRUSTED_PROXIES` пустым**, если перед стендом нет обратного прокси.
- **`ALLOW_DEV_LOGIN=0`**, пока стенд доступен кому-то кроме вас.

`DIAG_TOKEN` сгенерировать `openssl rand -hex 24`. На стенде диагностика заработает сразу —
там свежий код, в отличие от прода.

## Данные

Каталог `stand-data` должен лежать на NVMe или SSD. Сетевые шары не подходят: SQLite на них
ведёт себя непредсказуемо, а файл базы уже около 2 ГБ.

Пустая база годится для функциональных проверок, но **не** для воспроизведения конкуренции:
именно объём и длительность транзакций создают ту картину, которую мы ловим. Поэтому для
нагрузочных сценариев нужна копия рабочей базы.

Снять её **согласованно**, не копируя файл на ходу (копия работающей WAL-базы может оказаться
битой). На NAS:

```bash
df -h /volume1        # нужно ~2.5 ГБ свободного места
sudo docker exec kz-price-hunter python3 -c "import sqlite3; s=sqlite3.connect('file:/app/data/prices.db?mode=ro',uri=True); d=sqlite3.connect('/app/data/stand-copy.db'); s.backup(d); d.close(); print('готово')"
```

Это онлайн-копия средствами SQLite: прод не останавливается, рабочая база только читается.
Затем перенести и положить на место:

```bash
scp molthun@NAS:/volume1/.../stand-copy.db ~/kzph-stand/stand-data/prices.db
```

После переноса копию на NAS удалить, чтобы не занимала место.

## Запуск

```bash
cd ~/kzph-stand
docker compose -f docker-compose.stand.yml up -d --build
docker compose -f docker-compose.stand.yml logs -f
```

Первая сборка небыстрая: базовый образ с браузерами около 1.1 ГБ.

Проверка, что живой:

```bash
curl -s http://localhost:35539/api/version
curl -s -H "X-Diag-Token: ВАШ_ТОКЕН" http://localhost:35539/api/diag
```

Второй запрос — это и есть то, чего не хватало на проде: журнальный режим базы, задержка
цикла событий, размер пула, глубина очереди, свежие ошибки и готовый список проблем.
Ответ занимает около 250 мс: столько длится замер задержки цикла.

Остановить: `docker compose -f docker-compose.stand.yml down`.

### Вариант без лимитов

Только для одного вопроса — куда уходит память (на NAS процесс растёт с 0.9 до 5.3 ГиБ
за волну и ниже 4.8 не опускается):

```bash
docker compose -f docker-compose.stand.yml -f docker-compose.stand.nolimits.yml up -d
```

Для всего остального пользоваться обычным стендом.

## Что на нём проверять

Порядок задан аудитом: сценарии должны идти по рабочим путям, а не отдельными удачными
тестами. Для каждого замечания критерии приёмки расписаны в разделе 4
[отчёта](FULL_AUDIT_2026-10-28_CODEX.md).

1. **Конкуренция за базу (B01).** Держать писателя на копии базы, параллельно дёргать
   `/api/live`, `/api/stats` и авторизацию. Задать предел задержки заранее и проверить его,
   а не любоваться числами.
2. **Надёжность очереди (B02, B04).** Уронить обработчик в середине пачки; отменить воркер;
   перезапустить контейнер с накопленной очередью. Каждое принятое наблюдение должно
   сохраниться, и ни одно уведомление не должно уйти дважды.
3. **Границы очереди (B03).** Переполнить in-memory fallback, остановить и поднять Redis,
   прогнать крупные категории. Смотреть возраст старейшей задачи и число подтверждённых
   записей, а не только `queue_size`.
4. **Аренда и завершение (B06).** Отобрать аренду между постановкой в очередь и записью;
   запустить два экземпляра. «Завершено» должно означать записано.
5. **Готовность (B07).** Остановленный воркер, занятая база, молчащий Redis, отсутствующие
   таблицы — для каждого случая заранее известный HTTP-код.
6. **Нагрузка целиком.** Полная волна на копии базы под лимитом в 4 ядра, рядом
   `docker stats` и снимки `/api/diag`. Сравнить с наблюдением NAS от 28.10
   ([NAS_OBSERVATION_20261028.md](NAS_OBSERVATION_20261028.md)): около 300% CPU,
   load average 15–24, рост памяти, обрыв волны с «результаты больше не записываются».
   Если стенд это воспроизводит — значит на нём можно и чинить.

## Чего стенд не заменяет

- Прод: там свои данные, свой прокси DSM, свой Watchtower и реальные пользователи.
- CI: сборка образа, гейты и публикация остаются в GitHub Actions.
- Наблюдение за живым продом: метрики NAS снимаются только на NAS.
