# Испытательный стенд

Стенд и прод работают на одном Linux-хосте в отдельных каталогах и контейнерах. Стенд собирает образ `kzph-stand:local` из checkout `~/kzph-stand`; прод берёт свой образ из GHCR.

| Параметр | Стенд |
|---|---|
| Адрес | [shdev.molthun.ru](https://shdev.molthun.ru/) |
| Docker | `docker-compose.stand.yml`, контейнер `kzph-stand` |
| Порт хоста | 35539, публичный HTTPS через обратный прокси DSM |
| Данные | `~/kzph-stand/stand-data` → `/app/data` |
| Ресурсы | 4 CPU и 15 ГиБ по основному compose |
| Telegram | Свой тестовый бот и собственный токен |

Лимиты воспроизводят условия прошлых нагрузочных проверок. Актуальные лимиты и политику перезапуска смотрите в применённой конфигурации: checkout может содержать локальное переопределение. Вариант [без лимитов](../docker-compose.stand.nolimits.yml) используется для отдельного замера. Производственный порядок описан в [руководстве по проду](PROD_MOVE_P17E.md).

## Подготовка и доступ

На существующем хосте Docker установлен. Для нового хоста понадобятся Docker с Compose v2, Git, SSH и отдельный SSD/NVMe-каталог данных. Доступ к существующему хосту выдаёт владелец; порт SSH — 2222.

Создайте рабочий checkout и заполните локальный `.env` по [шаблону стенда](../stand.env.example). Публичный адрес задаётся в `APP_URL` и `PUBLIC_ORIGIN` без завершающего слэша. `TRUSTED_PROXIES` должен соответствовать фактическому адресу ближайшего прокси, а `ALLOW_DEV_LOGIN=0` — публичному стенду. Для виджета Telegram привяжите к тестовому боту домен стенда. Для диагностики заполните `DIAG_TOKEN`. [Настройка безопасности](../SECURITY_CONFIG.md)

Токены бота, секреты и настройки прода хранятся отдельно. Два процесса с одним токеном конфликтуют при получении Telegram-обновлений.

## Доставка кандидата

1. На стенде проверьте текущий SHA, `git status --short`, staged/unstaged diff и локальные правки compose. Сохраните их.
2. На машине отправителя сформируйте bundle от известного SHA стенда до ветки кандидата и проверьте его состав.
3. Передайте bundle по SSH. На стенде проверьте его, извлеките ветку во временную ссылку и примените только fast-forward.
4. Для изменений приложения соберите и запустите контейнер. Для документации достаточно обновить checkout.
5. Сверьте SHA, версию приложения, состояние контейнера и результаты сценариев. Запишите результат в [журнал передачи](AGENT_HANDOFF.md).

Пример для локальной ветки `main` и уже переданного файла:

```bash
stand_sha=SHA_ИЗ_CHECKOUT_СТЕНДА
git bundle create /tmp/kzph-candidate.bundle "$stand_sha..main"
git bundle verify /tmp/kzph-candidate.bundle
```

```bash
cd ~/kzph-stand
git bundle verify /tmp/kzph-candidate.bundle
git fetch /tmp/kzph-candidate.bundle refs/heads/main
git merge --ff-only FETCH_HEAD
docker compose -f docker-compose.stand.yml up -d --build
curl -fsS https://shdev.molthun.ru/api/version
curl -fsS https://shdev.molthun.ru/api/health
```

## Данные для тестов

Начинайте с временной или пустой БД. Для миграции и нагрузки берите согласованный снимок через SQLite Backup API либо проверенный комплект ночной копии. Используйте отдельный путь, удалите данные пользователей и проверьте целостность. Перед подменой рабочей БД стенда согласуйте окно, остановите его запись, сохраните резервную копию и проверьте права на файл и набор данных. [Резервирование](PROD_MOVE_P17E.md#ночные-копии)

## Приёмка

- Публичные `/api/version`, `/api/health`, защищённый `/api/diag`; сверка кода и версии.
- Изменённый пользовательский сценарий на desktop и mobile, обе темы; для Telegram — нужное действие в настоящем клиенте.
- Для базы — миграция на копии, проверка целостности, открытие прежним образом либо репетиция восстановления.
- Для очереди, обхода и нагрузки — принятые результаты, потеря аренды, остановка воркера, задержка и возраст очереди. [Первоначальные сценарии нагрузки](FULL_AUDIT_2026-10-28_CODEX.md)

Стенд, CI и работающий прод дают отдельные результаты приёмки. [Порядок выпуска](RELEASE_AND_ROLLBACK.md)
