## G1 · P1 · Защита WAL обходится, когда путь БД — символическая ссылка

**Место:** `scripts/recompute_gpu_models.py:48–59`, открытие БД в `main()`
и запись плана `:164`.

Проверка строит имя служебного файла как `db + side`, а затем применяет realpath.
Если `alias.db` — ссылка на `actual.db`, для WAL проверяется `alias.db-wal`,
который не является ссылкой на `actual.db-wal`. Само соединение при этом открывается
по `Path(args.db).resolve()`, то есть использует настоящую actual.db и её WAL.

**Независимое CLI-воспроизведение на временной БД:**

1. Создать actual.db в WAL-режиме, отключить autocheckpoint и оставить соединение
   открытым после commit, чтобы настоящий WAL существовал и использовался.
2. Создать symlink alias.db → actual.db.
3. Передать утилите `--db alias.db`, `--report actual.db-wal`, **без --apply**.
4. Получить код **0**, `status: planned`; заголовок настоящего WAL меняется
   с `377f0682` на `7b0a2022` (начало JSON).

Следовательно, dry-run пишет в служебный файл работающей SQLite. Это оставшийся
случай опасной перезаписи из F1; блокировать его необходимо до применения утилиты
к живой БД. Рабочие данные не использовались: повреждался только disposable fixture.

**Приёмка:** вычислять защищаемые имена служебных файлов от фактического пути БД,
который открывает SQLite, и согласовать это с проверкой алиасов. Проверить symlink
в аргументе БД и назначения отчёта actual.db-wal/-shm/-journal, dry-run и apply.
Отказ должен происходить до открытия отчёта на запись, с сохранением БД и служебных
файлов. Существующие проверки прямых путей, report-symlink и hardlink сохранить.

Авторский тест `test_report_path_aliases_of_the_database_are_refused` проверяет
алиасы **отчёта** при прямом пути БД; зеркальный случай с алиасом **БД** отсутствует.

## G2 · P2 · Повторный запуск после partial стирает старые значения уже применённой пачки

**Место:** `scripts/recompute_gpu_models.py:160–164, 171–179`;
`write_report()` всегда заменяет существующий файл.

Первый partial-отчёт корректно содержит полный план и применённые ID. Однако при
повторном запуске строится новый план только для оставшихся строк, и он безусловно
записывается поверх прежнего отчёта. Уже изменённые товары больше не входят в план,
поэтому их прежние значения исчезают из единственного сохранённого undo-артефакта.

**Независимое воспроизведение:**

- Созданы 450 искусственных товаров; SQLite-trigger вызывает ABORT на p200,
  то есть во второй пачке.
- Первый apply возвращает **4**, `status: partial`: полный план **450**,
  фактически изменено **200**.
- После удаления тестового trigger повторены те же аргументы и тот же путь отчёта.
- Второй запуск возвращает **0**, все **450** товаров исправлены, но итоговый файл
  содержит план и applied только для **250**. Старые значения первых **200** отсутствуют.
  Других JSON-отчётов или архивов утилита не создала.

Повторный запуск завершает обновление данных, но полного отчёта для отката всей
операции больше нет. Проблема касается заявленного сценария восстановления после
частичной ошибки, а не гипотетического изменения файлов посторонним процессом.

**Приёмка:** сохранять историю предыдущих partial/applied запусков — например,
неперезаписываемым журналом/архивом, либо безопасным продолжением существующего плана.
Допустим и явный отказ от перезаписи с требованием отдельного нового отчёта.
После сбоя и продолжения сохранённые артефакты должны содержать исходные значения
всех 450 строк и фактические результаты всех пачек. Проверить это после повторного
запуска, а не только итоговое состояние БД.

Существующий `test_failure_after_some_batches_is_reported_as_partial` использует
тот же report при повторном запуске, но после него проверяет только модели в БД.
