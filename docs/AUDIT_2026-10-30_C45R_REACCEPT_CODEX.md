## C45RR-01 [P1] Участник без полей переносится вопреки известному объёму из названия

Участки: `product_key.py:419–429`, `product_verify.py:249–260`.

`_merge_conflict` загружает остальных участников групп, но у участника без fields
`identities_conflict` проверяет только сохранённый ключ и ревизию из title. Объём из
названия игнорируется, хотя `title_variants` умеет его извлечь. Общее предупреждение
автора о таких участниках зафиксировано в передаче; это ограничение остаётся существенным
для заявленного критерия C45R-01 о безопасности переноса всей группы.

Независимый сценарий:

1. Группа A: Galaxy S24 **128GB black**, ключ `samsung:s24-a`.
2. Прежняя группа B: Galaxy S24 **128GB white** и Galaxy S24 **256GB blue**,
   оба с ключом `samsung:s24-b`. У первых двух есть поля 128 GB; у третьего полей нет.
3. В очередь ставятся black/white; SAME **верен для проверяемой пары**.
4. Настоящий worker возвращает resolved и переносит всю группу B в A.

После переноса все три ключа — `samsung:s24-a`, все offers.product_id —
`prod_8163b3edceeaae28`. К новому предложению 128 GB присоединяется заведомый 256 GB.
Это не требование исправить все старые ошибки группировки автоматически: существовавшая
ошибка группы B не должна расширяться на новую группу после корректного вердикта по паре.
Вызов `title_variants` для третьего названия в том же сценарии возвращает 256 gb.

Сеть подменена только на границе вердикта; очередь, поля, кэш, предложения, rekey и V2 настоящие.
Прежний сценарий V2/V3 исправлен, но критерий всей группы полностью не закрыт.

**Приёмка:** перед переносом проверять известные варианты из title у участников без полей,
либо отложить перенос до получения недостающих полей. Явные 128/256, компонент/система и
ревизии не обходятся отсутствием fields и старым неспецифичным ключом. В этом сценарии
общего переноса не происходит; при отказе кэш, offers/history, aliases и память наблюдений
не меняются. Добавить регрессии для третьего участника без полей по обе стороны переноса.

## C45RR-02 [P2] Старая таблица k2_migration_runs не получает api_started

Участок: `scripts/migrate_to_k2.py:331–361`.

В CREATE TABLE добавлена колонка api_started, но для уже существующей таблицы нет
обновления схемы. CREATE TABLE IF NOT EXISTS оставляет прежнюю структуру, а load_baseline
сразу выполняет SELECT с новой колонкой.

Временная БД с **точной схемой из ae9dcf9**, существующим run_id, baseline и счётчиками
при вызове настоящего run_migration падает до обработки названий:

`OperationalError: no such column: api_started`.

Новая БД проходит штатные тесты; сохранённый проход прежней версии не возобновляется.
Замечание относится к совместимости форматов учёта между версиями скрипта этой ветки.
Наличие такой таблицы на реальной копии стенда или на проде в этой итерации не утверждается.

**Приёмка:** существующая схема корректно обновляется с сохранением run_id, неизменяемого
baseline и старых счётчиков. api_started/api_unfinished инициализируются согласованно,
без отрицательных/выдуманных незавершённых вызовов. Проверить обычный resume, повторное
открытие и dry-run старого формата; dry-run не меняет исходную БД. Не требовать удаления
таблиц или сброса прохода ради продолжения.
