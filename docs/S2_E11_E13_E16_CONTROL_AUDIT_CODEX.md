## Найденные дефекты

### C-E13-01 (P1, privacy/security): сырой запрос сохраняется и публично отдаётся гостю

`search_events` содержит обязательное поле `query`; оба v2 endpoint записывают в
него исходную строку. `normalize_search_query()` лишь меняет регистр, пунктуацию и
порядок слов, но не удаляет телефон, почту, адрес или другие чувствительные
значения. Затем публичный endpoint `/api/v2/analytics/search-quality` без
`require_admin` возвращает `MIN(query)` как `sample_query`.

Изолированное воспроизведение с синтетическим маркером:

```text
GET /api/v2/search?q=AUDIT_PERSON_77011234567@example.invalid -> 200
GET /api/v2/analytics/search-quality без входа -> 200
top_queries[0].sample_query = AUDIT_PERSON_77011234567@example.invalid
search_events.query = AUDIT_PERSON_77011234567@example.invalid
```

Это прямо противоречит P06 и уже принятому контуру `search_analytics.py`, который
отбрасывает чувствительный текст до записи, канонизирует город, не хранит текст
редкого запроса до третьего повторения и публикует отчёт только в админском
мониторинге.

Критерий исправления:

- не хранить сырой запрос и чувствительный `normalized_query` в новом контуре;
- переиспользовать действующий privacy-контракт P06 вместо параллельной ослабленной
  реализации либо документированно мигрировать его без потери защит;
- закрыть детальную аналитику админской авторизацией; наружу не возвращать
  `sample_query` для чувствительных или редких запросов;
- добавить негативные тесты для телефона, почты, адреса, длинного номера,
  произвольного `city` и гостевого доступа.

### C-E13-02 (P1): SSR включает ERROR в знаменатель и расходится с принятым KPI

Принятый P06-контракт:

```text
FOUND / (FOUND + WEAK + NOT_FOUND)
ERROR не входит в знаменатель и показывается отдельным error_rate
```

Новый `SearchAnalyticsRepository` считает `FOUND / total_searches`, включая
`ERROR`, и не возвращает `error_rate`. Нынешний тест закрепляет ошибочное значение:
для 6 FOUND, 2 WEAK, 1 NOT_FOUND, 1 ERROR ожидает 60%, хотя действующий контракт
даёт 66,7% и отдельный error rate 10%.

Критерий исправления: одна формула во всех API/экранах, отдельный `error_rate`,
регрессия на выборке с ошибкой backend.

### C-E13-03 (P2): город из естественного запроса теряется в аналитике

Search Core корректно определяет город внутри запроса и записывает его в
`resp.parsed_query.detected_city`, но оба endpoint создают `SearchEvent(city=city)`,
где `city` — только явный query parameter. Поэтому `айфон астана` без `&city=`
попадает в аналитику с `city = NULL`; произвольный `&city=` при этом сохраняется без
канонизации. Сигналы спроса дробятся по способу ввода и могут содержать
чувствительный произвольный текст.

Критерий исправления: использовать итоговый канонический город из parser/override и
тот же справочник/контракт `canonical_city`, что уже действует в P06.

### C-E13-04 (P2): заявленный retention фактически не выполняется

`purge_old_events(days=90)` существует только как метод и вызывается только тестом.
Фоновое обслуживание вызывает старый `prune_search_analytics`, но не очищает новую
таблицу `search_events`. Это создаёт неограниченное хранение, особенно опасное при
дефекте C-E13-01.

Критерий исправления: после решения по архитектуре подключить одну проверяемую
retention-политику и тест реального maintenance path, а не только прямого вызова
метода репозитория.

### C-E16-01 (P1): фильтры «Новое» и «Б/у» из UI всегда дают пустую выдачу

UI отправляет `condition=new|used`, а `SearchRepository` сравнивает это значение с
хранящимися enum `NEW|USED` без нормализации. Фактический результат на фикстуре с
двумя NEW и одним USED оффером:

```text
condition=new  -> 0 товаров, 0 офферов
condition=used -> 0 товаров, 0 офферов
condition=NEW  -> 1 товар, 2 оффера
condition=USED -> 1 товар, 1 оффер
```

Оба существующих теста проходят ложно: они перебирают возвращённые офферы, но не
проверяют, что результат непустой.

Критерий исправления: нормализовать condition на серверной границе и добавить
проверки ненулевого результата и отсутствия офферов другого состояния.

### C-E16-02 (P1): карточка читает цену и счётчики не из тех полей API

`ProductSearchResult.to_dict()` отдаёт `min_price`, `max_price`, `sellers_count` и
`offers_count` на верхнем уровне item. Renderer присваивает `p = it.product`, после
чего читает `p.min_price`, `p.max_price`, `p.stores_count`, `p.offers_count` и
`p.condition`, которых в canonical product нет. Кроме того, condition API имеет
верхний регистр, а JS сравнивает с `used/refurbished`.

Браузерное воспроизведение с валидным item (`430000..550000`, 2 продавца, 3 оффера,
USED) отрисовало:

```text
✨ Новое
1 маг. • 1 предл.
Цена не указана
```

Критерий исправления: читать агрегаты из `it`, состояние выводить по
`conditions_available`/офферу без ложного общего бейджа и добавить настоящий
browser-тест значений DOM, а не только поиск строк в исходном HTML.

### C-E16-03 (P1): совместимый endpoint снова делает stale/out-of-stock лучшей ценой

Search Core правильно возвращает `best_offer = null`, если пригодных к покупке
офферов нет. Но адаптер `/api/best-price?v2=1` при пустом `valid_offers` намеренно
подставляет все положительные цены, включая stale и out-of-stock, а
`store_comparison` вообще не проверяет `is_purchasable`.

Изолированное воспроизведение с единственным out-of-stock оффером от 2020 года:

```text
item.best_offer = null
response.best_deal.price = 123456
response.store_comparison = [{shop: "Repro Web", min_price: 123456}]
```

Это повторно открывает C-E11-03 на реальном интеграционном пути.

Критерий исправления: best deal, статистика и сравнение магазинов строятся только
по `is_purchasable`; при отсутствии таких офферов возвращаются честные null/empty и
отдельное состояние «нет актуальной доступной цены».

### C-E16-04 (P1): включённый по умолчанию v2 молча игнорирует основные фильтры

Форма передаёт `shop`, `category`, `only_discount`, `exclude_acc`, `mode`, `neg` и
`live`, но v2-ветка прокидывает в Search Core только city/condition/channel/price/
sort/limit. `live=1` проходит проверки доступа, но живой опрос не выполняется.
Поскольку чекбокс v2 отмечен по умолчанию, это меняет смысл существующей формы для
всех пользователей.

Проверка с несуществующими `shop` и `category` всё равно вернула 1 товар и 3
оффера.

Критерий исправления: либо реализовать эквивалентные фильтры/режим live, либо явно
отключать недоступные элементы и держать v2 opt-in до функционального паритета.

### C-E16-05 (P2): заявленные автосохранение и fallback отсутствуют

Для `checkSearchV2` нет чтения/записи `localStorage`. При пустом v2 ответе сервер
всё равно возвращает `v2: true`, поэтому renderer остаётся в v2-ветке, скрывает
классическую таблицу и показывает пустую карточку; повторного legacy-запроса нет.

Критерий исправления: сохранить явный выбор пользователя и определить один
проверяемый fallback-контракт. Пустой корректный результат нельзя автоматически
выдавать за технический сбой; fallback должен отличать эти случаи.
