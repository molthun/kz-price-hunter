## Подтверждённые замечания

### A01 — P1: сырой текст HTTP-ошибки обходит очистку URL

Место: `telemetry.py:311–319`, `sanitize_payload` и `record_event`.

Поле `data.url` проходит `sanitize_url`, но то же значение из исключения попадает в `message` и `data.error` через общий `redact_secrets`. Этот фильтр не удаляет пароль из userinfo URL и параметр `signature`. Синтетический `ConnectionError: https://alice:FAKE_PASSWORD@shop.example/api?signature=FAKE_SIGNATURE` сохраняет оба маркера в событии. Это не утверждение об обнаруженной утечке реальных ключей: проверка использовала только выдуманные значения. Дополнительно `sanitize_payload({'Cookie': 'sid=FAKE_COOKIE'})` сохраняет Cookie без очистки.

Последствие: транспортная диагностика может сохранять секреты в памяти и далее в таблице событий на 30 дней, несмотря на очищенное соседнее поле URL.

Рекомендация: вместо сырого исключения сохранять безопасную категорию/код; если текст нужен — обрабатывать вложенные URL и чувствительные поля структурно, по разрешённому набору. Cookies, Authorization, userinfo, signed URL не должны сохраняться. Не ограничиваться расширением одного regex для signature.

Приёмка: проверить message, data_json, память и строку БД после flush на отсутствие синтетических маркеров userinfo/signature/Cookie/Authorization, включая вложенные структуры и исключения сериализации; полезный host/status/class ошибки остаётся.

### A02 — P2: ограничение 4 КБ не соблюдается на Unicode

Место: `telemetry.py:174–176`.

После проверки байтовой длины обрезается количество символов (`max_bytes // 2`), затем добавляется JSON-обёртка. Для `{'x': '😀' * 10000}` результат занимает **8209 байт** при лимите 4096. ASCII-тест существующего набора это не замечает.

Рекомендация: ограничивать размер окончательно сериализованного UTF-8 JSON с учётом обёртки и экранирования; сохранять валидный JSON и не разрывать символы. Безопасный краткий ответ при ошибке сериализации также должен проходить очистку/лимит.

Приёмка: ASCII, кириллица, emoji, кавычки, обратные слеши и управляющие символы дают валидный JSON не более 4096 байт.

### A03 — P2: при переполнении буфера p95 систематически теряет хвост

Место: `telemetry.py:352–355`, `_flush_aggregate`.

До flush сохраняются только первые 2000 latency на ключ, остальные отбрасываются, хотя total_requests продолжает расти. Algorithm R в БД уже не может восстановить равномерную выборку по всем запросам. Воспроизведение: 2000 запросов по 1 мс, затем 1000 по 1000 мс до одного flush; total_requests=3000, p95=**1 мс** вместо **1000 мс**, dropped_samples=3000 (три бакета). Нагрузка синтетическая; частота достижения лимита на проде не измерялась.

Рекомендация: reservoir или совместимая квантильная структура уже на входе; при слиянии учитывать число наблюдений и веса. Либо явно обозначать квантиль неполным при потере samples, не выдавая его за p95 всего бакета.

Приёмка: slow-tail и fast-tail после 2000 наблюдений, несколько flush, несколько бакетов; оценка не зависит систематически от порядка поступления, память ограничена, total_requests сохраняется.

### A04 — P2: отменённый обход записывается как успешный

Место: `web/server.py:1244–1246`, `1259–1264`.

При обычном CancelledError (остановка приложения, без потери lease) ошибка пробрасывается, но finally пишет scan_end по `scan_state.error`, оставшемуся None. Воспроизведено на настоящем `_do_scan_task` с подменой тела обхода и операций lease: `task.cancelled() == True`, но событие имеет severity INFO и сообщение **«Итог обхода (manual): ок»**. В проверенном сценарии is_running корректно сброшен; зависание не заявляется.

Рекомендация: явный outcome completed/failed/cancelled/lease_lost; отмена не является успешным завершением. Очистка состояния должна выполняться независимо от записи/flush телеметрии.

Приёмка: обычная отмена, потеря аренды, ошибка тела и успешный обход дают разные корректные исходы; аренда/флаги/контекст освобождены, отмена не маскируется.

### A05 — P2: HTTP-данных недостаточно для заявленной диагностики P01

Место: `telemetry.py:301–319`, `332–341`; таблицы HTTP в `database.py`.

401/403/404 сливаются в status_4xx. Обычный 403/5xx не создаёт диагностического события (только 429 и transport error), а агрегат не хранит scan_id/category/request_id. Поэтому после успешного получения HTTP 403 невозможно восстановить из этой телеметрии, какой код и в какой части конкретного обхода произошёл. Наличие contextvars само по себе не сохраняет эту связь. Существующий тест 200→403 подтверждает лишь общий счётчик 4xx.

Рекомендация: сохранить отдельные требуемые коды (либо распределение кодов) и ограниченную по объёму диагностику ошибок с scan_id/category и безопасным адресом. Для успешных страниц допустима ограниченная трасса/сводка; бессрочная запись каждого HTTP не нужна. Уточнить минимальный контракт цепочки «обход → страницы → результат», затем покрыть тестом.

Приёмка: сценарий page1=200, page2=403 отличим от 404/401/500, связан с нужным scan_id и категорией; счётчики запросов совпадают, retention и ограничения объёма соблюдаются.

```bash
DATA_DIR="$(mktemp -d)" ./venv/bin/python - <<'PY'
import random
import database

t = TelemetryService()
url = 'https://alice:FAKE_PASSWORD@shop.example/api?signature=FAKE_SIGNATURE'

                     error='ConnectionError: ' + url, url=url)

print('A01:', {s: s in e['message'] + e['data_json']
               for s in ('FAKE_PASSWORD', 'FAKE_SIGNATURE')})

t = TelemetryService()
random.seed(42)

for v in values:
    t.record_http_metric('latency.example', 'GET', 200, v)
assert t.flush()
a = t.get_http_summary()[0]
print('A03:', a['total_requests'], a['latency_p95_ms'], calculate_p95(values))
PY
```
