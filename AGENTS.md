# Совместная работа над KZ Price Hunter

## Роли и полномочия
- Владелец: идеи, приоритеты, запуск и администрирование прода, поиск проблем, продуктовая приёмка.
- Antigravity (Антигравити): основной разработчик.
- Claude (Клоуд): исправление ошибок, реализация рекомендаций аудита; подхватывает разработку после Antigravity.
- Codex: аудит, рекомендации, описание идей и критериев приёмки. Также пишет код по прямому поручению владельца или при передаче ему уже разрешённой задачи разработки.
- Порядок подхвата разработки: **Antigravity → Claude → Codex**. Прямое назначение владельца имеет приоритет. Передача не расширяет объём разрешённой работы.

## Начало каждой сессии
1. Прочитать `docs/DEVELOPMENT_PLAN.md` и `docs/AGENT_HANDOFF.md`.
2. Проверить текущую ветку, HEAD, `git status --short`, staged и unstaged diff. Сохранить чужие изменения. Не выполнять reset/clean/checkout поверх них.
3. Прочитать карточку текущей задачи и связанные файлы. Сверять заявления старых отчётов с кодом; не считать число тестов или версию в старом документе текущим фактом.
4. Если поручена реализация, записать исполнителя, время и область файлов в реестр до правок. По умолчанию в общем checkout работает один пишущий агент. Реестр — договорённость, не техническая блокировка.
5. Продолжить ближайший незавершённый шаг, не переписывая уже выполненное. Если это аудит, записать выводы и рекомендации; не начинать реализацию без поручения или передачи.

## Работа и передача
- После каждого завершённого небольшого шага обновлять карточку в `docs/AGENT_HANDOFF.md`: что изменено, что проверено, что осталось, следующий точный шаг.
- При приближении лимита сохранить checkpoint заранее, не ждать последнего ответа. Состояние хранить в файлах проекта, а не только в чате агента.
- При смене агента следовать протоколу в `docs/AGENT_HANDOFF.md`. Исчерпание токенов не означает, что фоновые команды остановлены.
- Не редактировать одновременно одни и те же файлы. Для отдельно порученных независимых работ использовать разные checkout/worktree и согласовать интеграцию.
- Коммитить только файлы своей задачи после просмотра diff; не включать чужие правки и секреты. Незавершённую работу можно передать без коммита, явно перечислив файлы.

## Проверки и выпуск
- Проверять поведение, а не только наличие кода. Указывать команды, окружение, результат и непроведённые проверки.
- Тесты и миграции проводить на временных данных/копии БД, не на рабочей `prices.db`. Для работающей SQLite использовать согласованный snapshot через backup API, не обычное копирование одного файла при активном WAL.
- Не выводить и не сохранять содержимое ключей, cookies, токенов и личных данных в отчёты. Существующие реальные ключи не заменять самовольно.
- Mock/fallback не подтверждает работу реального AI-провайдера. Реальные вызовы и их стоимость отражать отдельно.
- `ROADMAP_AND_LOG.md` и `CHANGELOG.md` — история реализации; рабочая очередь следующего поколения — `docs/DEVELOPMENT_PLAN.md`, текущая передача — `docs/AGENT_HANDOFF.md`.
- Push в `main` запускает публикацию образа; по документации проекта `latest` забирает Watchtower. Не использовать push в main как способ передачи между агентами. Выпуск и изменения прода — по поручению владельца; уже данное разрешение не запрашивать повторно.
- Для релиза учитывать `version.py`, CHANGELOG и дорожную карту. Для правок только документации версию не повышать.
- Результат реализации, независимый аудит и подтверждение на проде фиксировать отдельно. Не объявлять этап внедрённым по локальным тестам.
